Unsorted Maps and HashingData Structures · Chapter 7

An array finds item number 500,000 at once, because the position is the key. This chapter keeps that speed for keys that are words, names or order numbers: a hash function turns the key into a position, and the table jumps straight to it, without keeping the keys in order. Two keys sometimes land in the same slot, so we meet the two ways to handle a collision, chains and probing, what makes deleting tricky, and the rule that keeps the table fast as it fills: rebuild it bigger before it gets crowded.

Put keys in a table

Type a key or pick one from the list and press Put: the hash code is shown, then its remainder modulo the number of slots, then the key drops into that slot of a seven-slot table; when the slot is taken the key is appended to the chain of that slot and a counter shows how many keys were compared. Press Get to see a lookup walk the chain.

Why this matters

about 90–120 minutes (4 videos of 8–10 minutes plus the exercises).

Jump instead of search

A dictionary, a set, a cache, a symbol table, a database index and a "have I seen this before?" check are all a map from keys to values. A hash table answers get and put in about one step, however many keys it holds, while a sorted structure of chapter 6 needs about log n.

A good hash and a good table are a pair

The speed is an average: it needs a hash function that spreads the keys and a table that is not overcrowded. A bad hash function turns the table into one long list, and a table that never grows slows down with every key; this chapter shows both, with real numbers.

Equal keys must hash equally

Hashing is a contract between your key class and the table. Break it, or change a key after it has been stored, and the map does not crash: it quietly loses data. This is the most common bug in code that uses hash maps.

§1From a key to a slot

The hash code is any rule that maps a key (a word, a pair, a record) to an int. Compression maps that number to an index of a table with m slots; the simplest rule is the remainder, h mod m. The word "hello" has the hash code 99,162,322; in a table with 13 slots its index is 99,162,322 mod 13 = 12 (code/py/hash_demo_output.txt, identical in Java). A prime m helps, because a prime has no factors in common with the patterns found in real keys. There are far more possible keys than slots, so two different keys sometimes get the same slot: a collision. The words "Aa" and "BB" are different keys with the same hash code, 2,112. Collisions cannot be avoided; we make them rare and we handle them when they happen (videos 2 and 3).

Hash a key

Pick a word and a table size: the characters are combined one by one into the hash code, the code is reduced modulo the table size and the key lands in a slot; picking "Aa" and "BB" shows two keys with the same code in the same slot.

§2Spreading the keys

A table is fast only if the keys are spread evenly. A tempting hash function adds up the character codes, and it is terrible: rearranging letters never changes their sum, so all 720 anagrams of "abcdef" get the same hash code and fall into one bucket of a table with 1,009 buckets, a chain of 720 keys. The polynomial hash treats the characters as digits written in base 31, so the position of every letter counts: h = s₀·31ⁿ⁻¹ + s₁·31ⁿ⁻² + … + sₙ₋₁. The same 720 keys now get 720 different hash codes and the longest bucket holds 4 (514 buckets stay empty, close to the 494 that random placement gives).

The words "stop" and "pots" show it in miniature: both have the character sum 454, but their polynomial codes are 3,540,994 and 3,446,974. Java computes exactly this polynomial in String.hashCode, with int arithmetic that wraps around at 32 bits, so some hash codes are negative.

PREDICT

Put the 720 anagrams of "abcdef" in a table with 1,009 buckets. With the "sum of the letters" hash, how long is the longest chain? And with the polynomial hash?

Show the answer

720 and 4. The sum of the letters does not change when the letters are rearranged, so every anagram has the same hash code and the table is a single list of 720 keys: a lookup takes 720 comparisons instead of about one. The polynomial hash gives 720 different hash codes; four keys share a bucket at worst. The only thing that changed is the hash function.

§3Two rules for keys

  1. Equal keys must have equal hash codes. If two equal keys hashed to different slots we would look in the wrong slot and never find what we stored. Example: a reading class whose equality compares only the temperature but whose hash code also uses the reading number: two readings of 20 degrees are equal, but b in dict is false after the dictionary stored a.
  2. A key must not change while it is in the table. Its hash code is used once, when it goes in. A point stored with x = 1 and then changed to x = 9 sits in the slot of its old value: a lookup with the old value fails, and so does one with the new value, yet the map still counts the entry (size 1, unreachable).
PITFALL · Rule 2 is about the fields that equality and hash use.

Changing a field that neither uses is harmless, but the safest keys are immutable (a string, an integer, a tuple, a record).

The polynomial hash is in code/py/hashing.py: to_int32 wraps a Python integer (which never overflows) to a signed 32-bit value and poly_hash applies it at every step, so that for base 31 it equals Java's String.hashCode. In Python % is never negative for a positive m (-3 % 7 is 4), so compression is one operator. A class that defines __eq__ but no __hash__ is unhashable: using it as a key raises TypeError, which protects you from the commonest mistake. The built-in hash of a string is randomized per process (a new secret seed at every start, a protection against attackers who craft colliding keys): never save it to a file and do not rely on the iteration order of a set of strings (code/py/hash_seed_demo.py).

The polynomial hash is in code/java/HashCodes.java: an int wraps around at 32 bits by itself, so polyHash("hello", 31) is exactly "hello".hashCode(), 99,162,322. The % operator keeps the sign of its left side, so -3 % 7 is −3, a negative index that would crash a table: compress with Math.floorMod(h, m), which gives 4. The contract of equals and hashCode says that equal objects must return the same hash code; if you override equals and forget hashCode, the class inherits the identity hash code of Object, two equal objects hash differently and map.get(equalKey) returns null, with no error. The string "polygenelubricants" has the hash code −2,147,483,648, the most negative int, whose absolute value is still negative: one more reason to use floorMod. Compare keys with equals, never with ==.

NOTE · Why the Python and Java traces in this chapter are identical.

An integer hashes to itself, and our own string hash is Java's, so the Python and Java maps of this chapter place every key in the same slot and print the same numbers.

§1A list of lists

The table is an array of m buckets; bucket i holds the entries whose index is i, in a chain (the singly linked list of chapter 2, or a small array list). put(key, value) computes the index, walks the chain looking for the key, replaces the value if it finds it and otherwise appends a new entry at the end; get walks the same chain; remove unlinks the entry from it. Every operation touches one chain only. In the example the table has 7 buckets, the hash code of an int is the int itself and the keys 12, 44, 13, 88, 23, 94, 11, 39, 20, 16 arrive in this order (code/py/trace_demo_output.txt, identical in Java):

The load factor is 10/7 = 1.43 and the longest chain has 3 keys. get(12) takes 1 comparison, get(16) takes 3, and get(9), which is absent but hashes to bucket 2, takes 3: the whole chain. Finding each of the ten keys once costs 17 comparisons, 1.70 on average.

Chains in action

Put the ten keys of the example one after another into seven buckets and watch each one hash to its slot and join the chain; then press Get on a key (or on one that is not there) to see the comparisons walk the chain, counted one by one, and the average cost of all ten keys.

PREDICT

With a good hash, 1,000 keys in a table of 1,000 buckets: about how many keys does a chain hold on average, and about how many comparisons does a successful search need?

Show the answer

The load factor is 1.0, so a chain holds 1 key on average, and a successful search needs about 1 + α/2 = 1.5 comparisons (an unsuccessful one about 1). Some chains are empty and a few hold 3 or 4 keys; the average is what counts, and it stays constant however large the table is, as long as the load factor does (Exercise 1 proves the formula).

§2What it costs

If the hash spreads the keys, a chain holds about α = n/m keys, the load factor, so get, put and remove cost about 1 + α: O(1) on average as long as α stays bounded. The textbook estimate for a successful search is 1 + α/2 = 1.71 here, close to the measured 1.70. But "O(1)" is an average for a good hash on a table that is not overloaded. The anagram experiment of video 1 is the worst case: 720 keys in one chain, 720 comparisons per lookup; with the polynomial hash the longest chain is 4.

PITFALL · "A hash table is always O(1)."

It is O(1) on average, under the assumption that the hash spreads the keys; the worst case is O(n), and an attacker can craft keys that all collide (the reason for Python's randomized string hash).

ChainedHashMap in code/py/chained_map.py keeps buckets, a list of chains, and remembers a trace of the last operation (hash code, index, probes, comparisons) so that the numbers above are real. put returns the old value, remove raises KeyError for a missing key, and the map is checked against a built-in dict on random operations. Python's own dict does not use chaining (next video).

ChainedHashMap<K,V> in code/java/ChainedHashMap.java is an array of Nodes, each with a key, a value and the next node, and the loop in put walks the chain comparing keys with equals. The standard java.util.HashMap is a chaining table too: an array of nodes holding the hash code, the key, the value and the next node, with one difference: since Java 8 a long chain is turned into a balanced tree (video 4).

Open addressing

Chaining needs a list for every slot. Open addressing needs nothing but the table: every entry lives in the array, and when the slot you want is taken you probe another slot, following a fixed sequence that depends on the key, so a lookup can follow the same sequence. Linear, quadratic and double hashing differ in the sequence. Deleting must leave a tombstone, not an empty slot, or the probe sequences of other keys break.

§1Probing

The table has 13 slots; a key goes to slot h mod 13. If that slot is taken, the next slot of the key's probe sequence is tried. The keys 18, 41, 22, 44, 59, 32, 31, 73 have the home slots 5, 2, 9, 5, 7, 6, 5, 8 and show the three rules (code/py/trace_demo_output.txt, identical in Java):

With linear probing the final table is - - 41 - - 18 44 59 32 22 31 73 -: slots 5 to 11 form one unbroken run of seven, a cluster; a key that hashes anywhere into a cluster has to walk to its end, and every key that joins makes it longer (31 needed six probes). Quadratic probing (the offsets 0, 1, 4, 9, …) spreads the keys out and avoids clusters, and double hashing (a second hash decides the step) uses a different step for every key; both need a prime table size (Exercise 2).

Probe the table

Put the eight keys into a 13-slot table with the probing rule of your choice (linear, quadratic, double): every probe is highlighted slot by slot until a free slot is found, the cluster of linear probing grows on screen and a counter adds up the probes of each rule.

§2Deleting needs a tombstone

Delete 44 from the linear table by emptying its slot 6, and then look for 32: its home slot is 6 and that slot is now empty, so get(32) stops after one probe and answers "missing", although 32 is in slot 8. Searches stop at an empty slot; emptying a slot in the middle of a run breaks every key that was pushed past it.

PREDICT

After deleting 44 by emptying slot 6, where does get(32) stop, and what does it answer? What should the table do instead?

Show the answer

get(32) probes only [6] (empty: stop) and answers "missing". Instead the table leaves a tombstone in slot 6, a mark that says "something was here": get skips it and carries on, probing [6, 7, 8] and finding 32, and a later put may reuse the tombstone. (Another way for linear probing, without tombstones, is the backward shift of Exercise 5.)

Delete a key

Delete 44 from the linear-probing table in two ways: emptying the slot, where the lookup of 32 stops at once and fails, and leaving a tombstone, where the lookup walks past the mark, probes [6, 7, 8] and finds 32; then put a new key and watch it reuse the tombstone.

Tombstones count toward the load: a search stops only at an empty slot, so a table crowded with tombstones is as slow as a crowded table, and it must be rebuilt (a rehash drops them). A table with no empty slot at all would make a naive probe loop run forever: Exercise 10.

PITFALL · "To delete, just empty the slot."

It silently loses every key that was probed past that slot (the key 32 above). Use a tombstone, or the backward shift of Exercise 5, and count tombstones toward the load factor.

Load factor and rehashing

Every put makes the table fuller and a fuller table is slower. The remedy is the one the dynamic array uses: when the load factor passes a threshold, build a bigger table and re-insert every entry (rehashing). Entries must be re-indexed, because the index depends on the table size. Since the table grows by a factor, not by a constant, the rebuilds cost O(1) per put on average.

Load factor and rehashingVideo in preparation.
IN THIS CHAPTER§1 Growing the table§2 Why a put is still O(1)

§1Growing the table

The load factor is α = n/m. A chaining table is happy up to about 0.75 (a chain of 0.75 keys on average), an open-addressing table wants to stay below about ½ to ⅔ (the table above). When a put pushes α over the threshold, the map allocates a table with about twice as many buckets (the next prime above 2m in our code) and re-inserts every entry. It is not enough to copy the old array into a bigger one: the bucket of a key is h mod m, and m has changed. The key 44 lives in bucket 44 mod 7 = 2 of a table of 7, but a lookup in a table of 17 looks in bucket 44 mod 17 = 10. Every entry must be hashed again.

Watch a rehash

Put keys into a table of 7 buckets: when the load factor passes 0.75 the table is replaced by one with 17 buckets and every entry flies to its new bucket, with its old and new index shown and a counter of the moves; keep pressing Put to see the next rehash, 37 buckets, and compare the total number of moves with the number of puts.

§2Why a put is still O(1)

A rehash costs n steps, but it is rare. 1,000 puts into a chained map that starts with 7 buckets and grows to the next prime above its double at load factor 0.75 (code/py/rehash_demo_output.txt, identical in Java):

The moves add up like a geometric series, each rehash about twice the previous one, so the total is below 2n: the same argument as the doubling of the dynamic array in chapter 1 (Exercise 3 proves it, and shows that growing by a fixed number of buckets would cost n²/(2λc) moves instead). A map whose final size is known can skip all of them: presized to 1,361 buckets, the same 1,000 puts need 0 rehashes and move nothing.

PREDICT

A table of 7 buckets grows to 17 when its sixth entry arrives. The key 44 was in bucket 2. In which bucket is it afterwards?

Show the answer

In bucket 10, because 44 mod 17 = 10: the index depends on the table size, so every entry is hashed again. The misconception to avoid is "copy the old array into a bigger one".

ChainedHashMap in code/py/chained_map.py rehashes at the end of put (_rehash re-inserts every entry and counts the moves). CPython's dict does the same with its own numbers: its memory size changes when the 1st, 6th, 11th, 22nd, 43rd and 86th key is added (code/py/dict_growth_demo.py); the table has 8 slots with 5 usable (two thirds), then 16 with 10, 32 with 21, 64 with 42 and 128 with 85: the load factor is kept below two thirds and the table roughly triples the number of used entries, rounded up to a power of two. Since Python 3.7 the entries are stored in a compact array, in insertion order, and the sparse table holds only indexes into it.

ChainedHashMap<K,V> in code/java/ChainedHashMap.java ends put with the check and a rehash that walks the old nodes and appends each to its new chain. java.util.HashMap has default capacity 16 and load factor 0.75, so the first resize happens when the 13th entry arrives; its table size is always a power of two and the index is (n - 1) & (h ^ (h >>> 16)), a mask instead of a remainder; since Java 8 a chain of 8 or more entries is turned into a balanced tree when the table has at least 64 buckets, and back into a list when it shrinks to 6. To avoid rehashing when you know the size, give the capacity in the constructor (HashMap.newHashMap(n) since Java 19).

NOTE · Both languages keep the table sparse on purpose.

A hash table trades memory for speed: Python's dict keeps at least a third of its slots empty and Java's map a quarter, and that waste is exactly what keeps the chains and probe sequences short.

§2Check your understanding

1. Two keys a and b are equal (a.equals(b) is true). What must be true for a hash map to find a's entry when you look up b?

The slot is chosen from the hash code, so equal keys must hash equally; if the hash codes differ the table looks in a different slot and never finds the entry, although equals is true.

2. A table with separate chaining holds n = 10 keys in m = 7 buckets and the hash spreads the keys uniformly. About how many key comparisons does a search for a key that is not in the table take on average?

The absent key hashes to a random bucket and is compared with every key of its chain, whose average length is the load factor α = 10/7 = 1.43.

3. In a linear-probing table, key 44 sat in slot 6 and key 32, whose home slot is also 6, was pushed to slot 8. Slot 6 is emptied to delete 44. What does get(32) do?

A search stops at the first empty slot, so emptying a slot in the middle of a run makes the keys behind it unreachable; a tombstone makes the search carry on.

4. A chained table with 7 buckets grows to 17 buckets. Why must every entry be hashed again, and not just copied to the same bucket number?

The index depends on the table size.

5. A map doubles its table when the load factor passes a threshold. What is the amortized cost of a put?

Each rehash moves about twice as many entries as the previous one, a geometric series; growing by a fixed number of buckets instead would cost about n²/(2λc) moves.

PROOFS

Exercise 1 · Expected chain length. Simple uniform hashing: every key goes to each of the m buckets with probability 1/m, independently of the other keys. n keys are stored by separate chaining, a new key is appended at the end of its chain, and α = n/m is the load factor. (a) Prove that the expected length of any given bucket is α. (b) An absent key is searched; its bucket is uniformly random. Show that the expected number of key comparisons is α (it walks the whole chain), so the cost is Θ(1 + α) with the hash computation. (c) A stored key, chosen uniformly among the n stored keys, is searched. Show that the expected number of comparisons is exactly 1 + (n − 1)/(2m), which is less than 1 + α/2. (Hint: the key inserted j-th is preceded in its chain by each of the j − 1 earlier keys with probability 1/m.) (d) Evaluate (a)–(c) for the map of video 2 (n = 10 keys, m = 7 buckets) and compare with what the video measured: chain lengths 0, 0, 3, 1, 3, 1, 2, and 17 comparisons for finding each of the ten keys once (1.70 on average). Also compute the expected number of empty buckets, m(1 − 1/m)ⁿ, and compare it with the two empty buckets of the video. Is one measurement that differs from an expectation a contradiction?

Solution

(a) Let Xₖ = 1 if key k is in the given bucket, else 0. Then P(Xₖ = 1) = 1/m, and the length of the bucket is X₁ + … + Xₙ, so by linearity of expectation E[length] = n · (1/m) = α. (No independence is needed for this step.) ∎

(b) The absent key hashes to a uniformly random bucket, independently of the stored keys, and a failed search compares it with every key of that chain, so the expected number of comparisons is E[length of a random bucket] = α. This holds for any set of stored keys, because the average of the m chain lengths is n/m whatever they are. With the hash computation and the index the cost is Θ(1 + α). ∎

(c) Number the keys 1, …, n in the order of insertion. A successful search for key j compares it with the keys before it in its chain and then with itself: 1 + (the number of earlier keys i < j in the same bucket) comparisons. Each earlier key shares the bucket with probability 1/m, so the expectation is 1 + (j − 1)/m. Choosing j uniformly: (1/n) Σⱼ (1 + (j − 1)/m) = 1 + (1/(nm)) · n(n − 1)/2 = 1 + (n − 1)/(2m) = 1 + α/2 − α/(2n) < 1 + α/2. (Checked exactly, by enumerating all mⁿ assignments for small n and m, in test_ex7_claims.pyEx7ClaimsTest.java.) ∎

(d) n = 10, m = 7, α = 1.43. (a) A bucket holds 10/7 = 1.43 keys on average (the video's chain lengths 0, 0, 3, 1, 3, 1, 2 add up to 10: this holds for any ten keys). (b) An absent key costs 1.43 comparisons on average (3 for the key 9 of the video, which is one particular bucket). (c) A stored key costs 1 + 9/14 = 1.643 on average (the rule of thumb 1 + α/2 gives 1.714; the video quotes 1.71). The video measured 17/10 = 1.70: the chains of 3, 1, 3, 1, 2 keys cost 6 + 1 + 6 + 1 + 3 = 17 comparisons. The expected number of empty buckets is 7 · (6/7)¹⁰ = 1.50; the video has two. These are not contradictions: an expectation is an average over all possible key sets, and the video shows one set of ten keys, whose chains are a little uneven (two chains of 3). A Monte Carlo experiment with random buckets (60,000 trials, test_monte_carlo_agrees) gives averages that match 1.643, 1.43 and 1.50 to within 0.02; it is the average over many tables that obeys the formulas, and that is why a table is run at a load factor below 1: a chain of length 3 or 4 is normal and costs nothing.

Exercise 2 · Quadratic probing and the size of the table. Quadratic probing looks at the slots (h + i²) mod m for i = 0, 1, 2, …, where h is the home slot of the key. (a) For m = 12 and for m = 16, which slots does the probe sequence of a key with home slot 0 ever visit? What does that mean for the table when most slots are still free? (b) Let p be an odd prime. Prove that the first (p + 1)/2 probes (i = 0, 1, …, (p − 1)/2) visit (p + 1)/2 different slots. (Hint: if i² ≡ j² (mod p), then p divides (j − i)(j + i).) (c) Conclude: in a table of p slots with fewer than (p + 1)/2 slots occupied (a load factor below about ½), a new key is always stored within the first (p + 1)/2 probes. (d) The bound of (c) is sharp. For p = 13, find a set of 7 occupied slots such that a new key with home slot 0 can never be stored, although 6 slots are free.

Solution

(a) The probe sequence of a key with home slot 0 is i² mod m, and for m = 12 the squares are 0, 1, 4, 9, 16 → 4, 25 → 1, 36 → 0, 49 → 1, 64 → 4, 81 → 9, 100 → 4, 121 → 1, then the pattern repeats: the visited slots are {0, 1, 4, 9} and no others. For m = 16 the squares mod 16 are again {0, 1, 4, 9}. A key with home slot h only ever reaches h, h + 1, h + 4 and h + 9. So if those four slots are occupied the key cannot be inserted, although the table is mostly free: with a composite table size quadratic probing may fail long before the table is full. (13 is better: its squares reach seven slots, see (d).)

(b) Let 0 ≤ i < j ≤ (p − 1)/2 and suppose i² ≡ j² (mod p). Then p divides j² − i² = (j − i)(j + i). Here 1 ≤ j − i ≤ (p − 1)/2 < p and 1 ≤ j + i ≤ (p − 3)/2 + (p − 1)/2 = p − 2 < p, so p divides neither factor; but a prime that divides a product divides one of its factors, a contradiction. Hence the squares i² mod p for i = 0, …, (p − 1)/2 are pairwise different: those are (p + 1)/2 different slots. (Checked for every odd prime below 400.) ∎

(c) The first (p + 1)/2 probes of a key visit (p + 1)/2 different slots. If fewer than (p + 1)/2 slots are occupied (with tombstones counting as occupied for this purpose, because an insert may reuse a tombstone but a search may not stop at it), at least one of the probed slots is free, so the insert succeeds within (p + 1)/2 probes: quadratic probing on a prime-sized table is safe up to a load factor of about ½. (Verified for every set of (p − 1)/2 occupied slots for p = 3, 5, 7, 11, 13.) ∎

(d) For p = 13 the squares of 0, 1, …, 6 are 0, 1, 4, 9, 16 → 3, 25 → 12, 36 → 10: the seven slots {0, 1, 3, 4, 9, 10, 12}; and (13 − i)² = i² (mod 13), so i = 7, …, 12 repeat the same seven slots. Occupy these seven slots: a new key with home slot 0 probes only them, so it can never be stored, although the six slots 2, 5, 6, 7, 8 and 11 are free. The load factor is 7/13 = 0.54, just above the bound of (c). ∎

Exercise 3 · Rehashing costs O(1) per put on average. A chained map starts with m₀ buckets and, whenever a put makes the size exceed λ·m (λ is the maximum load), builds a table of at least twice as many buckets (the next prime above 2m) and re-inserts every entry; each re-insertion is a move. (a) Prove that n puts cause fewer than 2n + R moves, where R is the number of rehashes, and that R = O(log n). So the amortized cost of a put is O(1), as for the dynamic array of chapter 1. (b) Check (a) against the experiment of video 4: 1,000 puts, a start with 7 buckets, λ = 0.75, 7 rehashes and 984 moves. At which sizes did the rehashes happen? (c) Suppose the table grows by a fixed 100 buckets instead of doubling. Show that the number of moves for n puts is about n²/(2λ·100); evaluate it for n = 1,000 and λ = 0.75, and compare with 984. What happens to the number of moves when n doubles? (d) With λ = 0.5 instead of 0.75, does (a) still hold? What do you pay, and what do you get?

Solution

(a) Let the capacities be m₀ < m₁ < … < m_R with m_{r+1} ≥ 2m_r. The r-th rehash (r = 1, …, R) happens in a table of capacity m_{r−1} when the size reaches ⌊λ·m_{r−1}⌋ + 1, and moves that many entries. Hence the total number of moves is Σᵣ (⌊λ·m_{r−1}⌋ + 1) = Σᵣ ⌊λ·m_{r−1}⌋ + R. Because the capacities at least double, λ·m_{R−1−t} ≤ λ·m_{R−1}/2ᵗ, so Σᵣ ⌊λ·m_{r−1}⌋ ≤ λ·m_{R−1} · (1 + ½ + ¼ + …) < 2λ·m_{R−1}. The last rehash happened at size ⌊λ·m_{R−1}⌋ + 1 ≤ n, so λ·m_{R−1} < n. Altogether moves < 2n + R. And m_{R−1} ≥ 2^{R−1}·m₀ with λ·m_{R−1} < n gives R ≤ log₂(n/(λ·m₀)) + 1 = O(log n). So the amortized cost of a put is < 2 + R/n = O(1). (The bound is checked for every n below 3,000.) ∎

(b) The rehashes of video 4 happened when the sizes 6, 13, 28, 60, 123, 249 and 505 were reached (the table had 7, 17, 37, 79, 163, 331 and 673 buckets and grew to 17, 37, 79, 163, 331, 673 and 1,361), so R = 7 and the moves are 6 + 13 + 28 + 60 + 123 + 249 + 505 = 984 < 2 · 1,000 + 7. The last rehash moved 505 entries, about half of all moves, exactly as the geometric sum predicts.

(c) With a growth of c = 100 buckets the r-th rehash happens at about λ(m₀ + c(r − 1)) entries and moves that many, and R ≈ n/(λc) rehashes are needed, so the number of moves is about Σᵣ λcr ≈ λc·R²/2 = n²/(2λc). For n = 1,000, λ = 0.75, c = 100 the formula gives 6,667; the exact count (rehashes at 6, 81, 156, …, 981 entries, 14 of them: 14 · 6 + 75 · (0 + 1 + … + 13) = 84 + 6,825) is 6,909, seven times as many as the 984 of doubling, and for n = 2,000 it is 26,487: doubling n multiplies the cost by about 4. A fixed growth step makes a put cost Θ(n) on average, a growth factor keeps it Θ(1): the same lesson as for the dynamic array.

(d) Yes: (a) never used the value of λ, only that every table is at least twice as large as the one before, so moves < 2n + R still holds. With λ = 0.5 the same 1,000 puts need 8 rehashes and 1,338 moves (final capacity 2,729, load factor 0.37), against 7 rehashes and 984 moves for λ = 0.75 (final load 0.73). So you pay more moves, and about twice the memory, and in return get shorter chains (expected 1 + α/2 comparisons for a successful search, about 1.2 instead of 1.4) and, for open addressing, far fewer probes (video 3). A larger λ such as 0.9 gives 1,180 moves here (7 rehashes) but, for linear probing, long probe sequences (video 3's table: 51 probes for a miss at load 0.9).

Exercise 4 · A hash code for a composite key. The points (x, y) of a 100 × 100 grid (0 ≤ x, y < 100, so 10,000 points) are the keys of a map; equality compares x and y. The table has m = 10,007 buckets (a prime). (a) Four colleagues propose the hash codes h = x + y, h = x xor y, h = 31·x + y (this is what Objects.hash(x, y) computes, up to a constant: 31·(31 + x) + y) and h = 100·x + y. Predict which are good. Then run ex7_designs.grid_stats (or Ex7Designs.gridStats) in solutions/, which reports the number of distinct hash codes, the length of the longest bucket and the number of empty buckets, and explain every row. (b) State a recipe for hashing a key with several fields: which fields go in (and why the same ones as in equals), how to combine them, what to avoid. (c) Why is 100·x + y perfect on this grid but a poor design in general? What would you use for coordinates of unknown range?

Solution

(a) The results for 10,000 points in 10,007 buckets (test_hash_codes_of_a_100_by_100_grid_in_10007_buckets, also in Java):

x + y takes only the values 0 … 198, so the 10,000 points share 199 codes and the 100 points of the anti-diagonal x + y = 99 land in one bucket: one chain holds 100 entries. x xor y is worse still, 128 codes (it is below 128), and it is 0 for all 100 points with x = y. 31·x + y: (x, y) and (x + 1, y − 31) have the same code (31 · 3 + 40 = 31 · 4 + 9), because y ranges over 100 values but the multiplier is only 31; each code is shared by up to 4 points, only 3,169 codes exist, and 6,838 buckets stay empty, yet the longest chain is a modest 4. 100·x + y gives every point its own code (it is the position in the grid) and the prime table size keeps them apart: a perfect hash for this grid. Note that Objects.hash(x, y) is 31·(31 + x) + y = 31·x + y + 961, so a small grid behaves exactly like the third row.

(b) Recipe: (1) include exactly the fields that equals compares, no more (a field that equals ignores breaks the contract, Exercise 9) and no fewer (leaving one out is legal but collides every pair that differs only in it); (2) combine them in a way that depends on the position of each field, the polynomial rule h = 31·h + hash(field) for each field in turn (Objects.hash and Arrays.hashCode do exactly this): sums and xors are symmetric, so (x, y) and (y, x) collide, and they stay inside a small range; (3) use all 32 bits (int wrap-around is fine) and compress with a (floor) mod by a prime; (4) never hash a mutable field of a key that is stored in the table (video 1).

(c) 100·x + y works only because we know that y < 100: it is a perfect hash for this range, and (x, 100) would collide with (x + 1, 0). For a general design the range is unknown, so use a multiplier that is large and odd (such as 1,000,003, last row: all 10,000 codes differ and only a few pairs share a bucket) or a library hash; a mixing step on the result helps for patterns like grids, where neighbouring keys have neighbouring codes.

Exercise 5 · Deleting from an open-addressing table. Linear probing, m slots, int keys. (a) Show with the table of video 3 (13 slots, keys 18, 41, 22, 44, 59, 32, 31, 73 inserted in this order) why "delete = empty the slot" is wrong (delete 44, look for 32). Describe the tombstone scheme: what get, put and remove do with a tombstone, and when the table has to be rebuilt (do tombstones count toward the load factor?). (b) There is a second scheme for linear probing that leaves no tombstones. After emptying the slot i, scan the slots j = i + 1, i + 2, … (cyclically) up to the first empty slot. An entry at j whose home slot lies cyclically in (i, j] stays; any other entry is moved into the hole at i and the hole becomes j. State the invariant that makes this correct, prove that it is preserved, and apply the procedure to delete 44 from the table of video 3. (c) Compare the two schemes (cost of a delete, effect on later searches, memory, simplicity). Does (b) work for quadratic probing and double hashing?

Solution

(a) In the table [-, -, 41, -, -, 18, 44, 59, 32, 22, 31, 73, -] the key 32 has home slot 32 mod 13 = 6 but sits in slot 8, because 44 was in slot 6 when it was inserted. Emptying slot 6 to delete 44 makes get(32) stop at the empty slot 6 (probes [6]) and answer "missing" although 32 is in slot 8; with a tombstone it probes [6, 7, 8] and finds it (video 3, and test_remove_leaves_a_tombstone_and_get_skips_it). Tombstone scheme: remove turns the slot into DELETED; get and remove treat DELETED as "occupied by something else" (skip it, never match it) and stop only at an EMPTY slot or after m probes; put of a new key probes until an EMPTY slot (to be sure the key is not further along) and stores the entry in the first tombstone met, otherwise in the empty slot; put of an existing key updates it. Because searches stop only at EMPTY slots, tombstones count toward the load: the rebuild condition is (entries + tombstones) > λ·m, and the rebuild (a rehash into a fresh table of the same or a larger size) drops all tombstones. Without it a table that has seen many removals ends up with no empty slot, and every unsuccessful search walks the whole table (Exercise 10).

(b) Invariant I: for every stored key k at slot s, all slots from home(k) to s (cyclically) are occupied. Search is correct exactly when I holds: a search from home(k) walks along occupied slots to k. Deleting key x at slot i: empty slot i; this can break I only for entries whose path from home to their slot crosses i, and those lie after i in the same run of occupied slots (before the first empty slot e). Scan j = i + 1, … until the first empty slot. For the entry at j with home h: if h lies in (i, j] (cyclically), its path starts after i, so it does not cross the hole: leave it. Otherwise the path from h to j contains i (h is at or before i): move the entry to i; its new path h → i is a prefix of the old path and all of its slots are occupied (i is now filled), so I holds for it; the hole is now at j, and the entries after j are examined against the new hole. When the scan reaches an empty slot, no entry beyond it has a path that crosses the holes (their paths cannot cross an empty slot by I), so I holds everywhere. ∎ Example: delete 44 (slot 6): j = 7 holds 59 with home 7 ∈ (6, 7]: stay; j = 8 holds 32 with home 6 ∉ (6, 8]: move to slot 6, the hole is 8; j = 9 holds 22 with home 9 ∈ (8, 9]: stay; j = 10 holds 31 with home 5 ∉ (8, 10]: move to slot 8, the hole is 10; j = 11 holds 73 with home 8 ∉ (10, 11]: move to slot 10, the hole is 11; j = 12 is empty: stop and empty the hole 11. Result [-, -, 41, -, -, 18, 32, 59, 31, 22, 73, -, -]: no tombstone, and 32, 31, 73 are found after 1, 4 and 3 probes (test_the_worked_example; with a wrap-around across the end of the array in test_wrap_around_case; random operations in both languages check that I holds after every operation and that the table equals a built-in map).

(c) A delete with a tombstone costs a search (O(1) expected); backward shift costs a search plus a scan of the rest of the run (the cluster after the slot: O(1) expected at a moderate load, but it grows with the clustering of linear probing). Tombstones make later searches longer until the next rebuild and cost memory for the counters and the rebuild logic; backward shift keeps the table exactly as if the key had never been inserted, so later searches are never slowed down and no rebuild is needed, at the price of a trickier delete. Backward shift needs one cheap test per entry — "is the hole on the path from the entry's home to its slot?" — which is the interval test of linear probing; for quadratic probing and double hashing the path of an entry is a different sequence for every key, entries that depended on the hole may be anywhere in the table (not in the run that follows), and there is no simple test: those schemes use tombstones. (Chaining needs neither: a delete is a list removal.)

Exercise 9 — Reading in read/py/ex7_read.py / Ex7Read.Reading in read/java/Ex7Read.java. The comment claims that two readings with the same temperature are equal and are the same key of a dictionary (a HashMap).

Solution

The bug. __eq__ / equals compares only the temperature, but the hash code is computed from the number and the temperature. So two readings that are equal have different hash codes: Reading(1, 20) == Reading(2, 20) is true, but hash(Reading(1, 20)) != hash(Reading(2, 20)) (Java: 1,012 and 1,043 for Objects.hash(1, 20) and Objects.hash(2, 20)). A hash table finds the bucket from the hash code, and compares the stored hash code before it calls equals, so the second reading is never even compared with the first: Reading(2, 20) in {Reading(1, 20): "a"} is False, put stores a second entry, and len(table) is 2 for two keys that are equal. The claim "the same temperature means the same key" is false; the table holds duplicates (test_equal_readings_are_not_the_same_key, also in Java with a HashMap and a HashSet). Why the quick tests miss it. Every test the AI wrote probably used the same object, or two readings with the same number (Reading(1, 20) twice), whose hash codes agree; the difference only shows for readings with different numbers and the same temperature. Compare an equal-but-different object with the one you stored: that is the test for the equals/hashCode contract. The fix. Hash exactly the fields that equality compares: hash(self.temperature) (Java: Integer.hashCode(temperature), or Objects.hash(temperature)). Then equal readings have equal hash codes (the contract of video 1: equal keys, equal hash codes) and the dictionary has one entry (test_the_repair). What happens if the hash is missing. In Python a class that defines __eq__ but no __hash__ becomes unhashable and raises TypeError the moment it is used as a key, which protects you (video 1). In Java a class that overrides equals but not hashCode silently inherits the identity hash code of Object: two equal objects have different hash codes and map.get(equalKey) returns null, with no error (equalsWithoutHashCodeUsesTheIdentityHashCode). Override both, with the same fields.

Exercise 10 — Probe10 in read/py/ex7_read.py / Ex7Read.Probe10 in read/java/Ex7Read.java. The comment claims that put, get and remove always terminate and take O(1) on average. (When you run it on a bad input it will not come back: interrupt it, or run it with a step limit.)

Solution

The bug. The probe loop while slot is not EMPTY and slot != key: i = next(i) only stops at an EMPTY slot or at the key, and the class never makes a slot EMPTY again and never reuses a tombstone, so it ends up in a state without any empty slot, and then every search for a key that is not there runs forever. Two inputs show it: (1) put the 13 keys 0 … 12 into the 13 slots and call get(99) (or put(99, …)): all slots are used and none holds 99, the loop never ends (an existing key such as 5 is still found, which makes the failure look random); (2) worse, with no entries at all: put a key and remove it, 13 times (put(5), remove(5), put(5), …): a remove leaves a tombstone, the next put skips the tombstone (it is not an EMPTY slot) and takes the next free slot, so each cycle uses up one more slot, and after 13 cycles all 13 slots are tombstones, size is 0 and get(7) hangs (test_tombstones_are_never_reused_so_an_empty_map_hangs; the tests use a subclass with a step limit so that the endless loop becomes a failing assertion). Why the quick tests miss it. A table with a few entries and a removal or two always has empty slots; the bug needs the table to run out of them, by being full or by tombstones piling up over time (a long-running server, not a unit test). The claim "always terminate" is a claim about the corner of the table, so test the full table and the table full of tombstones. The fix. (1) Bound the loop: at most capacity probes per operation, so a search in a table without empty slots ends with "not found". (2) Remember the first tombstone on the way and reuse it for a new key (the loop still goes on to an empty slot to be sure that the key is not further along). (3) Count the tombstones and rebuild the table (a rehash into a fresh array) when entries + tombstones exceed the maximum load, or use the backward-shift delete of Exercise 5(b), which needs no tombstones at all. Without (3) the bounded loop would end, but lookups would still degrade to O(m) as tombstones pile up. The class Fixed in test_ex7_read.pyEx7ReadTest.java does (1) and (2) and survives both inputs and 5,000 random operations (test_the_repair_survives_the_hanging_inputs).

§4Working with AI

When an AI writes a hash table or a key class it usually also claims that it works and how fast it is. Treat both as hypotheses:

  1. Test equal-but-different keys. Put one key in, look it up with an equal object that is not the same object (a second Reading(2, 20) for Reading(1, 20), a new string built at run time). The hash that includes a field equals ignores fails exactly there (Exercise 9) and passes every test that reuses the same object.
  2. Test the corners of the table, not only the middle. A full table, and a table full of tombstones: every operation must terminate. A map that "always terminates" but hangs on a full table (Exercise 10) is typical; run suspicious loops with a step limit.
  3. Compare with the built-in map on random operations, including removals. Random put, get and remove against a dict or a HashMap, with keys from a small range so that collisions and removals are frequent; check the size after every operation.
  4. Test negative hash codes. In Java h % m can be negative; ask for Math.floorMod and test a string whose hash code is negative ("polygenelubricants", or any long word). In Python test int keys of both signs.
  5. Count probes and comparisons, do not just time. A claim of "O(1)" can be tested with the doubling test of chapter 1 on probes: the average probes per search must stay flat as n grows with the load factor fixed (and the load factor must stay below the threshold after every put).
  6. Ask what happens when the table fills and when keys are deleted. Does it resize? Does it count tombstones toward the load? Does the new index come from the new size (Exercise 7)? An AI that "grows" a table by copying the old array is repeating the misconception of video 4.
  7. Distrust claims about the standard libraries. "Python's dict uses chaining" (it uses open addressing), "HashMap iterates in insertion order" (it does not; LinkedHashMap does), "string hashes are the same in every run" (not in Python): print the real behaviour.
PITFALL · "It finds the key I just put" is not a test of the contract.

The same object always has the same hash code. Only an equal-but-different key, a removal followed by a lookup, and a nearly full table test the parts of the map that fail.
