Trees and Binary Search TreesData Structures · Chapter 5

Folders, family trees and web pages are all trees. This chapter shows how to walk every item of a tree exactly once, how one extra rule turns a binary tree into a search structure whose search, insert and delete follow a single path, and why that path can still be as long as the whole tree when the keys arrive in the wrong order. That last problem is the reason for chapter 6.

Why this matters

about 90–120 minutes (4 videos of 7–9 minutes plus the exercises).

Trees are how hierarchical data is stored

File systems, expression parsers, web pages and the call tree of a recursive function are all trees, and almost every algorithm on them has the same shape: do something with the root and let recursion handle the subtrees.

One rule makes a tree searchable

If every key in the left subtree is smaller and every key in the right subtree larger, each comparison discards a whole subtree, so search, insert and delete cost time proportional to the height h.

Height is not guaranteed

The same keys give a tree of height about log₂ n or of height n − 1, depending on the insertion order; knowing why is the first step towards the balanced trees of chapter 6.

§1The vocabulary

The node at the top is the root; every other node has exactly one parent, the node directly above it. A node can have children; a node with no children is a leaf. The depth of a node is the number of steps down from the root (the root has depth 0), and the height of the tree is its largest depth. We count height in edges: a single node has height 0 and, by convention, the empty tree has height −1. In a binary tree every node has at most two children, called left and right, and any node together with everything below it is a subtree. Our example has seven nodes: root 50, children 30 and 70, and leaves 20, 40, 60, 80. Its size is 7, its height is 2 and its leaves are 20 40 60 80.

PITFALL · Height in edges or in nodes?

Some books count the nodes on the longest path instead, so their heights are one larger. This course counts edges (a leaf has height 0, the empty tree −1); check which convention your textbook or exam uses before you compare numbers.

§2A tree is a root and two smaller trees

A binary tree is either empty, or a root together with a left subtree and a right subtree, each of which is a binary tree again. That is the shape of chapter 4's recursion: a big problem handed to smaller copies of itself.

Python has no built-in tree type: a node is a small object with three attributes, key, left and right, and None means "empty subtree" (code/py/tree.py).

Java has no general-purpose tree class either: a node is a small generic class TreeNode<K> with key, left and right, and null means "empty subtree" (code/java/TreeNode.java).

§3Four ways to walk a tree

  • Preorder: the root first, then the left subtree, then the right subtree: 50 30 20 40 70 60 80.
  • Inorder: left subtree, then the root, then the right subtree: 20 30 40 50 60 70 80 (the keys come out sorted, which video 2 explains).
  • Postorder: both subtrees first, the root last: 20 40 30 60 80 70 50.
  • Level order: the root, then everything at depth 1, then depth 2, …: 50 30 70 20 40 60 80.

§4Does the order matter?

Take the arithmetic expression (3 + 4) × (5 − 2) as a tree: every operator is a node and the numbers are leaves. Three walks of the same tree give three different sequences:

walksequencemeaning
postorder3 4 + 5 2 - *every operator comes right after its two operands: no parentheses needed; a stack evaluates it to 21
inorder3 + 4 * 5 - 2the parentheses are gone: read normally it means something else
preorder* + 3 4 - 5 2the operator comes before its operands
PREDICT

Evaluate 3 4 + 5 2 - * with a stack: what are the stack contents before the final *?

Show the answer

Push 3 and 4; + replaces them by 7. Push 5 and 2; - replaces them by 3. The stack holds 7 and 3, and * turns them into 21.

§5Walks without recursion

The recursive walks use the call stack: every recursive call remembers where to continue. We can take it away and keep our own stack: for preorder, push the root; then repeat "pop a node, visit it, push its right child and then its left child" (the left child is popped first). For inorder, go left as far as you can, pushing every node on the way, then pop one, visit it and move to its right child. Level order uses a queue instead: visit a node and add its children at the back, so the node that has waited longest is next. A stack goes deep, a queue goes wide. Every node is visited exactly once, so a walk takes time O(n) for n nodes, and an iterative walk cannot run out of recursion depth.

Use collections.deque as the queue (popleft is O(1), while list.pop(0) is O(n)). A recursive height of a chain of 500 nodes works (it returns 499); a chain of 2000 raises RecursionError (code/py/degenerate_demo_output.txt).

Use ArrayDeque for both the stack and the queue (the class java.util.Stack is a legacy class). A recursive height of a chain of 500 nodes works (499); on a chain of a million nodes the same code throws StackOverflowError, while the iterative version still works (code/java/DegenerateDemo_output.txt).

NOTE · Three common mistakes.

Forgetting the empty-tree check (None / null) before reading node.left; mixing up height in edges and in nodes; trusting a recursive walk on a very deep tree.

IN THIS CHAPTER§1 The rule: all the keys in the subtree§2 Search§3 Insert§4 What it costs

§1The rule: all the keys in the subtree

For every node, all keys in its left subtree are smaller than its key and all keys in its right subtree are larger. In the example (root 50) everything on the left is smaller (30, 20, 40), everything on the right larger (70, 60, 80), and the same rule holds again at 30 and at 70. The inorder walk of a BST visits the keys in sorted order: 20 30 40 50 60 70 80. The rule and the sorted walk are two views of one property.

PITFALL · It is not enough to compare a node with its two children.

Take root 50 with left child 30 and right child 70, and put 60 as the right child of 30. Every node is larger than its left child and smaller than its right child, yet 60 sits in the left subtree of 50 and is larger than 50, so the tree is broken (the inorder walk is 30 60 50 70, not sorted). A correct check carries an interval of allowed keys down the tree, or tests that the inorder walk is strictly increasing (Exercises 1 and 6).

§2Search

To look for 60 start at the root: 60 > 50, so 60 can only be in the right subtree and the whole left half is ruled out in one comparison. Move to 70: 60 < 70, go left. We arrive at 60 after three comparisons (the path is 50, 70, 60). Look for 45, which is not there: 50 → go left; 30: 45 is larger, go right; 40: larger again, go right; the right child of 40 is empty. Reaching an empty spot means the key is not in the tree, and the empty spot is exactly where 45 would have to be (path 50, 30, 40).

PREDICT

Show the answer

It visits 50, 30, 40 (three comparisons), ends at the empty right child of 40, so 45 becomes the right child of 40. After the insertion the height grows from 2 to 3, and the inorder walk is 20 30 40 45 50 60 70 80 (code/py/bst_demo_output.txt).

§3Insert

Insertion is the same walk: search for the key, and the empty spot where the search falls off the tree is where the new node goes, as a new leaf. Nothing else moves and no other node is touched, and the rule still holds. If the key is already in the tree we stop and do nothing (a search tree stores each key once).

The loop version of insert in code/py/bst.py counts one comparison per visited node in comparisons; the recursive version is shorter but easy to get wrong (forgetting to return the new child loses the new node).

The loop version of insert in code/java/BST.java counts one comparison per visited node in comparisons; the key type is K extends Comparable<K> and a key whose compareTo disagrees with equals makes the tree and a hash set disagree about which keys are the same.

§4What it costs

Every step goes one level down and does a constant amount of work, so search and insert make at most h + 1 comparisons: time O(h). For the example h is 2, then 3 after inserting 45. If a tree with n keys is balanced, its height is about log₂ n and we are as fast as binary search; but nothing so far guarantees that, which is the question of video 4.

BST delete

Insertion always adds a leaf, but deleting a key from the middle of the tree must keep the ordering rule. There are three cases by the number of children: a leaf is cut off, a node with one child is replaced by that child, and a node with two children takes the key of its in-order successor, the smallest key of its right subtree, whose node is then removed. All three cost O(h).

IN THIS CHAPTER§1 Case 1: a leaf§2 Case 2: one child§3 Case 3: two children§4 The cost, and what goes wrong in code

§1Case 1: a leaf

Take 20 in the tree built from 50 30 70 20 40 60 80 45 65 (inorder 20 30 40 45 50 60 65 70 80). It has no children, so we just cut it off: the left child of 30 becomes empty. The rule still holds because we removed a key and moved nothing. The inorder walk is now 30 40 45 50 60 65 70 80.

§2Case 2: one child

Take 40; its only child is 45. We let 45 take its place: the parent of 40 points to 45 directly and 40 drops out. The rule still holds, since 45 was in the right subtree of 30, so it is larger than 30 and smaller than 50; a whole subtree moves up one level with its inner order unchanged. The inorder walk is 30 45 50 60 65 70 80.

§3Case 3: two children

Take the root, 50: its left subtree holds 30 and 45, its right subtree 70, 60, 65 and 80. We cannot hang both subtrees from the parent, since a node in the middle has only one free slot and the root has no parent. Instead we do not remove the node: we replace its key by another key and remove that other node. The replacement must be larger than everything on the left and smaller than everything else on the right: the in-order successor, the smallest key of the right subtree (the next key in the sorted order). To find it, go right once and then left as far as you can: here that is 60. Copy 60 into the root, then remove the old 60 from the right subtree; the successor never has a left child, so that is a case 1 or 2 (here 65 takes its place). The root is now 60 and the inorder walk is 30 45 60 65 70 80, still sorted.

Deleting from a binary search tree: three cases

Click any node of the tree: the demo names the case (leaf, one child, two children) and animates it: a leaf fades, a one-child node is bypassed, and for two children the in-order successor is highlighted, its key is copied up and the old node is removed. The inorder output row stays sorted after every step.

PREDICT

Show the answer

The in-order successor of 50 is 60 (go right to 70, then left to 60), so 60 becomes the root and 65, its only child, takes the old 60's place under 70. The inorder walk is 20 30 40 45 60 65 70 80. (The video deletes 20, then 40, then 50, so its final walk is 30 45 60 65 70 80: code/py/bst_demo_output.txt.)

PITFALL · Deleting a node means re-attaching its subtrees to its parent.

With two children there is one free slot and two subtrees; that is why the key is copied from the successor instead.

§4The cost, and what goes wrong in code

First the search for the key (one path of length at most h), then in case 3 a continuation of the same path down to the successor, then one or two link changes: the total never goes deeper than the height, O(h), like search and insert. Two classic bugs: ignoring the subtree returned by the recursive call (the change is lost; Exercise 9), and removing the successor by the old key instead of by the successor's key (you delete the wrong node).

The recursive _delete in code/py/bst.py makes one call per level, so on a chain of 2000 nodes it raises RecursionError; the loop versions of search and insert do not. Python's standard library has no tree: a sorted list supports del, but moving the later items costs O(n).

The recursive delete in code/java/BST.java makes one call per level, so a chain of a million nodes throws StackOverflowError. TreeMap.remove implements exactly these three cases plus the rebalancing of chapter 6.

§1Sorted insertion builds a chain

Insert 10 into an empty tree, then 20: it is larger, so it goes to the right of 10. Then 30 goes to the right of 20, and so on: every new key is larger than everything in the tree, so it always goes to the far right and the left subtrees stay empty. The tree is a chain: every node has one child and, with n keys, the height is n − 1. It is still a perfectly valid search tree; it just is not a fast one.

PITFALL · "A BST searches in O(log n)."

It searches in O(h), and h can be anywhere from about log₂ n to n − 1. Always test a tree implementation with sorted input as well as random input, and look at the height.

PREDICT

Show the answer

Height 999 and 1000 comparisons: the tree is a chain and the search visits every node. Binary search on a sorted array of 1,000 keys needs about log₂ 1000 ≈ 10.

§3Random order keeps the tree short, on average

If the keys arrive in random order, the first key is probably neither very small nor very large, so the tree splits roughly in two, and the same happens at every level below. For the shuffled 1,000 keys the height is 22 (a perfect tree would have height 9) and the average depth of a node is 11.02. Probability theory says that for random insertion order the average depth of a node is about 2 ln n minus a small constant (about 2 ln n − 2.85), which is 10.99 for n = 1,000 and 15.58 for n = 10,000. The height is larger than the average depth, because the tallest path is longer than the typical one, but it still grows in proportion to log n.

NOTE · Average depth is not height.

The numbers "2 ln n" belong to the average depth of a node. The expected height of a random BST is larger (roughly 4.3 ln n), and a given insertion order can be much worse than average.

§4Why we cannot just rely on random order

Timestamps, order numbers and identifiers arrive in increasing order; a list that was sorted once and then loaded into a tree is sorted; nearly sorted data is nearly as bad as sorted data. Shuffling first works only when all the keys are known in advance, and many programs add and remove keys all the time. What we want is a tree that keeps itself short whatever the order of the keys: after every insertion and deletion it repairs its shape with a few local changes called rotations. AVL trees, (2,4) trees and red-black trees do this and guarantee a height of order log n, so search, insert and delete always take O(log n). That is chapter 6.

Python's standard library has no balanced tree: use a dictionary when you do not need order, a sorted list with bisect for small data, or a third-party package such as sortedcontainers.

This is exactly why TreeMap and TreeSet are balanced (they are red-black trees): they guarantee O(log n) whatever the order of the keys. Insert a million sorted keys into a TreeMap and it stays fast; do the same with the plain BST above and it becomes a million-node list.

PROOFS

Exercise 1 · Insertion keeps the order. A binary search tree (BST) with distinct keys is a binary tree in which, for every node, all keys in its left subtree are smaller than its key and all keys in its right subtree are larger. Let T be a BST and k a key that is not in T. Insertion walks down from the root: at node x go left if k < x.key and right otherwise; when the child you want is empty, attach a new leaf with key k there. (a) Give a loop invariant about k and the subtree rooted at the current node x. (Hint: every node's subtree has an allowed open interval of keys, (lo, hi); the root's is (−∞, +∞).) Prove initialization and maintenance. (b) Use (a) to prove that the tree is still a BST after the insertion. Where do you use that k is not already in T? (c) A programmer tests "is this a BST?" by comparing every node only with its two children. Give a tree with four nodes that passes this test but is not a BST, and say which check (a) suggests instead.

Solution

(a) For a node x of T let lo(x) be the largest key among the ancestors a of x with x in a's right subtree (−∞ if there is none) and hi(x) the smallest key among the ancestors with x in their left subtree (+∞ if none). Invariant, true every time the loop looks at a node x:

lo(x) < k < hi(x)

Because lo(x) is the largest and hi(x) the smallest of the relevant ancestor keys, the invariant says exactly that k is on the correct side of every ancestor of x. Initialization: x = root has no ancestors, lo = −∞, hi = +∞. ✓ Maintenance: assume lo(x) < k < hi(x). Since k is not in T, k ≠ x.key. If k < x.key we move to the left child y: lo(y) = lo(x) and hi(y) = x.key (x is the nearest ancestor with y in its left subtree, and it is smaller than the old hi(x) by the BST property), so lo(y) < k < x.key = hi(y). If k > x.key we move right: lo(y) = x.key and hi(y) = hi(x), so x.key < k < hi(y). ✓ The walk ends because the tree is finite; it stops at an empty child, where the new leaf N is attached, and lo(N) < k < hi(N) still holds.

(b) After the insertion only the ancestors of N have a subtree that changed (it gained k). For an ancestor a, N is in a's left subtree iff the walk went left at a, which happened because k < a.key; it is in the right subtree iff k > a.key (here we use that k is not in T: if k were equal to a key on the path, the walk would send it right while the tree needs a strict inequality, so a duplicate would break the property). Every other node keeps the same subtrees. N itself has two empty subtrees, so its condition holds vacuously. Hence the tree is a BST. ∎

(c) Root 50, left child 30, right child 70, and 60 as the right child of 30. Every node is larger than its left child and smaller than its right child, so the children-only test passes, but 60 lies in the left subtree of 50 and is larger than 50. The correct check carries the interval of (a) downwards: the root must lie in (−∞, +∞); a node with key v in (lo, hi) passes (lo, v) to its left child and (v, hi) to its right child. Equivalently: the inorder walk must be strictly increasing (Exercise 6).

Exercise 2 · Height versus size. Count the height in edges (a single node has height 0, the empty tree −1). (a) Prove by induction on d that a binary tree has at most 2ᵈ nodes at depth d. (b) Conclude that a binary tree of height h has at most 2^(h+1) − 1 nodes, so a tree with n nodes has height h ≥ log₂(n + 1) − 1. Compute the smallest possible height for n = 1,000 and n = 10,000 (compare with the "perfect height" column of video 4). (c) Prove that h ≤ n − 1 for every binary tree with n nodes, and describe the trees with equality. (d) Conclude: in every BST with n keys some key needs at least ⌈log₂(n + 1)⌉ comparisons to be found (count one comparison per visited node), and no key needs more than n.

Solution

(a) Depth 0 holds 1 = 2⁰ node (the root). If depth d holds at most 2ᵈ nodes, every one has at most two children, so depth d + 1 holds at most 2·2ᵈ = 2^(d+1). ∎

(b) n ≤ Σ_{d=0}^{h} 2ᵈ = 2^(h+1) − 1 (the geometric sum of chapter 1, Exercise 2(a)). So 2^(h+1) ≥ n + 1, i.e. h + 1 ≥ log₂(n + 1), and since h is an integer h ≥ ⌈log₂(n + 1)⌉ − 1. For n = 1,000: log₂ 1001 ≈ 9.97, so h ≥ 10 − 1 = 9. For n = 10,000: log₂ 10001 ≈ 13.29, so h ≥ 14 − 1 = 13. These are the "perfect height" numbers 9 and 13 of video 4.

(c) A node at depth h has one ancestor at every smaller depth, so every depth 0, 1, …, h contains at least one node and n ≥ h + 1. Equality holds when every level has exactly one node, i.e. every node has at most one child: a chain (which may zigzag between left and right children).

(d) Finding a key at depth d visits d + 1 nodes, i.e. makes d + 1 comparisons. The key at the deepest level, depth h, needs h + 1 ≥ ⌈log₂(n + 1)⌉ comparisons by (b), so no BST, however clever, has every key within fewer. By (c) h + 1 ≤ n, so no key needs more than n. Video 4 shows both ends: the chain (n) and a good tree (about log₂ n).

Exercise 3 · Counting trees. Let Cₙ be the number of different binary tree shapes with n nodes. (a) Show that C₀ = 1 and Cₙ = Σᵢ₌₀ⁿ⁻¹ Cᵢ·Cₙ₋₁₋ᵢ. Compute C₁, …, C₅. (b) Explain why the number of different BSTs that hold the keys {1, …, n} is also Cₙ. (c) For n = 3 list all the BSTs on {1, 2, 3} and, for each, the insertion orders (among the 6 permutations) that build it. If the six orders are equally likely, which tree is the most likely and with what probability? What does this say about "random insertion order" and balance? (d) Show that the inorder walk does not determine a BST (give two BSTs on {1, 2} with the same inorder walk), but the preorder walk does: prove by strong induction on n that two BSTs with the same preorder sequence are equal.

Solution

(a) The empty tree is the only shape with 0 nodes: C₀ = 1. A shape with n ≥ 1 nodes is a root, a left subtree with i nodes and a right subtree with n − 1 − i nodes (0 ≤ i ≤ n − 1), and the two subtrees can be chosen independently: Cₙ = Σᵢ Cᵢ·Cₙ₋₁₋ᵢ. Then C₁ = 1, C₂ = C₀C₁ + C₁C₀ = 2, C₃ = 2 + 1 + 2 = 5, C₄ = 5 + 2 + 2 + 5 = 14, C₅ = 14 + 5 + 4 + 5 + 14 = 42. (These are the Catalan numbers.)

(b) Let Bₙ be the number of BSTs on {1, …, n}. B₀ = 1. Choose the root key r; the keys 1, …, r − 1 must all go into the left subtree, which can be any BST on those keys, and r + 1, …, n into the right subtree. So Bₙ = Σᵣ B_{r−1}·B_{n−r}, the same recurrence with the same start as Cₙ; hence Bₙ = Cₙ.

(c) The five BSTs and the orders that build them:

treeinsertion orders
1 → 2 → 3 (right chain)1 2 3
1, right child 3, whose left child is 21 3 2
root 2 with children 1 and 3 (balanced)2 1 3 and 2 3 1
3, left child 1, whose right child is 23 1 2
3 → 2 → 1 (left chain)3 2 1

The balanced tree is built by two of the six orders, so it has probability 2/6 = 1/3; every other tree has probability 1/6. Random insertion order does not give a uniformly random shape: balanced shapes are favoured (twice as likely as any particular chain for n = 3, and more strongly for larger n), which is why random insertion keeps trees short on average (video 4).

(d) Two BSTs on {1, 2}: root 1 with right child 2, and root 2 with left child 1. Both have the inorder walk 1, 2. In any BST the inorder walk is the sorted list of the keys, so it carries no information about the shape. Claim: two BSTs with the same preorder sequence p₁, …, pₙ (distinct keys) are equal. Strong induction on n. n = 0: both empty. n ≥ 1: preorder visits the root first, so both roots are p₁. Preorder then visits the whole left subtree and afterwards the whole right subtree; in a BST the left subtree holds exactly the keys smaller than p₁ and the right subtree exactly the larger ones, so the sequence is p₁, (all keys < p₁), (all keys > p₁). The cut point (the first key larger than p₁) depends only on the sequence, so both trees have left subtrees with the same preorder sequence, and right subtrees with the same one, each with fewer than n nodes. By the induction hypothesis the left subtrees are equal and the right subtrees are equal. ∎ (This is why inserting the keys of a BST in its preorder order rebuilds the same tree.)

Exercise 5 · Order statistics. An order-statistic tree is a BST in which every node also stores size, the number of keys in its subtree (itself included). (a) State the invariant that size must satisfy. (b) Design select(k) (the k-th smallest key, k = 1 is the minimum) and rank(key) (the number of keys smaller than key). Give the algorithms, their cost, and check them on the tree of video 2 (keys 50, 30, 70, 20, 40, 60, 80): what are select(4) and rank(60)? (c) What must insert and delete do to keep the invariant, and what does it cost? (d) How do the costs behave if the keys are inserted in sorted order into a plain BST, and what would fix that?

Solution

(a) size(empty) = 0 and size(x) = 1 + size(x.left) + size(x.right) for every node x.

(b) select(k), 1 ≤ k ≤ size(root):

x = rootloop:    r = size(x.left) + 1            # x is the r-th smallest key of its subtree    if k == r: return x.key    if k < r:  x = x.left    else:      k = k - r; x = x.right

The keys of the left subtree are the size(x.left) smallest keys of x's subtree, x is the next one, and the rest are in the right subtree; so the k-th key is in the left subtree if k < r, is x if k = r, and is the (k − r)-th key of the right subtree otherwise. rank(key), the number of keys smaller than key:

x = root; count = 0while x is not empty:    if key <= x.key: x = x.left                          # x and its right subtree are not smaller    else: count = count + size(x.left) + 1; x = x.right  # x and its left subtree are smallerreturn count

Both follow one path from the root: O(h). On the tree of video 2 the left subtree of 50 has 3 keys (20, 30, 40), so r = 4 and select(4) = 50. rank(60): at 50, 60 > 50, count = 3 + 1 = 4, go right; at 70, 60 ≤ 70, go left; at 60, 60 ≤ 60, go left: empty; result 4 (the keys 20, 30, 40, 50).

(c) insert: first search; if the key is already there do nothing; otherwise, on the walk down to the new leaf add 1 to the size of every node on the path (each gains one key); the new leaf has size 1. delete: when a node is removed, subtract 1 from the size of every node on the walk from the root to the node that is physically removed (in the two-children case that walk continues down to the in-order successor). Both are one extra constant-time step per node of a path the operation walks anyway: still O(h). (Chapter 6's rotations will recompute the size of the two nodes they move from their children.)

(d) Sorted insertion into a plain BST gives a chain, h = n − 1, so select, rank, insert and delete are all O(n). Keeping the tree balanced (AVL, red-black) keeps h = O(log n), and all four become O(log n); this is how real order-statistic trees are built.

Exercise 6 · Walks without recursion — ex_walks.pyExWalks.java. Write an inorder iterator with an explicit stack, then height level by level, then is_bst on top of your iterator. The tests check the output, that the stack never holds more than height + 1 nodes, that a chain of 50,000 (Java: 200,000) nodes does not run out of stack, and that the tree from Exercise 1(c) is rejected.

Solution

Reference code: solutions/py/ex_walks.py, solutions/java/ExWalks.java. The iterator keeps a stack holding the nodes whose left subtrees are being explored: the constructor pushes the left spine; next() pops the top (the smallest key not yet returned), then pushes the left spine of its right child, which is exactly the next part of the walk. Every node is pushed and popped once, so the whole walk takes O(n) and each next() O(1) amortized. Why the stack never holds more than h + 1 nodes: at every moment the stack contains only ancestors of the next node to be returned (together with that node), and those lie on one root-to-node path, which has at most h + 1 nodes. height goes level by level (a list of the nodes at the current depth), which needs no recursion and counts edges (start at −1). is_bst is the observation of video 2: the inorder walk of a BST is strictly increasing, and a tree whose inorder walk is strictly increasing is a BST. The tree of Exercise 1(c) has the inorder walk 30, 60, 50, 70 and is rejected; a node compared only with its parent would have accepted it.

Exercise 7 · Counting comparisons — ex_bst.pyExBst.java. Implement insert, contains, path and height of a BST that counts one comparison per visited node. The tests check the counts against the walks of the video and the total cost n(n − 1)/2 of inserting 1, 2, …, n in order.

Solution

Reference code: solutions/py/ex_bst.py, solutions/java/ExBst.java. insert and contains follow the same path from the root, adding 1 to comparisons for every visited node; the first insert into an empty tree visits nothing, and a duplicate is detected at the visited node, so it costs the same as the successful search. path records the visited keys, so len(path(k)) equals the comparisons of one contains(k). The total for sorted insertion: the k-th insertion (k ≥ 2) visits all k − 1 existing nodes (every key is larger than everything in the tree, so the walk goes right all the way down the chain), so inserting 1, …, n costs 1 + 2 + … + (n − 1) = n(n − 1)/2 comparisons, the pair count of chapter 1; for n = 1,000 that is 499,500. The tree is a chain of height n − 1, and finding n afterwards costs n comparisons.

Exercise 8 · Delete — ex_delete.pyExDelete.java. Implement delete in the three cases (leaf, one child, two children through the in-order successor) and, as a final milestone, without recursion. The tests check that the tree stays a BST on random sequences, that the root is re-pointed correctly, and that 60 becomes the new root when 50 is deleted from the tree of video 3.

Solution

Reference code: solutions/py/ex_delete.py, solutions/java/ExDelete.java. A loop walks down remembering the parent (None / null for the root). If the node was not found, return False. In the two-children case, find the successor by going right once and then left as far as possible (remembering its parent), copy its key into the node, and continue with the successor as the node to remove; it has no left child (otherwise we could go further left), so it has at most one child. Now both remaining cases are one: the node has at most one child; re-point parent.left, parent.right or the root (when parent is None) to that child, which may be empty. Subtract 1 from size. Special cases the tests probe: the root with one child (the root pointer changes), the successor being the right child itself (then it is parent.right, not parent.left, that must be re-pointed), and the chain (the loop version needs O(1) memory; a recursive version needs one frame per level). The cost is one path, O(h).

Exercise 9 — delete in read/py/ex_read.py / ExRead.delete in read/java/ExRead.java. The comment claims it is correct and O(h).

Solution

The bug. In the branches key < node.key and key > node.key the result of the recursive call is thrown away: delete(node.left, key) instead of node.left = delete(node.left, key). The function returns node unchanged, so a node that the recursive call "removed" by returning None or its only child is never unlinked from its parent. What it does. (1) A leaf or one-child node below the root is not removed at all: from the tree 50 / (30 / (20, 40), 70 / (60, 80)), deleting 20 returns the same tree. The smallest failing input has two nodes: root 1 with the right child 2; delete(root, 2) leaves 2 in the tree. (2) The two-children case copies the successor's key into the node and calls node.right = delete(node.right, successor.key), which does store the result of that call; so the case "works" when the successor is the right child itself (deleting 30 from the tree above gives 20, 40, 50, …), and when it works at a node below the root it works only because the key is overwritten in place. But when the successor lies deeper (deleting 50), the recursive call reaches it through a discarded branch: the key 60 is copied to the root and the old 60 stays: the walk reads 20, 30, 40, 60, 60, 70, 80. (3) A root that is a leaf or has one child is handled correctly. That is why tests that only delete the root of a tiny tree pass and the bug survives. Real complexity of the code as written: still O(h) time, but it is the cost of a function that does not do its job. Fix: store what the recursive call returns, node.left = delete(node.left, key) and node.right = delete(node.right, key) (and the caller must write root = delete(root, key)). After the fix the tests of solutions/py/test_ex_read.pyExReadTest.java (theRepairIsCorrect) show the right result for every key of the example. The habit that finds it: after every operation check the ordering invariant and compare with a reference (sorted(list) / TreeSet) on random operations; and test deletion of every key of a small tree, not only the root.

Exercise 10 — contains in read/py/ex_read.py / ExRead.contains in read/java/ExRead.java. The comment claims O(h).

Solution

The error. The code returns the right answers but never uses the ordering: it searches the left subtree and the right subtree (contains(left) or contains(right)). That is a plain tree search, a preorder walk that stops at the first match. Real cost: a failed search visits every node, Θ(n); a successful search visits every node that comes before the key in preorder, up to n. On the 7-node tree of video 2, searching for 45 visits all 7 nodes where the real search visits 3 (50, 30, 40); the test counts these visits. The answers are right, so a correctness test cannot catch it; the doubling test does: in perfect trees of size 2ᵏ − 1 the correct search for an absent key visits k nodes, this one 2ᵏ − 1. (On a chain, both versions visit n nodes for the last key, since h = n − 1; this is not the case that shows the difference.) Fix: use the comparison to choose one side, if key < node.key: return contains(node.left, key) else contains(node.right, key), or write it as the loop of video 2. The cost is then O(h) (log n only for a balanced tree). The habit that finds it: count the nodes visited rather than timing, on a tree where h is much smaller than n, and compare with the length of the search path.

§4Working with AI

When an AI writes a tree or a BST it usually also claims that it works and how fast it is. Treat both as hypotheses:

  1. Delete every key, not just the root. Delete bugs hide behind small examples: a recursive call whose result is not stored (Exercise 9) passes tests that only delete the root. Test deleting each key of a small tree and compare with a reference (sorted list / TreeSet).
  2. Check the invariant after every operation. Write is_bst with an interval or an inorder check (never "node vs its children") and run it after each insert and delete in a random test.
  3. Feed it sorted input. A BST that is fast on shuffled keys and a chain on sorted keys is a classic; print the height and the comparisons for n = 1,000 and 10,000 (video 4), and use the doubling test of chapter 1.
  4. Count visited nodes, do not just time. A search that ignores the ordering returns right answers in O(n) (Exercise 10); only the count of visited nodes, compared with the length of the search path, shows it.
  5. Watch the recursion depth. Recursive tree code works on shuffled data and overflows on a chain: Python raises RecursionError at depth 1000 by default, Java throws StackOverflowError after a few thousand frames. Ask for a loop version, or test a long chain.
  6. Ask which comparison it uses. Keys that compare inconsistently with equals (Java compareTo) or with == vs is on numbers (Python) break searches in ways that small tests hide.
PITFALL · "O(log n)" without a reason is a claim, not a fact.

Ask what keeps the height small; for a plain BST the honest answer is "nothing".
