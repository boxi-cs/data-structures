RecursionData Structures · Chapter 4

A recursive function solves a problem by solving a smaller copy of the same problem. Four lines of Fibonacci make almost three million calls for fib(30); binary search finds one name among a million in at most twenty looks; merge sort and quicksort turn "sort everything" into "sort two halves". This chapter gives you the picture that explains all of it, the recursion tree, and the habit of reading the cost of a recursive function off the tree: the number of nodes is the time, the depth is the stack space.

Why this matters

about 100–130 minutes (4 videos of 7–9 minutes plus the exercises).

Cost lives in the tree, not in the code

A recursive function can be four lines long and still make billions of calls; counting the nodes of its recursion tree (and its depth) tells you the time and the stack space.

Recurrences turn a tree into a formula

T(n) = T(n/2) + 1 is binary search, T(n) = 2T(n/2) + n is merge sort; unrolling a recurrence is the same as summing the levels of the tree.

The same idea sorts faster, if the split is balanced

Merge sort splits evenly by construction, quicksort only by luck; the tree shows why a random pivot protects it.

§1Frames and the call stack

When a function calls itself, the computer cannot forget where it was: it stores a frame (the arguments and the place to continue from) on the call stack. The last call made is the first to return (last in, first out, exactly the stack of chapter 3).

def factorial(n):    if n == 0:        return 1    return n * factorial(n - 1)
public static long factorial(int n) {    if (n == 0) {        return 1;    }    return n * factorial(n - 1);}

The code is in code/py/recursion.pycode/java/Recursion.java. A traced run of factorial(3) (the real output of factorial_trace / factorialTrace):

The call stack of factorial(3)

The code with a pointer on the current line and the call stack drawn next to it: each call pushes a frame holding n, factorial(0) is the base case, then the frames pop one by one and the returned values 1, 1, 2, 6 appear. Choose n = 1…6.

PREDICT

How many frames are on the stack at the deepest moment for factorial(3)? For factorial(100)?

Show the answer

Four for factorial(3) (n = 3, 2, 1, 0), and 101 for factorial(100): n + 1 frames, one per call. For factorial the recursion tree is a chain, so the number of nodes and the depth are both n + 1.

§2The recursion tree: nodes are time, depth is space

Draw each call as a node, with the calls it makes as its children. Two numbers describe any recursive function: the number of nodes (the time: every call does some work) and the depth (how many frames can be on the stack at once: the space).

NOTE · Base case.

Every chain of calls must reach a case that returns without calling itself. In factorial it is n == 0. Exercise 9 shows how a base case that looks fine can still be missed.

§3Fibonacci: a wide tree

Each call of fib makes two calls, so the tree widens as it goes down. For fib(5) the tree has 15 nodes and only five levels: fib(3) is computed twice and fib(2) three times, because the tree keeps solving the same small problems from scratch.

The calls of fib(5)

The tree of fib(n), n = 3…7, expands one level at a time; repeated subproblems share a colour, a counter shows the nodes so far, a bar shows the depth. A toggle switches to the memoized tree where repeated nodes become single lookups.

PREDICT

fib(30) makes 2,692,537 calls. About how many does fib(32) make?

Show the answer

About 7 million (exactly 7,049,155). The count grows by a factor of about 1.6 per step (φ ≈ 1.618), so two steps multiply it by about 2.6: 2,692,537 · 2.6 ≈ 7.0 million. The calls satisfy C(n) = 1 + C(n − 1) + C(n − 2), which Exercise 1(d) solves exactly: C(n) = 2F(n + 1) − 1.

The cost of a recursive function is the size of its recursion tree. Count the calls (a global counter, as in code/py/recursion.py) before you trust a recursion.

§4Memoization

In Python the table is a dictionary passed down the calls (fib_memo(n, memo=None)); the standard library offers functools.lru_cache for the same job.

Memoization is the seed of dynamic programming, which this course does not cover; the idea is to turn a wide tree into a table.

§5The stack is finite

Every frame takes memory and every language limits how deep a recursion may go; a runaway recursion does not just get slow, it stops with an error.

Python limits the depth to 1,000 frames by default: depth(500) works, a deeper call raises RecursionError: maximum recursion depth exceeded. Python integers have unlimited size, so factorial(21) is 51,090,942,171,709,440,000.

Java's limit depends on the thread's stack size (the demo's depth(500) works, depth(100_000_000) throws StackOverflowError). Java's long has 64 bits: factorial(20) is 2,432,902,008,176,640,000 but factorial(21) wraps around to −4,249,290,049,419,214,848.

So when you design a recursive function ask two questions: how many nodes does the tree have, and how deep does it go?

Binary search and recurrences

How many looks does it take to find one name in a sorted phone book of a million names? At most twenty. We write the cost of binary search as a recurrence, solve it by unrolling, check it against real counts, and read recurrences as trees: levels times work per level.

§1Throw half away

Look at the middle item. If it is the target, done. If the target is smaller, search the left half, otherwise the right half. The list must be sorted: that is what lets one look rule out half of the items. Searching a half is the same problem again, only smaller.

Binary search: halve the range

Sixteen sorted numbers with pointers lo, mid, hi; each step dims the ruled-out half and a counter shows the looks so far. Target 51 is found in four looks. Try a target that is not there.

PREDICT

1,000 items need at most 10 looks. The list doubles to 2,000 items. How many looks, at most?

Show the answer

Only 11. One extra look cuts the doubled list back to the old size. The tempting answers (20, or "twice as many") confuse halving with doubling.

§2The recurrence

Let T(n) be the largest number of looks for n items. One look, then the same problem on at most half of the list: T(n) = T(n/2) + 1, with T(1) = 1. Unrolling: T(n) = T(n/4) + 2 = T(n/8) + 3 = … = T(1) + k = k + 1 for n = 2ᵏ, that is log₂ n + 1 (Exercise 1(a) proves it by induction).

Real worst-case probe counts (identical in both languages):

n12481632641282565121,024
probes1234567891011

For n = 1,000 the worst case is 10 probes and for n = 1,000,000 it is 20 (the exact formula is ⌊log₂ n⌋ + 1; Exercise 2 proves it).

§3Reading recurrences as trees

Many recursive algorithms fit one shape: a subproblems of size n/b, plus the work to split and combine. Draw the tree: at depth k there are aᵏ nodes, each with a problem of size n/bᵏ, and the cost is the sum level by level. Everything depends on one question: as we go down, does the work per level shrink, stay the same, or grow?

  • Equal on every level: total = work per level × number of levels. Binary search: one look per level, log₂ n levels.
  • Shrinking: the top level dominates. T(n) = T(n/2) + n costs n + n/2 + n/4 + … < 2n.
  • Growing: the leaves dominate. T(n) = 2T(n/2) + 1 has 2ᵏ nodes on level k and costs 2n − 1 in all.

This is the idea behind the master theorem; we use the intuition rather than memorize its cases. Merge sort (next video) is the "equal" case with T(n) = 2T(n/2) + n.

§4Pass indexes, not slices

return contains_sliced(items[mid + 1:], target)
PITFALL · A slice is a copy.

Passing items[mid + 1:] (Python) or Arrays.copyOfRange(...) (Java) to the recursive call looks neat but copies half the list on the first call, a quarter on the second, and so on: about n items in all, far more than twenty looks. The search is no longer logarithmic. Pass the bounds lo and hi instead.

The recursive and the iterative version are binary_search and binary_search_iter in code/py/binary_search.py; the copying one is contains_sliced.

The recursive and the iterative version are binarySearch and binarySearchIter in code/java/BinarySearch.java; the copying one is containsCopied.

PITFALL · The midpoint can overflow (Java).

(lo + hi) / 2 is fine in Python, whose integers have unlimited size. In Java, lo + hi overflows an int when both are around 2 billion: for lo = 2,000,000,000 and hi = 2,100,000,000 it gives −97,483,648. Use lo + (hi - lo) / 2. The same bug was found in the JDK's own binary search in 2006. (Exercise 10.)

§5In the standard library

Use the bisect module: bisect.bisect_left(items, x) returns the position where x is, or would be inserted to keep the list sorted. It returns an insertion point, not −1.

Use Arrays.binarySearch(int[], key) (or Collections.binarySearch(list, key)): it returns the index, or −(insertion point) − 1 when the key is missing.

Merge sort

Sorting a million items by comparing every pair takes about 500 billion comparisons; merge sort needs about 20 million. We merge two sorted lists with two fingers, split a list in half and sort each half recursively, and read the cost off the tree: n per level, log₂ n levels.

§1Merge: two fingers

Two lists are already sorted and we want one sorted list. Put a finger at the front of each, compare the two items, move the smaller to the output and advance that finger. Merging [2, 5, 9] and [1, 6, 7] takes 5 comparisons (1, 2, 5, 6, 7, then 9 is left over); merging n items takes at most n − 1.

§2Split, sort, merge

To sort a list: cut it in half, sort each half the same way, merge. A list of zero or one item is already sorted (the base case). Eight items are cut into eight single items, then merged back as pairs, fours, and one list of eight.

Merge sort: split, then merge

Eight numbers are cut in half down to single items (the recursion tree on top), then merged back up; each merge shows the two fingers and a counter of comparisons. Choose the numbers or shuffle.

PREDICT

Where does the sorting happen: when the list is split, or when it is merged?

Show the answer

In the merge. Splitting just computes a midpoint: nothing is compared and nothing moves. The recursion is the scaffolding that decides which merges to do, and in which order.

§3The cost: n per level, log n levels

T(n) = 2T(n/2) + n (two halves, then a merge of at most n comparisons). Level k of the tree has 2ᵏ merges of n/2ᵏ items each: every level costs about n, and there are log₂ n levels, so about n log₂ n in all. Unrolling gives T(n) = 2ᵏ·T(n/2ᵏ) + k·n, and k = log₂ n finishes it (Exercise 1(b)).

Real comparison counts on random lists (the two languages use different random generators, so the numbers differ slightly):

§4Properties

  • Always n log n, for any input: there is no bad case.
  • Extra memory: about n items for the merged lists.
  • Stable: equal items keep their order, because the merge takes from the left list on ties. That matters when you sort records by one field and want an earlier order kept for the rest.
  • Shallow stack: the recursion is only about log₂ n + 1 frames deep (21 for a million items).
NOTE · The work happens after the recursion.

Merge sort splits (free), recurses, then does its work. Quicksort, next, does its work before the recursion.

§5In the standard library

Call sorted(x) or x.sort(): they use Timsort, a stable merge-based sort. heapq.merge merges sorted inputs lazily.

Call Arrays.sort(Object[]), Collections.sort or List.sort: TimSort, stable and merge-based. Arrays.sort(int[]) uses a dual-pivot quicksort instead (stability is irrelevant for plain ints).

Quicksort

Quicksort sorts inside the array it is given, with no extra arrays. It picks a pivot, partitions the items around it, and recurses on both sides. A balanced split gives n log n, a lopsided split gives n², and an already sorted list is the worst input when the last item is the pivot. A random pivot protects us.

QuicksortVideo in preparation.
IN THIS CHAPTER§1 Partition§2 The cost depends on the split§3 A random pivot§4 In the standard library

§1Partition

Pick the last item as the pivot. Sweep through the list with an index j; keep a boundary i so that everything before i is smaller than the pivot. When item j is smaller than the pivot, swap it to the boundary and move the boundary on. After the sweep swap the pivot into the boundary: now the pivot is exactly where it belongs in the sorted list, and it never moves again. Partitioning n items takes n − 1 comparisons, one per other item.

def partition(items, lo, hi):    global comparisons    pivot = items[hi]    i = lo    for j in range(lo, hi):        comparisons += 1        if items[j] < pivot:            items[i], items[j] = items[j], items[i]            i += 1    items[i], items[hi] = items[hi], items[i]    return i
static int partition(int[] items, int lo, int hi) {    int pivot = items[hi];    int i = lo;    for (int j = lo; j < hi; j++) {        comparisons++;        if (items[j] < pivot) {            swap(items, i, j);            i++;        }    }    swap(items, i, hi);    return i;}
Quicksort: one partition

An array with the pivot highlighted, pointers i and j moving, swaps animated, then the pivot jumping into place; a toggle shows the recursion on the two sides as a tree and a counter of comparisons. Choose random, sorted, reversed or all-equal input.

§2The cost depends on the split

If the pivot lands near the middle, T(n) = 2T(n/2) + n: n log₂ n again. If it lands at an end, T(n) = T(n − 1) + (n − 1) = n(n − 1)/2 (Exercise 1(c)).

PREDICT

The list is already sorted and we always take the last item as the pivot. How many comparisons for 500 items?

Show the answer

124,750 = 500·499/2. The last item is the largest, so everything goes to the left, the right part is empty, and we are left with a sorted list one item shorter. The easiest-looking input is the worst one. With a random pivot the same list needs about 5,000 comparisons.

§3A random pivot

Pick a random item, swap it to the end, partition as before. No input is bad by design now: about half of the time the pivot lands in the middle half of the list, which already guarantees a decent split. The expected cost is about 1.39 n log₂ n = 2n ln n, whatever the input (Exercise 3 proves the bound 2n ln n). A bad split can still happen, but a long run of them is very unlikely.

quick_sort_random uses rng.randint(lo, hi), which includes both ends.

quickSortRandom uses lo + rng.nextInt(hi - lo + 1): nextInt(bound) excludes bound.

PITFALL · All items equal.

This partition puts only strictly smaller items on the left. If every item is equal, nothing goes left and we get the worst case again. Real libraries use a three-way partition (smaller, equal, larger).

PITFALL · Depth.

In the bad case the recursion is n frames deep and the stack overflows. A standard trick is to recurse on the smaller part and loop on the larger one, which keeps the depth at log₂ n (Exercise 5). This chapter's code does not implement it.

Sorting 2,000 already sorted items with the last item as the pivot raises RecursionError in the demo: the depth reaches the 1,000-frame limit.

Java's default stack holds far more frames than Python's 1,000: on our machine 10,000 sorted items still sort with the last item as the pivot, and 20,000 throw StackOverflowError (the limit depends on the JVM and the thread's stack size).

§4In the standard library

Python's own sorted and list.sort are Timsort, a merge-based sort, so they have no bad case like this one; quicksort lives in the libraries of other languages.

Arrays.sort(int[]) is a dual-pivot quicksort with insertion sort for tiny ranges; Arrays.sort(Object[]) is TimSort. Quicksort works in place and is often the fastest in practice, but unlike merge sort it is not stable and its worst case is real.

§2Check your understanding

1. The recursion tree of the naive fib(5) has 15 nodes and 5 levels. Which statement is right?

Every call does a little work, so time ∝ nodes; only the calls on one root-to-node path are on the stack at once, so space ∝ depth.

2. Binary search on 1,000 items needs at most 10 looks. On 2,000 items it needs at most

T(n) = T(n/2) + 1: doubling n adds one look (⌊log₂ 2,000⌋ + 1 = 11).

3. The recurrence T(n) = 2T(n/2) + n, T(1) = 0 solves to

Every level of the tree costs n and there are log₂ n levels (T(n) = n log₂ n for n = 2ᵏ).

4. Quicksort with the last item as the pivot sorts a list that is already sorted, 500 items. About how many comparisons?

Every partition removes one item: 499 + 498 + … + 1 + 0 = 500·499/2. (5,000 is what a random pivot needs.)

5. An AI says its recursive is_power_of_two(n) works for every n ≥ 0 because the base case is n == 1. What is wrong?

Test the base-case boundaries (0, 1, −1, an empty list) before you trust a recursive function (Exercise 9).

PROOFS

Exercise 1 · Unrolling recurrences. For each recurrence, unroll it a few levels, guess the closed form, and prove the closed form by induction. (In (a) and (b) take n = 2ᵏ.) (a) T(1) = 1 and T(n) = T(n/2) + 1. Compare your answer with the table of worst-case probes in video 2. (b) T(1) = 0 and T(n) = 2T(n/2) + n. Say what each level of the recursion tree contributes. (c) T(0) = 0 and T(n) = T(n − 1) + (n − 1). Evaluate it at n = 500. (d) C(0) = C(1) = 1 and C(n) = 1 + C(n − 1) + C(n − 2) is the number of calls the naive fib(n) makes. Let F(0) = 0, F(1) = 1, F(n) = F(n − 1) + F(n − 2) be the Fibonacci numbers. Prove that C(n) = 2F(n + 1) − 1, and check it against the call counts 15, 177 and 2,692,537 for n = 5, 10, 30.

Solution

Method: replace T(n) by its definition k times, find the pattern in k, stop when the argument reaches the base case, then prove the pattern by induction.

(a) T(n) = T(n/2) + 1 = T(n/4) + 2 = T(n/8) + 3 = … = T(n/2ʲ) + j. With n = 2ᵏ and j = k: T(n) = T(1) + k = k + 1 = log₂ n + 1. Proof. Claim P(k): T(2ᵏ) = k + 1. Base k = 0: T(1) = 1. ✓ Step: T(2^(k+1)) = T(2ᵏ) + 1 = k + 2 = (k + 1) + 1. ✓ ∎ Compare with the table of worst-case probes in video 2: n = 1, 2, 4, …, 1024 needs 1, 2, 3, …, 11 probes, i.e. k + 1 for n = 2ᵏ. (The table is the exact worst case of binary search; this recurrence reproduces it because one probe leaves at most half of the items.)

(b) T(n) = 2T(n/2) + n = 4T(n/4) + 2n = 8T(n/8) + 3n = … = 2ʲ·T(n/2ʲ) + j·n. With n = 2ᵏ and j = k: T(n) = n·T(1) + k·n = n log₂ n (T(1) = 0). Proof. P(k): T(2ᵏ) = k·2ᵏ. Base k = 0: T(1) = 0 = 0·1. ✓ Step: T(2^(k+1)) = 2·T(2ᵏ) + 2^(k+1) = 2·k·2ᵏ + 2^(k+1) = (k + 1)·2^(k+1). ✓ ∎ Reading it as a tree: level j has 2ʲ subproblems of size n/2ʲ, each costing n/2ʲ for its merge or partition, so every level costs n, and there are k = log₂ n levels. That is the n log n of merge sort (the measured 8,715 comparisons for n = 1,000 in Python are below n log₂ n ≈ 9,966, because merging stops early when one list runs out).

(c) T(n) = T(n − 1) + (n − 1) = T(n − 2) + (n − 2) + (n − 1) = … = 0 + 1 + 2 + … + (n − 1) = n(n − 1)/2. Proof. P(n): T(n) = n(n − 1)/2. Base n = 0: T(0) = 0. ✓ Step: T(n + 1) = T(n) + n = n(n − 1)/2 + n = n(n + 1)/2 = (n + 1)·n/2. ✓ ∎ For n = 500: 500·499/2 = 124,750, the comparison count of quicksort on sorted input in video 4.

(d) Proof. P(n): C(n) = 2F(n + 1) − 1. Base cases: C(0) = 1 = 2F(1) − 1 and C(1) = 1 = 2F(2) − 1 (F(1) = F(2) = 1). ✓ Step (n ≥ 2, assume P(n − 1) and P(n − 2)): C(n) = 1 + C(n − 1) + C(n − 2) = 1 + (2F(n) − 1) + (2F(n − 1) − 1) = 2(F(n) + F(n − 1)) − 1 = 2F(n + 1) − 1. ✓ ∎ Check: F(6) = 8 → 2·8 − 1 = 15; F(11) = 89 → 177; F(31) = 1,346,269 → 2,692,537. ✓ Since F(n) ≈ φⁿ/√5 with φ ≈ 1.618, every step up in n multiplies the call count by about 1.6: exponential.

Exercise 2 · Binary search. Let search(items, target, lo, hi) be the recursive binary search of video 2 on a list sorted in ascending order: if lo > hi return "not found"; let mid be the middle index of lo..hi; if items[mid] == target return mid; if items[mid] < target search mid + 1..hi, otherwise search lo..mid − 1. (a) Prove by induction on the length m = hi − lo + 1 of the range that search returns an index holding the target if and only if the target occurs in items[lo..hi]. Say exactly where you use the fact that the list is sorted. (b) Let P(m) be the largest number of probes (items looked at) over all targets when the range has m items. Show that P(0) = 0 and P(m) ≤ 1 + P(⌊m/2⌋), then prove P(m) ≤ ⌊log₂ m⌋ + 1 for every m ≥ 1. (c) Evaluate the bound for m = 1,000 and m = 1,000,000 and compare with the numbers in the video.

Solution

(a) Claim: for a list sorted in ascending order and any lo ≤ hi + 1 inside the list, search(items, target, lo, hi) returns an index of the target if it occurs in items[lo..hi], and "not found" if it does not. Strong induction on the range length m = hi − lo + 1 ≥ 0. Base m = 0 (lo > hi): the range is empty, the target does not occur, and the function returns "not found". ✓ Step m ≥ 1: then lo ≤ mid ≤ hi. If items[mid] == target the function returns mid, which holds the target. ✓ If items[mid] < target, then because the list is sorted every item of items[lo..mid] is ≤ items[mid] < target, so the target cannot be there: it occurs in items[lo..hi] exactly when it occurs in items[mid + 1..hi]. That range has hi − mid < m items (as mid ≥ lo), so by the induction hypothesis the recursive call answers correctly. The case items[mid] > target is symmetric with items[lo..mid − 1], of length mid − lo < m. ∎ Sortedness is used exactly once: to discard a whole half after one comparison. (On an unsorted list the call can discard the half that contains the target.)

(b) One probe, then a call on a range of length mid − lo = ⌊(m − 1)/2⌋ or hi − mid = ⌈(m − 1)/2⌉. Both are at most ⌊m/2⌋ (for m = 2t the lengths are t − 1 and t; for m = 2t + 1 both are t). So P(0) = 0 and P(m) ≤ 1 + P(⌊m/2⌋). Claim: P(m) ≤ ⌊log₂ m⌋ + 1 for m ≥ 1. Induction on m. Base m = 1: P(1) ≤ 1 + P(0) = 1 = ⌊log₂ 1⌋ + 1. ✓ Step m ≥ 2: ⌊m/2⌋ ≥ 1, so P(m) ≤ 1 + P(⌊m/2⌋) ≤ 1 + ⌊log₂ ⌊m/2⌋⌋ + 1. If 2ᵗ ≤ m < 2^(t+1) then 2^(t−1) ≤ ⌊m/2⌋ < 2ᵗ, so ⌊log₂ ⌊m/2⌋⌋ = t − 1 = ⌊log₂ m⌋ − 1 and P(m) ≤ ⌊log₂ m⌋ + 1. ✓ ∎

(c) m = 1,000: 2⁹ = 512 ≤ 1,000 < 1,024, so ⌊log₂ 1,000⌋ = 9 and the bound is 10. m = 1,000,000: 2¹⁹ = 524,288 ≤ 10⁶ < 2²⁰, so ⌊log₂ 10⁶⌋ = 19 and the bound is 20. These are the numbers the demos print (n = 1000: 10 probes, n = 1000000: 20 probes). Doubling the list from 1,000 to 2,000 raises the bound only from 10 to 11.

Exercise 3 · Quicksort. Quicksort with the last item as pivot: partitioning a range of m items makes m − 1 comparisons (each other item is compared with the pivot once). (a) The input is already sorted. Set up the recurrence for the number of comparisons, solve it with Exercise 1(c), and compare with 124,750 for n = 500. (b) Now choose the pivot uniformly at random in every range. Name the items by their rank 1, 2, …, n in sorted order (assume they are distinct). Prove that the items of rank i < j are compared at most once, and that they are compared with probability exactly 2 / (j − i + 1). Hint: when are two items separated for good? Which pivot decides it? (c) Use (b) to show that the expected number of comparisons is at most 2n ln n. Hint: group the pairs by d = j − i and use Σ 1/k ≤ ln n. How does the bound compare with the 5,116 (Python) and 4,744 (Java) comparisons the demos measured for n = 500 with a random pivot?

Solution

(a) On sorted input the last item is the largest, so the partition leaves all other m − 1 items on the left and the right part is empty. A range of m items costs m − 1 comparisons, and the left part is again sorted. So T(n) = T(n − 1) + (n − 1), T(0) = 0, and by Exercise 1(c) T(n) = n(n − 1)/2. For n = 500 that is 124,750, exactly the count the demos print (both languages). The recursion is also n levels deep, which is why 2,000 sorted items overflow Python's default recursion limit in the demo.

(b) At most once. Two items are compared only when one of them is the pivot and the other is in the pivot's current range. After a partition the pivot is in its final place and belongs to no later range, so a pair can be compared only in the step where one of the two is chosen as pivot; that happens once. Probability. Items of rank i < j stay in the same range for as long as no pivot with rank strictly between i and j has been chosen (such a pivot would send one of them left and the other right). Look at the first pivot chosen among the j − i + 1 ranks {i, i + 1, …, j}. While i and j are together, all of these ranks are in the current range and the pivot is uniform on the range, so the first pivot to land in the set is uniform on the set. If it is i or j, they are compared (one is the pivot, the other is in its range). If it is a rank strictly between, they are separated and never compared. Hence P(compared) = 2 / (j − i + 1).

(c) By linearity of expectation, E[C] = Σ over pairs i < j of 2/(j − i + 1). Group by d = j − i (there are n − d pairs with that difference): E[C] = Σ_{d=1}^{n−1} (n − d)·2/(d + 1) ≤ 2n·Σ_{d=1}^{n−1} 1/(d + 1) = 2n·(Hₙ − 1), where Hₙ = 1 + 1/2 + … + 1/n. And Hₙ − 1 = Σ_{k=2}^{n} 1/k ≤ ∫₁ⁿ dx/x = ln n. So E[C] ≤ 2n ln n ≈ 1.39 n log₂ n. For n = 500: 2n ln n ≈ 6,215. (The exact expectation of this sum is 2(n + 1)Hₙ − 4n; for n = 500 that is about 4,806.) The demos measured one run each: 5,116 in Python and 4,744 in Java, both close to the expectation and below the bound. Note what is random: the pivot choices, not the input, so the bound holds for every input, including sorted ones.

Exercise 4 · Towers of Hanoi. Three pegs; n disks of different sizes start on peg A, smallest on top. Move them all to peg C, one disk at a time, never putting a disk on a smaller one. (a) Find the recursion: how do you move n disks from one peg to another using the third as a spare, if you already know how to move n − 1 disks? State the base case. (b) Write the recurrence M(n) for the number of moves your method makes, solve it, and prove the solution by induction. Then argue that no method can use fewer moves. Hint: where must the other n − 1 disks be while the largest disk moves? (c) How many calls does the recursive method make in total (count the calls with n = 0 too)? What is the deepest number of frames on the call stack at once? With n = 64 and one move per second, how long would the moves take?

Solution

(a) To move n disks from A to C with spare B: (1) move the top n − 1 disks from A to B (using C as the spare); (2) move the largest disk from A to C; (3) move the n − 1 disks from B to C (using A as the spare). Base case: with n = 0 disks there is nothing to do.

(b) M(0) = 0 and M(n) = 2M(n − 1) + 1. Unrolling: M(n) = 2M(n − 1) + 1 = 4M(n − 2) + 2 + 1 = … = 2ⁿ·M(0) + (2ⁿ⁻¹ + … + 2 + 1) = 2ⁿ − 1. Proof. P(n): M(n) = 2ⁿ − 1. Base n = 0: 0 = 2⁰ − 1. ✓ Step: M(n + 1) = 2(2ⁿ − 1) + 1 = 2^(n+1) − 1. ✓ ∎ No method does better. Let Opt(n) be the fewest moves. The largest disk has to move at least once. When it moves from its peg to another, no other disk can be on either of those two pegs (a disk on top of it would block it; a disk on the target peg would be smaller than the largest disk, which is not allowed to sit on it), so all n − 1 other disks are on the third peg. Getting them there took at least Opt(n − 1) moves (it is the same puzzle for n − 1 disks), and after the big move they must travel again to the target peg, at least Opt(n − 1) more. So Opt(n) ≥ 2·Opt(n − 1) + 1, and by induction Opt(n) ≥ 2ⁿ − 1. The recursive method is optimal.

(c) Let K(n) be the number of calls: K(0) = 1 and K(n) = 1 + 2K(n − 1), so K(n) = 2^(n+1) − 1 (a complete binary tree with n + 1 levels). The call stack is deepest at the first leaf, n + 1 frames (n = n, n − 1, …, 0), so the depth is linear while the time is exponential. For n = 64: 2⁶⁴ − 1 = 18,446,744,073,709,551,615 moves; at one move per second that is about 5.8 × 10¹¹ years, roughly forty times the age of the universe.

Exercise 5 · Which sort, and how deep? Two jobs: (A) sort 10,000,000 records by last name; the records are already in first-name order and records with the same last name must keep that order; there is memory for about one extra copy of the data. (B) Sort an array of 10,000,000 ints in place; memory is tight. (a) Choose an algorithm from this chapter for each job and justify the choice with: stability, worst-case time, extra memory and call-stack depth. (b) With the last item as the pivot, quicksort's recursion can be n frames deep. Change the recursion so that the depth is at most log₂ n whatever the input, say which part you recurse on and which you handle by a loop, and prove the bound. Does the worst-case running time improve? (c) What do Python and Java use for these two jobs in their standard libraries?

Solution

(a) Job A: merge sort (or the library's stable sort): it has to be stable, because equal last names must keep their first-name order; its time is Θ(n log n) for every input; the extra memory is about n items, which the problem allows; the call stack is only about log₂ n ≈ 24 frames deep for n = 10⁷. Quicksort as written here is not stable. Job B: quicksort with a random pivot: in place (no second array), expected n log n comparisons (≈ 1.39 n log₂ n) for every input, and the equal-ints question does not arise (equal ints are indistinguishable, so stability is irrelevant for plain ints). The price is the worst case Θ(n²), which a random pivot makes very unlikely, and a deep stack (see (b)). Merge sort would work but needs a second array, which job B cannot spare.

(b) After the partition recurse on the smaller of the two parts and handle the larger part by looping (update lo/hi and partition again) instead of calling. Each recursive call is on at most half of the current range, so the depth d satisfies n/2ᵈ ≥ 1, i.e. d ≤ log₂ n, whatever the pivots are. The worst-case running time does not improve: it is still Θ(n²) for a pivot that is always extreme (the loop does the same work the larger call would have done). Only the stack space is bounded, which removes the stack overflow but not the slowness. (This chapter's code does not implement the trick; the video only names it.)

(c) Python: sorted and list.sort use Timsort, a stable merge-based sort, for both jobs. Java: Arrays.sort(int[]) (job B) is a dual-pivot quicksort with insertion sort for small ranges; Arrays.sort(Object[]), Collections.sort and List.sort (job A) are TimSort, stable and merge-based. In real programs call the library; the point of this chapter is to know what it trades.

Exercise 8 · Partition and quickselect. In ex_quickselect.pyExQuickselect.java write Lomuto partition and use it to find the k-th smallest item without sorting. The tests count comparisons through a counting item or comparator: partition must make exactly hi − lo comparisons and quickselect must stay linear even on sorted input.

Solution

Reference code: solutions/py/ex_quickselect.py, solutions/java/ExQuickselect.java. Partition keeps the invariant "a[lo..i−1] < pivot, a[i..j−1] ≥ pivot" while j sweeps from lo to hi − 1; each step compares a[j] with the pivot once, so exactly hi − lo comparisons. Finally the pivot is swapped into position i. Quickselect partitions, and then the pivot's final index p tells where the k-th smallest item is: p = k means the pivot is the answer, k < p means the answer is in the left part, k > p in the right part, so only one side is searched. The invariant "lo ≤ k ≤ hi" holds at every iteration, so the loop ends when p = k. With a random pivot the expected number of comparisons is linear (about 3.4n for the median; we measured a mean of 3.41n for n = 4,000, and never more than 8.2n in 900 runs, which is why the tests allow 12n). With the last item as the pivot, sorted input would cost about n²/2. Sorting first would cost n log n; quickselect saves the log n factor.

Exercise 9 · A missing base case. read/py/ex_read.pyread/java/ExRead.java, function is_power_of_two / isPowerOfTwo. The assistant says it works for every n ≥ 0 and always terminates. Find the input that breaks it, say what the program does, and fix it. Java readers: also try n = −1 and say why Java behaves differently from Python.

Solution

is_power_of_two(0) never terminates: 0 is even and 0 // 2 = 0, so the call repeats itself with the same argument until the stack is exhausted (Python raises RecursionError, Java StackOverflowError). The docstring's claims "works for every n ≥ 0" and "always terminates" are false: the only stopping case is n == 1 (and the odd case), and the sequence n, n//2, n//4, … from n = 0 is stuck at 0 and never reaches 1. A recursion needs a base case that every chain of calls reaches; here 0 is a fixed point of the step n ↦ n//2. In Java −1 breaks it too: -1 % 2 is −1 in Java (the remainder keeps the sign of the dividend), so the test n % 2 == 1 is false for negative odd numbers; the method then calls itself with −1 / 2 = 0 and falls into the same loop. In Python −1 % 2 is 1, so is_power_of_two(-1) returns False. Fix: a power of two is positive, so start with if n < 1: return False (Java: if (n < 1) return false;), or avoid recursion: n > 0 and n & (n - 1) == 0. The tests in solutions/ show the failing inputs.

Exercise 10 · A binary search that does not end. In the same file, contains (and, in Java, midpoint). (a) Find an input on which contains never terminates, and an input that makes it look correct. Explain which sentence of the docstring is false and fix the code. (b) Java readers: the docstring of midpoint also makes a claim; find a pair of indexes that breaks it, say what the method returns, and give two fixes. Why can the Python version of the same line not fail this way?

Solution

(a) contains([1, 2], 2): lo = 0, hi = 1, mid = 0, items[0] = 1 < 2, so it calls contains(items, 2, mid, hi) = contains(items, 2, 0, 1), the same call, forever (RecursionError / StackOverflowError). contains([1, 3, 5], 5) and contains([1, 3, 5], 4) stall the same way. It looks correct on contains([1, 2, 3, 4, 5], 3) (found at the first middle) and on any target in the left half, because the left branch is mid − 1, which does shrink the range; only the right branch is broken, so tests that never need to go right pass. The false sentence is "Every call works on a smaller part of the list": the right call uses mid, not mid + 1. We have just looked at items[mid] and found it too small, so the range must start after it. Since mid is rounded down, mid == lo whenever hi ≤ lo + 1, and the range does not shrink at all. Fix: contains(items, target, mid + 1, hi). By Exercise 2 the corrected version is correct and ends after at most ⌊log₂ n⌋ + 1 calls. (b) (Java) midpoint(2_000_000_000, 2_100_000_000): lo + hi = 4,100,000,000 does not fit in an int (maximum 2,147,483,647), wraps around to −194,967,296, and dividing by 2 gives −97,483,648, a negative array index. The claim "correct for every pair of valid indexes" is false for arrays with more than 2³⁰ elements. Fixes: lo + (hi - lo) / 2 (hi − lo never overflows when 0 ≤ lo ≤ hi), or the unsigned shift (lo + hi) >>> 1 (the sum is read as an unsigned 32-bit number, which fits). The same line was found in the JDK's own binary search and reported in 2006. A Python int has unlimited size, so (lo + hi) // 2 cannot overflow; that part of the bug is specific to fixed-width integers.

§4Working with AI

When an AI writes a recursive function, test the recursion the way this chapter taught you to read it:

  1. Find the base case and attack its boundary. Run 0, 1, −1, an empty list, one item, two items. Every chain of calls must reach a base case; a step like n // 2 has 0 as a fixed point (Exercise 9).
  2. Count the calls. Add a counter (or wrap the arguments, as in the demos) and compare the count with the formula the AI claims; for two sizes n and 2n the ratio tells you linear, n log n, quadratic or exponential (the doubling test of chapter 1).
  3. Ask for the recurrence, then unroll it yourself. "State T(n) and solve it" is a claim you can check against the counter.
  4. Check the depth. Run it on 10,000 and 100,000 items: Python RecursionError, Java StackOverflowError are not "edge cases", they are the stack limit of the tree's depth. An input that is already sorted, reversed or all equal is the usual culprit for quicksort.
  5. Hunt hidden copies. Slices (items[mid + 1:]) and Arrays.copyOfRange make each call O(n); an AI's "O(log n)" binary search with slices is O(n) (video 2).
  6. Compare with the library. On random, sorted, reversed and all-equal inputs compare the result with sorted (Python) or Arrays.sort (Java); the tests of this chapter do exactly that.
  7. Ask for the loop invariant of every iterative rewrite (chapter 1, video 4) and check it with an assertion.
PITFALL · A clear explanation is not a correct program.

An AI's description of why its recursion terminates reads equally well when it is wrong (Exercises 9 and 10).
