Arrays and Linked ListsData Structures · Chapter 2

Where you put things in memory decides which operations are cheap. An array keeps its items side by side, so item i is one multiplication away, but inserting in the middle shifts everything after it. A linked list keeps its nodes anywhere and joins them with references, so inserting at the front moves nothing, but reaching the middle means walking. This chapter builds both, measures what each operation really costs, shows how a dynamic array grows without ever running out of room, and teaches the habit that decides whether pointer code is right: the order of the updates.

Array or linked list? Count the work

Two rows with the same n items: an array and a linked list. Choose "read item i", "insert at the front", "insert in the middle" or "remove the last item". Counters show the item moves (array) and the reference hops and changes (linked list) for each, and the counts grow with n as the chapter predicts.

Why this matters

about 100–130 minutes (4 videos of 8–12 minutes plus the exercises).

A layout decides the costs

"Side by side" gives constant-time access by index and expensive insertion in the middle; "joined by references" gives the opposite. Every structure later in the course is one of these two ideas, or a mix.

Growth is a design problem

A fixed block cannot grow, so a dynamic array allocates a bigger one and copies. Doubling the size makes that cheap on average; growing by a constant makes it quadratic. The same amortized argument returns in hashing and heaps.

Pointer code is easy to get almost right

Update the references in the wrong order, or forget the tail, and a list silently loses nodes. The same bug is common in code written by an AI, and a structural check (size equals the number of reachable nodes) finds it.

§1How does it find item 500,000?

A list of a million names answers "give me the 500,000th" instantly. The computer does not count its way there: memory is a long row of numbered boxes (addresses), the array reserves one block of them, and the items sit side by side in it. Say each item takes 4 boxes (4 bytes) and the block starts at address 1000 (the base address). Item 0 starts at 1000, item 1 at 1004, item 2 at 1008. In general

address(i) = base + i × size

PREDICT

At which address does item 500,000 start (base 1000, 4 bytes per item)?

Show the answer

1000 + 4 × 500,000 = 2,001,000. One multiplication and one addition, exactly as much work as for item 5. Reading or writing an item by its index is O(1).

Why index access is constant time

A row of numbered memory boxes with an array laid out in it. Slide i and watch the address formula fill in: base + i × size, the item's boxes highlight. The step counter stays at 2 (one multiplication, one addition) for every i.

NOTE · The misconception.

"Item i is found by walking past the i items before it." That describes a linked list (video 3), not an array.

§2Capacity and size

The block is reserved in advance, and the memory just after it may already belong to something else, so an array has a fixed capacity: the number of slots reserved. Alongside it we keep a size: how many of those slots hold real items. Capacity 8 and size 5 means five items and three free slots.

§3Inserting in the middle

Insert X at position 2 of A B C D E (capacity 8, size 5). The items must stay side by side with no gap, so C, D and E all move one slot to the right. The last one moves first: if C moved first it would overwrite D. E moves, then D, then C; now slot 2 is free and X goes in. Three items moved. In general the number of items that move is size − position: all of them for an insert at the front, none at the end.

PREDICT

How many items move if you insert at position 0 of an array that holds 1,000 items (capacity 1,001)?

Show the answer

All 1,000: size − position = 1,000 − 0. Inserting 1,000 items one after another at the front therefore moves 0 + 1 + … + 999 = 499,500 items in total, the same n(n − 1)/2 as the pair count of chapter 1.

Insert into the middle of an array

An array of 5 letters in capacity 8. Click a position, type a letter, press Insert: the items from that position on slide right one at a time, last one first, a counter "shifts" ticks, and the new letter drops into the gap. "Remove" does the mirror image. The formula "shifts = size − position" is shown and checked against the counter.

Removing is the mirror image: the items after the hole slide one slot to the left, starting with the first of them, so the cost is size − 1 − position moves. Cheap at the end, expensive at the front.

§5In Python and in Java

Python reserves a block of eight slots with [None] * 8. A Python list does not hold the items themselves: each slot holds a reference (a small address) to an object stored elsewhere. The slots are side by side, so the address formula still works, on the references.

Java builds arrays into the language: new int[8] reserves eight ints, 4 bytes each, side by side, filled with zeros, so an empty slot shows as 0 and the array cannot say which slots are in use: keep a separate size. An int[] really holds the numbers, so the address formula is exactly what the machine does. Java also checks every index at run time: ask for a slot outside the array and you get an exception, never someone else's memory.

def insert(self, index, value):          # code/py/array_ops.py    if self.size == len(self.items):        raise OverflowError("array is full")    if not 0 <= index <= self.size:        raise IndexError("index out of range")    for k in range(self.size, index, -1):    # last item first        self.items[k] = self.items[k - 1]    self.items[index] = value    self.size += 1
public static void insert(int[] a, int size, int index, int value) {   // code/java/ArrayOps.java    if (size == a.length) {        throw new IllegalStateException("array is full");    }    if (index < 0 || index > size) {        throw new IndexOutOfBoundsException("index out of range");    }    for (int k = size; k > index; k--) {     // last item first        a[k] = a[k - 1];    }    a[index] = value;}

Measured on our machine (code/py/bench_array_output.txt), one insert at the front takes about 44 µs at 2,000 items, 88 at 4,000, 190 at 8,000 and 395 at 16,000: eight times the items, about eight times the time. In the middle it takes about half as long.

Measured on our machine (code/java/bench_array_output.txt), one insert at the front takes about 0.19 µs at 2,000 items, 0.38 at 4,000, 0.76 at 8,000 and 1.56 at 16,000: eight times the items, about eight times the time. Java is far faster than Python here because the machine compiles the loop into a bulk memory copy, but the shape is the same.

PREDICT

The front insert takes about 395 µs (Python) or 1.6 µs (Java) at 16,000 items. What do you expect at 32,000?

Show the answer

About twice as much: 790 µs in Python, roughly 3 µs in Java. One insert is linear in n (size − 0 moves); it is n such inserts in a row that cost quadratic time.

PITFALL · O(1) access does not mean O(1) insertion.

An array is the right tool when you read by index far more often than you insert in the middle.

§1What happens when the block is full?

An array has a fixed capacity, but apps append items forever. The trick is a resize in three steps: reserve a new, bigger block, copy every item into it one at a time, then discard the old block. Then the append goes on. We start at capacity 1 and double when full. Cost model: 1 per item written, 1 per item copied.

append number123456–8910–1617
capacity after it124488161632
copies so far013377151531

A resize happens at append number 2ʲ + 1 and copies 2ʲ items: that is where 1, 3, 7, 15, 31 come from.

PREDICT

How many items are copied in total by 100 appends (capacity 1, doubling)?

Show the answer

Resizes at appends 2, 3, 5, 9, 17, 33, 65 copy 1 + 2 + 4 + 8 + 16 + 32 + 64 = 127 items: fewer than 2 × 100. (Our demo_growth prints 15, 127, 1,023 and 4,095 for 10, 100, 1,000 and 4,000 appends.)

A dynamic array grows

A row of boxes fills up. When it is full the three resize steps play: a bigger empty row appears (reserve), the items fly across one by one while a copy counter ticks (copy), and the old row fades (discard). Switch the growth rule between "double" and "add 1": a second counter shows the total copies, and a cost-per-append bar shows why one of them is amortized O(1).

§2Why doubling is cheap on average

Over n appends the copies are 1 + 2 + 4 + … + 2ᴶ < 2*n* (with 2ᴶ ≤ n − 1), and the n writes add n: fewer than 3 steps per append on average, the aggregate argument of chapter 1. The accounting argument says the same: charge each append 3 coins, 1 for the write and 2 saved on the new item; when the array fills up, the items added since the last resize hold enough coins to pay for copying all of them. So an append is amortized O(1).

PITFALL · Growing by a constant.

If the capacity grows by 1 (or by any fixed amount) when full, almost every append copies the whole array. For +1 the total is n(n − 1)/2 copies: 45 for 10 appends, 4,950 for 100, 499,500 for 1,000 and 7,998,000 for 4,000, against 15, 127, 1,023 and 4,095 for doubling. Multiply by a constant factor instead. Exercise 2 works out the factor g: fewer than g/(g − 1) copies per append.

NOTE · Amortized O(1) is not "every append is fast".

One append, the one that triggers the resize, still costs n copies. The guarantee is about the total over any sequence of appends, with no assumption about the data (it is not an average over random inputs).

Python has no raw array, so our DynamicArray reserves a block with [None] * new_capacity and copies in a loop (code/py/dynamic_array.py).

Java makes the three steps visible: Arrays.copyOf reserves and copies in one call, and the old array becomes garbage (code/java/DynamicArray.java).

def _resize(self, new_capacity):          # code/py/dynamic_array.py    bigger = [None] * new_capacity        # reserve    for k in range(self.size):        bigger[k] = self.items[k]         # copy, one item at a time        self.copies += 1    self.items = bigger                   # the old list is discarded
private void resize(int newCapacity) {    // code/java/DynamicArray.java    copies += size;    items = Arrays.copyOf(items, newCapacity);   // reserve + copy; the old array is discarded}

§3In the standard library

A Python list is a dynamic array, but CPython does not double: measured on 3.12.3 (code/py/probe_builtin_growth.out.txt) the capacity steps 4, 8, 16, 24, 32, 40, 52, 64, 76, 92, 108, 128, … (at appends 1, 5, 9, 17, 25, 33, 41, 53, 65, 77, 93, 109), a growth factor that settles near 1.13 (CPython over-allocates by about an eighth). Any constant factor above 1 gives amortized O(1) (Exercise 2: the smaller the factor, the more copying per append).

ArrayList is a dynamic array: measured on Java 21 (code/java/ProbeArrayList.out.txt) its capacity goes 10, 15, 22, 33, 49, 73, 109, 163, … a growth factor of 1.5, starting at 10 on the first add. Any constant factor above 1 gives amortized O(1) (Exercise 2).

§1Can we insert at the front without moving anything?

In an array, inserting at the front moves every item. A linked list answers differently: each node holds a value and a reference next to the following node; the last node's next is empty (None, null, drawn ∅). The list is a reference head to the first node. The nodes can sit anywhere in memory; what keeps them in order is the arrows.

§2add_first: two steps, in this order

To put A in front of B → C → D: (1) create the node A and make its next point at the old head B; (2) only then move head to A. Nothing else changes: no item moved.

PITFALL · Order matters.

Move head first, and the only reference to B is gone. Then "A's next := head" points A at itself: B, C and D are lost, a walk from head circles forever on A, and size still says 4. The rule: connect the new node to the rest of the list first, then change what the list starts with.

PREDICT

In add_first the order is "new node's next := head, then head := new node". If you swap the two lines, how many of the old nodes can you still reach from head?

Show the answer

None, whatever the length: after head := new node the old first node has no reference left, and "new.next := head" now reads the new head, which is the new node itself (a cycle of length 1). That is Exercise 3(b); the shorter variant new.next := head.next after moving head is the bug in Exercise 10.

Add at the head of a linked list

The list B → C → D with a head arrow. A new node A appears; step 1 draws A's arrow to B, step 2 moves the head arrow to A. A second copy of the list does the two steps in the wrong order: the head moves first and B, C, D fade out as unreachable. The code (the real add_first) highlights the line that is running.

insert_after(node, value) follows the same recipe on a node you already hold: first make the new node point to whatever node pointed to, then make node point to the new node: two reference changes, no walking. remove_first is just head := head.next.

def add_first(self, value):               # code/py/singly_linked_list.py    self.head = Node(value, self.head)    # the new node gets the old head as its next, then head moves    if self.tail is None:        self.tail = self.head    self.size += 1 def insert_after(self, node, value):    node.next = Node(value, node.next)    # same order again    if node is self.tail:        self.tail = node.next    self.size += 1
public void addFirst(E value) {           // code/java/SinglyLinkedList.java    head = new Node<>(value, head);       // the new Node gets the old head as its next, then head moves    if (tail == null) {        tail = head;    }    size++;}

§3Insertion is O(1) only once you hold the node

PITFALL · "A linked list makes every insertion O(1)."

Only the insertion step is. Finding the node in the middle takes n/2 hops, one next at a time, so inserting at position i costs i hops plus two reference changes.

arraylinked list
insert at the frontO(n): every item movesO(1)
insert at the endO(1) (if there is room)O(1) with a tail reference

read item iO(1)i hops

Measured (code/py/bench_output.txt, microseconds per insert at 2,000 → 16,000 items): at the front the array goes 47 → 373 µs and the linked list stays at about 0.1 µs; in the middle the array goes 26 → 187 µs and the linked list 9 → 74 µs (it grows by about 8×, the walk).

Measured (code/java/bench_output.txt, microseconds per insert at 2,000 → 16,000 items): at the front the array goes 0.19 → 1.6 µs and the linked list stays at about 0.01 µs; in the middle the array goes 0.12 → 0.76 µs and the linked list 0.75 → 6.2 µs: the linked list is slower than the array at every size, because walking node to node costs more than the machine's bulk copy.

PREDICT

You must insert in the middle of a list of 16,000 items. Linked list or array: which is faster, in Python and in Java?

Show the answer

In our measurements the linked list wins in Python (74 µs against 187 µs) and loses in Java (6.2 µs against 0.76 µs). The operation counts (n/2 hops against n/2 moves) do not decide it alone: what one hop and one move cost on the machine matters too. Big-O tells you how it grows, not who is faster at a given n.

Singly, doubly and circularly linked lists

We can add and remove at the front of a linked list, and add at the end with a tail reference, in constant time. Removing the last node is different: the node before it is needed, and a singly linked node does not know its predecessor. A doubly linked list gives every node a prev reference, two sentinel nodes remove the special cases, and a circular list makes the last node point back to the first.

§1Why can't we remove the last node quickly?

Removing a node means making its predecessor skip it. In A → B → C → D with head and tail, to remove D we must set C's next to empty and move tail to C, but no reference leads from D back to C. The only route to C is from head: A → B → C, 2 hops, and in general n − 2 hops, so remove_last is O(n). (Exercise 3(c) proves that no program that can only follow head, tail and next can do better.)

§2Doubly linked: a prev reference in every node

Give each node a prev reference as well as next. Now any node we hold can be removed in O(1): its predecessor is node.prev and its successor node.next, and removing it means two assignments, so the neighbours skip it.

def delete_node(self, node):              # code/py/doubly_linked_list.py    node.prev.next = node.next            # the predecessor skips the node    node.next.prev = node.prev            # the successor skips the node    self.size -= 1    return node.value
public E deleteNode(Node<E> node) {       // code/java/DoublyLinkedList.java    node.prev.next = node.next;    node.next.prev = node.prev;    size--;    return node.value;}
PREDICT

In A ⇄ B ⇄ C ⇄ D you delete C. How many references change? And when you insert a new node between B and C?

Show the answer

Deleting C changes 2 references (B's next, D's prev). Inserting between B and C writes 4: the new node's prev and next, then B's next and C's prev, new node first, so the list stays connected at every step. Two references per link is the price of the second direction.

Remove the last node of a doubly linked list

Two lists with the same items A…H. Left, singly linked: a cursor walks from head, counting hops (n − 2 = 6), then the last node is cut off. Right, doubly linked: tail.prev is the node before the last and the removal takes the two assignments at once. Change n and watch the left hop counter grow while the right one stays at 0.

§3Sentinels

A header and a trailer sentinel (nodes that hold no item) sit at the two ends; the real items always sit between them. An empty list is just header ⇄ trailer. Insertion and deletion never need a special case for the first, last or only item, because the neighbours always exist. add_first is insert_between(value, header, header.next), add_last is insert_between(value, trailer.prev, trailer), remove_last is delete_node(trailer.prev).

§4Circular lists

Make the last node point back to the first. One reference, tail, now gives both ends (tail.next is the first node), and rotating, moving the first item to the back, is a single step: tail := tail.next. That fits taking turns: serve the front, rotate. With Ann, Bo and Cy the turns go Ann, Bo, Cy, Ann.

A circular list as a round-robin scheduler

A ring of names with a tail marker. Press "Serve" to take the front, then the tail marker advances one node and the served name is the last in the queue; add and finish processes with the buttons. A caption lists the turns: Ann, Bo, Cy, Ann.

PITFALL · "Doubly linked is just better."

It stores an extra reference in every node and has twice as many references to keep consistent after every change: a bug in either direction corrupts the list. Use it when you need to remove from the back or to delete nodes you already hold; otherwise a singly linked list is simpler.

In Python, DoublyLinkedList in code/py/doubly_linked_list.py keeps header and trailer as ordinary nodes whose value is None; delete_node and insert_between are exactly the assignments above.

In Java, DoublyLinkedList<E> in code/java/DoublyLinkedList.java uses a nested Node<E> with prev and next; removeLast throws NoSuchElementException on an empty list. The standard java.util.LinkedList is doubly linked; ArrayDeque is usually the better choice as a queue, and chapter 3 returns to it.

§2Check your understanding

1. An array of 4-byte items starts at address 1000. At which address does item 500,000 start?

1000 + 4 × 500,000: one multiplication and one addition, whatever the index.

2. A dynamic array doubles its capacity when full. Which statement is true?

Amortized O(1) is a guarantee about a whole sequence of appends; growing by 1 copies n(n−1)/2 items in all.

3. In add_first on a singly linked list, which order of the two updates is correct?

Connect the new node to the rest of the list first; the other order loses every old node.

4. A singly linked list with head and tail holds 1,000 nodes. How many next hops does it take to reach the node before the tail, so that you can remove the last node?

That node is node number 999, which is 998 hops after head: n − 2.

5. You hold a node X in a doubly linked list with sentinels. What does deleting X cost?

X.prev.next = X.next and X.next.prev = X.prev: no walking, no moving.

(c) Insert n items one after another, each at index 0, into an initially empty array that is big enough. Prove by induction on n that the total number of moves is n(n − 1)/2.

Solution

(a) Item i starts at address(i) = base + i · s, where s is the item size. With base 5000 and s = 4, item 250 starts at 5000 + 4·250 = 6000. It is one multiplication and one addition whatever i is: no loop, no walk past the earlier items, so reading or writing item i is O(1). For the table, row-major order puts cell (r, c) at index r·C + c, so its address is base + (r·C + c)·s. With r = 3, c = 5, C = 8, s = 8 and base 2000: index 3·8 + 5 = 29 and address 2000 + 8·29 = 2232.

(b) There are n + 1 equally likely positions k = 0, …, n, and position k moves n − k items, so the average is (1/(n+1)) · Σₖ (n − k) = (1/(n+1)) · (n + (n−1) + … + 0) = (1/(n+1)) · n(n+1)/2 = n/2. A random insert still moves half the array: Θ(n).

(c) Claim P(n): after n inserts at index 0 into an initially empty array the total number of moves is n(n − 1)/2. Base n = 0: no insert, 0 moves, and 0·(−1)/2 = 0. ✓ Step: assume P(n). The (n+1)-th insert finds n items in the array and moves all of them (n − 0 = n), so the total becomes n(n − 1)/2 + n = (n*² + *n)/2 = (n + 1)n/2, which is P(n + 1). ∎ n inserts at the front cost Θ(*n*²), the same sum as the pair count of chapter 1, and the same shape the stopwatch showed (eight times the items, about eight times the time of one insert).

Exercise 2 · Growth factors. A dynamic array starts with capacity 1 and size 0. When an append finds the array full it multiplies the capacity by an integer g ≥ 2, copies every element once, and then writes. Cost model: 1 per element written, 1 per element copied. (a) Take g = 3 (capacities 1, 3, 9, 27, …). A resize happens at append number 3ʲ + 1 and copies 3ʲ elements. Show that n appends make fewer than 1.5·n copies. (b) For a general integer g ≥ 2 show that n appends make fewer than g·n/(g − 1) copies. What does this give for the amortized cost of an append (writes and copies together)? Check that g = 2 reproduces the "fewer than 3 per append" of chapter 1. (c) Right after a resize the array is as empty as it will ever get while you only append. How empty, as a fraction of the capacity, as a function of g? State the trade-off between copying and wasted memory.

Solution

(a) Let n ≥ 2 and let J be the largest j with 3ʲ + 1 ≤ n, that is 3ᴶ ≤ n − 1. The resizes happen at appends 3⁰ + 1, 3¹ + 1, …, 3ᴶ + 1 and copy 1, 3, …, 3ᴶ elements, in total (3^(J+1) − 1)/2 (geometric series). Since 3^(J+1) = 3·3ᴶ ≤ 3(n − 1), the total is at most (3(n − 1) − 1)/2 = (3*n* − 4)/2 < 1.5·n. For n = 1 there is no copy. Check: n = 10 has resizes at appends 2, 4, 10: 1 + 3 + 9 = 13 < 15; n = 100 has resizes at 2, 4, 10, 28, 82: 1 + 3 + 9 + 27 + 81 = 121 < 150.

(b) The same argument with g in place of 3: copies = (g^(J+1) − 1)/(g − 1) with g*ᴶ ≤ *n − 1, so copies ≤ (g(n − 1) − 1)/(g − 1) < g·n/(g − 1). Adding the n writes, an append costs on average less than 1 + g/(g − 1) = (2*g* − 1)/(g − 1): for g = 2 that is 3 (the "fewer than 3*n* steps" of chapter 1), for g = 3 it is 2.5, for g = 4 about 2.33. The argument also works for a real factor g > 1 (the capacities form a geometric series whose sum is at most g/(g − 1) times its largest term). A factor as small as CPython's roughly 1.125 therefore allows up to about 9 copies per append, against under 2 for doubling: a small factor means frequent resizes.

(c) Right after the resize at append g*ʲ + 1 the capacity is *g^(j+1) and the size is g*ʲ + 1, so the filled fraction is (*g*ʲ + 1)/*g^(j+1) > 1/g. While you only append, the array is never less than 1/g full, so less than (g − 1)/g of the slots are idle: under 1/2 for g = 2 and under 2/3 for g = 3. The trade-off: a bigger factor copies less (under 2 copies per append for g = 2, under 1.5 for g = 3) but can leave more memory unused.

Exercise 3 · Pointer updates and a lower bound. A singly linked list keeps head, tail and size. Call the list well formed if following next from head visits exactly size nodes, the last one is tail, and tail.next is empty (and head, tail are empty exactly when size is 0). (a) The operation add_first(v) is: new node's next ← head; head ← new node; if the list was empty, tail ← new node; size ← size + 1. Prove that it keeps a well formed list well formed. (b) Now do the first two steps in the other order: head ← new node, then new node's next ← head. If the list had m nodes, what is the new node's next afterwards, how many of the old nodes can still be reached, and what does a traversal from head do? (c) Assume the only way a program can reach a node is to follow head, tail or next references. Show that removing the last node of a singly linked list of n ≥ 2 nodes takes at least n − 2 next hops. How many hops does it take in a doubly linked list?

Solution

(a) Let the list have m nodes, well formed. Step 1 (new node n: n.next ← head): starting at n we visit n and then the m old nodes, ending at the old last node, whose next is empty. Step 2 (head ← n): a traversal from head now follows exactly that chain: m + 1 nodes. Step 3: if m = 0, n.next is empty and n is the only node, so tail ← n makes the last node the tail; if m > 0 the last node is still the old tail, which stays correct. Step 4: size = m + 1. So the traversal visits size nodes, the last is tail, tail.next is empty, and head is empty only when size is 0. ∎

(b) After head ← n, the old first node is referenced by nothing: the only reference to it was the old value of head, and no node points at the first node. Then n.next ← head reads the new head, which is n itself, so n.next is n: a cycle of length 1. All m old nodes are unreachable (garbage in Python and Java) although size says m + 1, and a traversal from head visits n, n, n, … forever. (If the second step read the old next field after head had moved, n.next would be empty and the list would shrink to the single node n: that is the bug in Exercise 10.)

(c) To remove the last node t the program must set p.next to empty and tail ← p, where p is the node just before t, the (n − 1)-th node. By assumption the only ways to reach a node are head, tail and next. tail is t, and t has no reference back to p; the only route to p is from head, which is node 1, and node n − 1 is n − 2 next hops later. So at least n − 2 hops, and the loop while p.next is not tail: p = p.next does exactly that many (a 4-node list A → B → C → D takes 2 hops, as in video 4). In a doubly linked list tail.prev is p: 0 hops, and the whole removal is a fixed handful of assignments.

Exercise 4 · Choose the structure. For each workload choose one of: fixed array, dynamic array, singly linked list (with head and tail), doubly linked list (with sentinels), circular singly linked list (with tail). Name the operations that dominate, give their costs, and say in one sentence why you did not pick the runner-up. There is more than one defensible answer when you justify it. (a) A table of the 366 records for the days of a year, read by day number, never resized. (b) An event log: append at the end, read the i-th event, never delete. (c) A music player's playlist with a cursor on the current track: "next" and "previous" move the cursor, "play next" inserts a track right after the current one, and "remove" deletes the current track. (d) A queue of print jobs: add at the end, take from the front. With a plain array, what would it cost to take all n = 1,000,000 queued jobs out one after another, counting item moves, as in chapter 1? (e) A round-robin scheduler: each process gets one time slice in turn; processes join and finish. (f) A sorted list of n names in which you must look names up by binary search.

Solution

Answers vary; these are defensible ones with their costs.

ChoiceDominant operationsWhy not the runner-up
(a)fixed arrayread by index: O(1)a dynamic array adds resizing machinery for a table that never grows
(b)dynamic arrayappend amortized O(1), read i-th O(1)a singly linked list appends in O(1) too, but reading the i-th event costs i hops, up to n − 1
(c)doubly linked list with sentinelsnext / previous: one reference step; "play next": insert_between O(1); "remove current": delete_node O(1)a singly linked list cannot go back in O(1) and needs the predecessor (a walk) to delete the current node; an array shifts n − k items for every insert or delete in the middle
(d)singly linked list with head and tail (or circular with tail)add_last O(1), remove_first O(1)a dynamic array would shift all remaining items at every removal from the front
(e)circular singly linked list with tailserve and rotate: tail = tail.next O(1); a finished process: remove_first O(1); a new one: add_last O(1)with an array every rotation or removal at the front shifts the whole array (a circular array, chapter 3, would also work)
(f)array (dynamic array)binary search: O(log n) index reads; insert O(n) shiftsa linked list needs n/2 hops to reach the middle, so binary search degrades to O(n)

For (d): removing from the front of an array with s items shifts s − 1 of them, and the sizes go n, n − 1, …, 1, so the total is Σ(s − 1) = n(n − 1)/2 = 499,999,500,000 moves for n = 1,000,000, against 1,000,000 constant-time removals from the linked list.

Exercise 5 · A shrink policy. A dynamic array doubles its capacity when full. Now it also has pop (remove the last item). Without shrinking, a program that once held a million items keeps a million slots forever, so we want to halve the capacity at some point after a pop. (a) Policy H: halve when size ≤ capacity / 2. Take an array with capacity 8 holding 8 items and perform "append, pop, append, pop, …". How many elements does each operation copy? What is the total for m operations? (b) Policy Q: halve when size ≤ capacity / 4. Right after a shrink from capacity c the array has exactly c/4 items, and a shrink copies c/4 elements. Right after a growth from capacity c the array has c + 1 items and the growth copied c elements. For each of the two cases find the smallest number of operations that must pass before the next resize. Use this to show that every resize copies at most twice as many elements as the number of operations between it and the next resize, and conclude that m operations cost O(m) copies in total. (c) Generalise Policy Q to "halve when size ≤ capacity / t" (growth factor 2, ignore rounding). For which t does the O(m) bound survive? What goes wrong for t = 2, and why is t = 4 the usual choice?

Solution

(a) Capacity 8, 8 items. Append: the array is full, so it grows to 16 and copies 8; size 9. Pop: size 8 ≤ 16/2, so Policy H shrinks to 8 and copies 8; size 8, capacity 8: the state we started from. Every operation copies 8 = n elements, so m operations copy m·n (2000 operations: 16,000 copies, against 8 for Policy Q). With n as large as you like, the cost per operation is Θ(n), not O(1).

(b) After a shrink from capacity c: the capacity is c/2 and the size c/4; the shrink copied c/4. The next shrink needs size ≤ (c/2)/4 = c/8, which takes at least c/4 − c/8 = c/8 pops; the next growth needs the array full and one more append: at least c/4 + 1 appends. So at least c/8 operations pass, and the shrink's cost c/4 is at most 2 per operation. After a growth from capacity c: the capacity is 2*c*, the size c + 1, and the growth copied c. The next shrink needs size ≤ 2*c*/4 = c/2: at least c/2 + 1 pops; the next growth needs the array full (2*c* items) and one more append: at least c appends. So at least c/2 operations pass, and the growth's cost c is at most 2 per operation. Charge each resize's copies to the operations between it and the next resize: every operation lies after exactly one resize and is charged at most 2 copies, so the total is at most 2*m* plus the cost of the last resize, which is at most the current size ≤ m. Altogether at most 3*m* copies for m operations: O(m), amortized O(1) per append or pop. (Rounding at tiny capacities changes nothing: a resize at capacity 1 or 2 copies at most 2 items.)

(c) For "halve when size ≤ capacity/t" (growth factor 2): after a shrink from c the array has c/t items in capacity c/2, so the next shrink needs at least c/(2*t*) pops and the next growth at least c(t − 2)/(2*t*) appends; the shrink copied c/t, at most max(2, 2/(t − 2)) per operation. After a growth from c the next shrink needs at least c(t − 2)/t pops and the next growth c appends: c copies, at most t/(t − 2) per operation. Both stay bounded exactly when t > 2. For t = 2 (Policy H) the array is right at the threshold after a growth: one pop shrinks it again, and every operation copies n. Larger t only lets the array get emptier before it shrinks (wasting memory), so t = 4 is the usual choice: after a shrink the array is exactly half full, the same distance (a factor of 2) from the next shrink and from the next growth, and both ratios equal 2.

Exercise 6 · Array insert and remove — ex_arrayops.pyExArrayOps.java. A fixed-capacity array whose insert and remove shift items, with a counter of the single-item moves. The tests check the contents after each operation, the error cases and the exact shift counts you derived in Exercise 1, also against a plain list on random operations.

Solution

Reference implementation in solutions/. The loop in insert runs from the first free slot down to index + 1: it moves the last item first, so nothing is overwritten before it has moved. A forward loop would copy the same item into every later slot: inserting X at index 2 of A B C D E that way produces A B X C C C, because C overwrites D and then the copy of C overwrites E before either has moved. The loop runs size − index times, so insert adds size − index shifts; the loop in remove runs from index to size − 2, size − 1 − index times. Both formulas are what the random test accumulates. Appending (index == size) and removing the last item run no loop at all: 0 shifts.

Exercise 7 · Dynamic array with insert, pop and shrinking — ex_growarray.pyExGrowArray.java. Implement resize, append, insert and pop with the growth rule of chapter 2 and the shrink rule of Exercise 5 (Policy Q). The tests check the capacity sequences, the exact copy and shift counts, that alternating append and pop at a growth boundary does not thrash, and the capacity invariant under random operations.

Solution

Reference implementation in solutions/. The numbers the tests encode: appending 9 items gives capacities 1, 2, 4, 4, 8, 8, 8, 8, 16 and 15 copies (resizes at appends 2, 3, 5, 9 copy 1, 2, 4, 8); 17 appends give capacity 32 and 31 copies; inserting 100 items at index 0 shifts 0 + 1 + … + 99 = 4,950 items (Exercise 1(c)) and copies 127 = 1 + 2 + … + 64 (resizes at 2, 3, 5, 9, 17, 33, 65). Popping 9 items from the 9-item array gives capacities 16, 16, 16, 16, 8, 8, 4, 2, 1: the shrinks happen at sizes 4 (16 → 8, copies 4), 2 (8 → 4, copies 2), 1 (4 → 2, copies 1) and 0 (2 → 1, copies 0), so 15 + 4 + 2 + 1 = 22 copies in all. Alternating append and pop with 8 items copies 8 once (the growth to 16) and then nothing; Policy H of Exercise 5 would copy 8 on every operation (16,000 in the test), which is what the thrash test catches. The invariant capacity = 1 or capacity < 4·size (and size ≤ capacity) holds after every operation. Proof: capacities are powers of two. A growth from c leaves capacity 2*c* and size c + 1, and 4(c + 1) > 2*c*; an insert without growth only increases the size; a pop that does not shrink leaves 4·size > capacity or capacity 1 by the shrink condition; a pop that shrinks from c ≥ 8 had 4(size + 1) > c before the pop, so 4·size > c − 4 ≥ c/2, the new capacity; from c = 4 the size is 1 and the new capacity 2 < 4; from c = 2 the new capacity is 1. So the array never keeps more than four slots per item. Note that only append and pop are amortized O(1); insert(i, x) costs n − i shifts.

Exercise 8 · Linked lists — ex_linked.pyExLinked.java and ExDoubly.java. A singly linked list with add_first, add_last, remove(value) and an in-place reverse, then a doubly linked list with sentinels whose delete_node and remove_last change a fixed number of references. The given check() verifies the whole structure and the tests call it after every operation.

Solution

Reference implementation in solutions/. The structure of the cases:

  • add_first: head = Node(value, head) creates the node with the old head as its next and only then moves head (Exercise 3(a)). If tail was empty the new node is also the tail.
  • remove(value): walk with a trailing reference prev. Cases: not found (return false, nothing changes); prev empty, so the node is the head (head = node.next); otherwise prev.next = node.next. If the node was the tail, tail = prev (empty when the list had one node, which makes head and tail both empty). Without prev you would have to walk the list a second time to find the predecessor.
  • reverse: one pass with three references: before overwriting node.next, save it in following; then node.next = prev, prev = node, node = following. At the end head = prev and tail is the old head. No new node is created and only O(1) extra space is used.
  • DoublyLinked: insert_between sets the new node's prev/next first and then pred.next and succ.prev; delete_node makes the neighbours skip the node with two assignments (node.prev.next = node.next, node.next.prev = node.prev); remove_last is delete_node(trailer.prev). Thanks to the sentinels there is no special case for the first, last or only item: the neighbours always exist.

Exercise 9 — insert in read/py/ex_read_shift.pyExReadShift.java.

Solution

The bug: the loop starts at size − 1 instead of size. The first free slot is size, and the item in slot size − 1 has to move into it; the loop never does that move, so slot size − 1 is overwritten by its left neighbour (or by the new value) and slot size is never written. Smallest input: items = ["A", None], size = 1, index = 0: the loop range(0, 0, -1) is empty and items[0] = "X" overwrites A: the result is ["X", None] instead of ["X", "A"]. With ["A","B","C","D","E",None,None], size = 5, index = 2 the result is A B X C D None: E is lost (D overwrote it), and slot 5 is None although the caller now thinks the array holds 6 items. Appending (index == size) works, which is why the bug is easy to miss. Why the AI's test passes: it inserts at index = size − 1 = 2 into ["A","B","C"] and checks only the first three slots, ["A","B","X"]; the lost item C would have been in slot 3, which the test never reads. Test the whole array and the item that should have moved. Fix: for k in range(size, index, -1): (Java: for (int k = size; k > index; k--)). The docstring's "size − index moves" was right; the buggy loop makes size − 1 − index.

Exercise 10 — LinkedList in read/py/ex_read_list.pyExReadList.java (two bugs).

Solution

Bug 1, add_first: the order of the first two steps is wrong. self.head = node moves head first, and then node.next = self.head.next reads the new head's next, which is node.next, which is empty. So the old list is not connected to the new node: all m old nodes become unreachable while size becomes m + 1. Shortest sequence: add_last(1); add_first(0): to_list() is [0], not [0, 1], and size is 2. The AI's test used an empty list for add_first, where there is nothing to lose. Fix: connect the new node to the rest of the list first, then move head: node.next = self.head; self.head = node (Java: node.next = head; head = node;). Bug 2, insert_after: when node is the tail, the new node becomes the last node but tail still points at the old one. Shortest sequence: add_last(1); insert_after(tail, 2); add_last(3): the list is [1, 2] and tail.value is 1; then add_last(3) sets tail.next = 3, which overwrites the link from node 1 to node 2, so to_list() is [1, 3] and 2 is lost. The AI's test inserted after the head of a three-node list, so the tail was never involved. Fix: if node is self.tail: self.tail = new (Java: if (node == tail) tail = created;). The lesson is the one of Exercise 8: after every operation the three facts size = number of reachable nodes, tail = last node reachable, empty list = head and tail both empty must hold. Write a check() like the one in Exercise 8 and call it in the tests; test the empty list, a one-node list and the tail as special cases.

§4Working with AI

When an AI writes an array or a linked list it often writes a loop with a subtle off-by-one or a reference update in the wrong order, and the tests it writes may check only what it got right. Treat the code as a hypothesis and test it:

  1. Check the structure after every operation. For a linked list the three facts are: size equals the number of nodes reachable from head, the last node reachable is tail, and the list is empty exactly when head and tail both are. Write that as a check() function and call it after every operation of every test (Exercise 8 gives one).
  2. Test the special positions. The empty list, one node, the head, the tail, the middle. The AI's insert_after in Exercise 10 works after a middle node and leaves a stale tail when called on the tail; its add_first passes on an empty list, where there is nothing to lose.
  3. Check the whole array, not a prefix. Exercise 9's insert passes a test that reads only the first three slots; compare against list.insert on every (size, index) pair, as the check in the exercises does.
  4. Look for hidden shifting and hidden walks. Python: list.insert(0, x), list.pop(0), del a[0], x in list. Java: ArrayList.add(0, x), remove(0), contains, LinkedList.get(i). A claimed "constant time" is true only if no statement in it shifts or walks.
  5. Count, don't time. Add counters (shifts, copies, hops) as the exercises do, and run the doubling test: ratio near 2 means linear, near 4 quadratic. Do not assume a linked list is faster than an array: in our Java measurement it was slower for a middle insert at every size we tried.
PITFALL · Plausible is not correct.

An AI explains insert as "moves the later items right, last one first" while the loop it wrote starts one slot too early. Read the loop bounds against a one-item example before you trust the prose.
