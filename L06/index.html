Sorted Maps and Balanced Search TreesData Structures · Chapter 6

A binary search tree is fast only while it stays balanced, and keys that arrive in sorted order turn it into a chain. This chapter shows three ways to keep a search tree balanced without knowing which keys come next: the AVL tree repairs itself with rotations, the (2,4) tree is balanced by construction because a node may hold several keys, and the red-black tree is a (2,4) tree written with ordinary binary nodes. Then we use such a tree as a sorted map, which answers "the last name before Morgan" and "everyone from M to P" in O(log n).

Why this matters

about 90–120 minutes (4 videos of 8–10 minutes plus the exercises).

A search tree is only as good as its shape

Inserting the keys 1 to 1,000 in order into a plain binary search tree gives a tree of 1,000 levels, and finding the last key takes 1,000 steps; balanced, the same keys need 10 levels. Real data often arrives in order (timestamps, ids), so a guarantee about the height is not a luxury.

One idea, three structures

A rotation changes the shape of a tree without changing the order of its keys; a (2,4) tree stays balanced by letting nodes hold 1 to 3 keys; a red-black tree is the same (2,4) tree drawn with a colour. Seeing that they are the same thing makes the three rules of a red-black tree something you can derive, not memorise.

A map that knows about order

A hash map finds a key instantly but cannot tell you the next smaller key or a range. A balanced tree can: a sorted map adds first, last, floor, ceiling and range queries, all in O(log n). It is what Java's TreeMap and TreeSet are, and what Python's standard library does not have.

§1Why sorted keys are a problem

Put the keys 1, 2, …, 1,000 into a plain binary search tree one after another. Every new key is larger than all the others, so it goes right, and right again: the tree is a chain of 1,000 nodes (height 1,000) and finding the last key takes 1,000 steps. An AVL tree keeps the same keys at height 10, and for the keys 1 … 2,000 at 11 (code/py/height_experiment_output.txt). With random keys the plain tree is not so bad (height 20 for 1,000 draws, against 12 for the AVL tree), which is why the problem is easy to overlook.

§2The rotation

Take a node x and its right child y. A left rotation lifts y above x: y becomes the root of the subtree, x becomes its left child, and the subtree that was y's left subtree (call it the middle subtree) becomes x's new right subtree. Its keys are larger than x and smaller than y, so that is exactly where they belong. Read the keys from left to right before and after: the same sequence. Only the heights changed. The right rotation is the mirror image.

Rotate a node

Click a node and press Rotate left or Rotate right: the child is lifted, the middle subtree changes sides and the other subtrees keep their shape. The in-order list of the keys below the tree is printed before and after and is identical; the heights of the two nodes involved are shown as they change.

§3The AVL rule and its four cases

The balance factor of a node is the height of its right subtree minus the height of its left subtree (the convention of this course and of the animation: positive means "leans right"). The AVL rule: the balance factor of every node is −1, 0 or +1. Insert a key the ordinary way, then walk back up toward the root; the first node whose factor has become ±2 is the one to fix. There are four shapes (insert in this order → shape without repair → with the AVL repair; code/py/avl_demo_output.txt):

caseinsertwithout repairwith AVLrotations
left-left30, 20, 1030(20(10,-),-)20(10,30)1
right-right10, 20, 3010(-,20(-,30))20(10,30)1
left-right30, 10, 2030(10(-,20),-)20(10,30)2
right-left10, 30, 2010(-,30(20,-))20(10,30)2

The two straight lines are repaired by one rotation of the node. A zig-zag (left-right or right-left) is only moved to the other side by one rotation (Exercise 1), so the child is rotated first to straighten it and then the node: a double rotation, two single ones. All four end as the same tree, 20 on top and 10 and 30 below.

Insert 1 to 7 into an AVL tree

Step through the insertion of the keys 1, 2, …, 7 into an AVL tree: every node shows its balance factor, the node that reaches ±2 turns red, and the repairing rotation is animated. A counter shows the rotations so far (0, 0, 1, 1, 2, 3, 4) and the final tree is 4(2(1,3),6(5,7)).

PREDICT

A tree holds a million keys and one insertion makes some node lean by two. How many rotations might it take to repair the whole tree?

Show the answer

At most two: one rotation, or one double rotation. After the repair the subtree is exactly as high as it was before the insertion, so no node above it sees a change and everything above is balanced again (Exercise 1(c)). The size of the tree does not matter: this is what "one rebalancing step per insertion" means, and the tests check it on random insertions.

§4Why the height is logarithmic

Turn the question around: what is the fewest nodes N(h) an AVL tree of height h can have? A root, one subtree of height h − 1 and, next to it, the thinnest subtree the rule allows, of height h − 2: N(h) = N(h − 1) + N(h − 2) + 1. The counts for h = 1 … 10 are 1, 2, 4, 7, 12, 20, 33, 54, 88, 143, each one more than the two before it added together: the Fibonacci pattern, which grows exponentially. So an AVL tree with n nodes has height at most about 1.44 · log₂ n (precisely h ≤ log_φ(n + 1), Exercise 2); 143 nodes fit in ten levels where a perfect tree needs eight. For a million keys the worst case is 28 levels against 20.

NOTE · The price of balance is small.

Inserting the keys 1 … 1,023 in order into an AVL tree costs 1,013 rotations and leaves a tree of 10 levels. Deleting works the same way: remove the key as in any search tree, then rebalance every node on the way back up (deleting 10 from 20(10,30(25,40)) needs one left rotation and gives 30(20(-,25),40)); unlike an insertion, a deletion can need a rotation at every level.

AVLTree in code/py/avl.py keeps key, value, height in each node; balance_factor is height(right) - height(left), update recomputes a height, rotate_right / rotate_left rotate and update the heights (the node that moves down first), and rebalance picks one of the four cases. The tree counts its rotations and comparisons, which is where the numbers above come from.

AvlTree<K extends Comparable<K>, V> in code/java/AvlTree.java has the same methods (rotateRight, rotateLeft, rebalance) and counters; AvlDemo.java prints the output of the four cases and the trace of the keys 1 … 7.

§1Nodes with several keys

A node with two keys has three children: the first holds keys smaller than the first key, the second keys between the two, the third the rest. A node with k keys has k + 1 children, and searching stays simple: compare with the keys of the node from left to right and follow the child where your key falls. A (2,4) tree has two rules: every node has 2, 3 or 4 children (1, 2 or 3 keys), and all leaves are at the same depth.

§2Insert and split

Search down to a leaf and put the key into it, in order. A leaf can hold three keys; a fourth makes it overfull, and the fix is a split: the third key moves up into the parent, the first two stay together as a left node and the last one becomes a right node. Insert 4, 6, 12 and the leaf is full; insert 15 and it splits, 12 moves up, and as there was no parent 12 becomes a new root: [12] / [4 6] [15]. A split can overflow the parent, which splits too, and so on up; if the root splits, a new root is created above it, and that is the only way a (2,4) tree gets taller.

Insert into a (2,4) tree

Insert the keys 1, 2, …, 13 into a (2,4) tree: the path of the search is highlighted, an overfull node shows its four keys, then splits and the third key moves up; the thirteenth key splits a leaf, the root overflows and splits too, and a new root appears above all the leaves. A counter shows the number of splits.

PREDICT

A binary search tree grows at the bottom: a new key becomes a new leaf below the old ones. Where does a (2,4) tree grow: at the bottom on one side, at the bottom everywhere, or at the top?

Show the answer

At the top. Only a root split adds a level, and it adds one above every leaf at once, so all the leaves stay at the same depth, always. Inserting 1 … 13 in order gives [3 6 9] / [1 2] [4 5] [7 8] [10 11 12] after twelve keys (two levels); the thirteenth key splits a leaf and then the root: [9] / [3 6] [12] / [1 2] [4 5] [7 8] [10 11] [13], three levels (code/py/two_four_demo.py).

§3The trace and the numbers

Inserting 4, 6, 12, 15, 3, 5, 10, 8, 11, 13, 18 one by one needs three splits (at 15, 5 and 11) and ends as [5 10 12] / [3 4] [6 8] [11] [13 15 18]: 11 keys in 2 levels (code/py/two_four_demo_output.txt).

§4Delete: transfer and fuse

To delete a key from an inner node, swap it with its in-order successor, the smallest key to its right, which always sits in a leaf, and delete it from the leaf. If the leaf still has a key, we are done; if it is empty, it has underflowed. The first repair is a transfer: a sibling with two or more keys gives its nearest key to the parent, and the parent gives a key down to the empty node. If no sibling can spare a key we fuse: the empty node, a sibling and the key between them in the parent become one node; the parent has lost a key and may underflow too, so the repair may repeat one level up, and if the root loses its last key the tree gets one level shorter. Removing 3, 12, 15, 4, 8 from the tree above: nothing special for 3, 12 and 15; removing 4 is a transfer ([6 10 13] / [5] [8] [11] [18]); removing 8 is a fuse ([10 13] / [5 6] [11] [18]): 6 keys, 2 levels, 1 transfer, 1 fuse.

Delete from a (2,4) tree

Delete keys from a (2,4) tree: an inner key is swapped with its successor first; an empty node is repaired by a transfer from a sibling (a key travels through the parent) or by a fuse (the empty node, a sibling and the parent's key merge); if the root becomes empty the tree shrinks. A counter shows transfers and fuses.

§5Why the height is logarithmic

With d levels, every node has at least one key and every internal node at least two children, so a tree holds at least 2^d − 1 keys; every node has at most three keys and four children, so at most 4^d − 1. So with n keys the number of levels is between ⌈log₄(n + 1)⌉ and ⌊log₂(n + 1)⌋: for 1,000 keys between 5 and 9 levels, for a million keys between 10 and 19 (Exercise 3). Measured: 6 levels for the keys 1 … 1,000 in order, 11 levels for 100,000 keys in order or random.

NOTE · Which key goes up?

The textbook allows either middle key of an overfull node. This chapter's code always moves the third one up, and the red-black insertion of video 3 sometimes moves the second: both give a valid (2,4) tree.

TwoFourTree in code/py/two_four.py: a node is a list of keys and a list of children (empty for a leaf); insert splits on the way back up (splits counter), remove does the transfers and fuses (transfers, fuses), and check_invariants raises an error unless every node has 1–3 keys in order, one more child than keys, and all leaves are at the same depth.

TwoFourTree<K extends Comparable<K>> in code/java/TwoFourTree.java has the same structure and counters; TwoFourDemo.java prints the trace above.

§1Reading a (2,4) tree with colours

A 2-node (one key) is simply one black node. A 3-node (two keys) is a black node with one red child, on the left or on the right. A 4-node (three keys) is a black node with a red child on each side. A red node means "I am a key that shares my parent's node"; everything black is the top of a node. Take [20] / [10] [30 40]: 20 black, 10 black, 30 black with 40 as its red child.

Two pictures of one tree

Insert keys into a tree shown as a (2,4) tree and press Switch view: the same tree is redrawn as a red-black tree, a 3-node becoming a black node with a red child and a 4-node a black node with two red children; insert again in either view and watch the other one follow.

§2The three rules, derived

  1. The root is black, because the root of the tree is the top of a node.
  2. A red node never has a red child. A red node is a key inside its parent's node, and a node has at most three keys; its children are the tops of other nodes, which are black.
  3. Every path from the root down to a missing child passes through the same number of black nodes. Each black node is one level of the (2,4) tree, and all the leaves of a (2,4) tree are at the same depth.

§3Insertion

Do an ordinary binary search tree insertion and paint the new node red: it joins its parent's node. If the parent is black the node had room, done. If the parent is red there are two reds in a row; look at the uncle, the parent's sibling. A red uncle means the (2,4) node now has four keys: recolour the parent and the uncle black and the grandparent red; that is exactly a split, the middle key moves up into the next node. A black uncle means the node is a 3-node written the wrong way round: one or two rotations rewrite the same node in the right shape; the (2,4) tree does not change at all.

Trace (code/py/red_black_demo_output.txt): insert 10, 20, 30: a rotation, and as a (2,4) tree it was one 4-node, [10 20 30], all along. Insert 40: red uncle, recolour, the 4-node splits: [20] / [10] [30 40]. Insert 50: a rotation. Insert 25: another recolouring. Totals for the six keys: 2 recolourings, 2 rotations, height 4.

NOTE · Deletion is the (2,4) deletion in disguise.

Removing a red leaf is free (it was one key of a bigger node). Removing a black node can leave a node empty, an underflow, and then the same two repairs apply: a transfer is a recolouring plus a rotation, a fuse is a recolouring that may push the shortage one level up. The code in this chapter implements deletion with the three textbook cases; the video explains it through the picture above.

PREDICT

In video 1 we inserted the keys 1 … 1,000 in order into an AVL tree and got 10 levels. How many levels will a red-black tree have: ten again, seventeen, or a thousand?

Show the answer

Seventeen. Taller than the AVL tree but still logarithmic. A red-black tree promises at most 2·log₂(n + 1) levels, the AVL tree promises less (about 1.44·log₂ n). Measured, keys in order (code/py/height_experiment_output.txt): 1 … 1,000 → AVL 10, red-black 17, (2,4) tree 6; 1 … 100,000 → AVL 17, red-black 31 (limit 2·log₂(100,001) ≈ 33.2), (2,4) tree 11. Sorted insertion of 1 … 1,023 into the red-black tree: height 18 (limit 20), 1,005 rotations and 1,004 recolourings.

§4How tall can it get, and what do we get for it

Count the black nodes on any path: that is the number of levels of the (2,4) tree, at most log₂(n + 1). Between two black nodes there is at most one red node, so a path is at most twice as long as its black count: height ≤ 2·log₂(n + 1) (Exercise 3). In return, updates are cheaper: an insertion needs at most 2 rotations and a deletion at most 3 (measured on random operations in the tests), and many repairs are only recolourings. That trade, a slightly taller tree for cheaper updates, is why library tree maps are red-black.

RedBlackTree in code/py/red_black.py is the standard (CLRS-style) tree with parent pointers; to_two_four converts it to the equivalent (2,4) tree so that you can see the correspondence, and check_invariants tests the three rules. Python's standard library has no red-black tree or any other sorted map.

RedBlackTree<K extends Comparable<K>> in code/java/RedBlackTree.java is the same tree with the same converter. In the standard library, java.util.TreeMap and TreeSet are red-black trees (the documentation says so): get, put and remove in O(log n), plus the order queries of video 4.

§1The interface

Think of a phone book. Given a name, a hash map finds the number almost instantly. But ask: who is the last person who comes before Morgan? Or: list everyone from M to P, in order. A sorted map keeps its keys in order and offers, besides get(key), put(key, value) and remove(key):

operationansweron a balanced tree
first, lastthe smallest / the largest keyO(log n): down the left / right edge

ceiling(k)the entry with the smallest key ≥ kO(log n)
sub_map(lo, hi)the entries with lo ≤ key < hi, in orderO(log n + k) for k results

Example (code/py/sorted_map_demo_output.txt, scores 72 Ana, 88 Ben, 95 Cai, 61 Dee, 79 Eli, 84 Fay): in order 61 72 79 84 88 95; first 61, last 95; floor(80) = 79 Eli, ceiling(80) = 84 Fay; sub_map(70, 90) = 72, 79, 84, 88 (four entries); get(79) = Eli, get(80) = none; after remove(88): 61, 72, 79, 84, 95.

Floor and ceiling in a sorted map

Type a key into a sorted map drawn as a search tree: the search path is highlighted, the candidates for the floor and the ceiling are marked as the search passes them, and the two answers are shown; a second field takes a range, and the in-order walk visits only the subtrees that can hold it.

§2Why not a sorted list?

A sorted array with binary search (bisect) finds a key in O(log n) and answers floor, ceiling and ranges just as well. The problem is the insertion: it shifts every entry after the new one. For 9,999 distinct random keys (10,000 draws with one repeat), the AVL-based sorted map needed 121,667 comparisons, height 16, while two sorted lists with bisect moved 24,909,043 entries (both languages; for 10,000 keys already in order the lists move nothing, because every key is appended, and the tree needs 123,617 comparisons).

PREDICT

Binary search makes a sorted list a fast sorted map. For 300,000 random insertions, which is faster, the tree or the sorted list, and by how much?

Show the answer

It depends on the size, and the answer is a trade-off, not a rule. On the machine of this chapter (measured once, code/py/timing_demo_output.txt, code/java/TimingDemo_output.txt): Python with 1,000 keys: the list is faster; with 10,000: list 0.010 s against tree 0.039 s; with 100,000: about even (list 0.965 s, tree 0.865 s); with 300,000: tree 5.9 s, list 9.3 s. Java: 10,000 keys: tree 0.003 s, list 0.013 s; 100,000: tree 0.124 s, list 0.509 s; 300,000: tree 0.474 s, list 2.950 s. A list's shifting is a very fast memory move, so it wins while the data is small; but it grows like n² and the tree like n log n. The step counts above are exact and do not depend on the machine; the seconds are not.

PITFALL · Seconds are a one-off measurement.

The timing tables of this video were measured once on one machine. Another computer, another Python or Java version, or a busy processor gives other seconds. What does not change is the shape: the list is quadratic in total, the tree is n log n.

SortedMap in code/py/sorted_map.py is built on the AVL tree of video 1 (put, get, remove, first_entry, last_entry, floor_entry, ceiling_entry, sub_map, items); BisectMap in the same file keeps two sorted lists and uses bisect and counts the entries it moves. Python's standard library has no sorted map: the bisect module works on a sorted list, and sortedcontainers is a popular third-party package (not used here). dict keeps insertion order, not key order.

AvlSortedMap<K, V> in code/java/AvlSortedMap.java offers the same operations (firstEntry, lastEntry, floorEntry, ceilingEntry, subMap, items) and ArrayListMap is the sorted-list version. The standard library already has it: java.util.TreeMap (a red-black tree) with firstEntry, lastEntry, floorEntry, ceilingEntry, lowerEntry, higherEntry and subMap(from, to), which is half-open, [from, to), by default. The tests compare AvlSortedMap with TreeMap on random operations.

§2Check your understanding

1. What does a rotation never change?

A rotation moves one subtree to the other side and changes the heights, but the keys read from left to right stay the same, so the search-tree property is kept.

2. One key is inserted into an AVL tree and some node now leans by two. How many rebalancing steps does the whole tree need?

After the repair the subtree is as high as before the insertion, so no node above it is out of balance.

3. Where does a (2,4) tree grow taller?

A split moves a key up and a new root is created only when the root itself overflows; that adds a level above every leaf at once, so all leaves stay at the same depth.

4. Keys 1 to 1,000 are inserted in increasing order. Which numbers of levels come out for an AVL tree and for a red-black tree?

Both are logarithmic, but the red-black tree is allowed up to 2·log₂(n + 1) levels and the AVL tree only about 1.44·log₂ n; the red-black tree repays it with at most two rotations per insertion and three per deletion.

5. A program with millions of entries needs floor(key) and range queries, and many insertions. Which structure fits best?

A hash map has no order; a sorted list finds keys fast but every insertion shifts half of it (24.9 million moves for 10,000 random keys in video 4); an unsorted list needs n steps for everything.

Exercise 1 · What a rotation does. Let x be a node whose right child is y. A left rotation at x makes y the root of the subtree and x the left child of y. The three subtrees T1 (the left subtree of x), T2 (the left subtree of y) and T3 (the right subtree of y) keep their shape; T2 changes its parent from y to x. Write h1, h2, h3 for their heights. (a) Draw the tree before and after, and prove that the in-order sequence of keys is the same: write the keys in order using T1 < x < T2 < y < T3. Say why a rotation can therefore never break the search-tree property. (b) Give the heights of x and y after the rotation in terms of h1, h2, h3, and the balance factors of both. (c) Left-left case. A node x has balance factor −2, its left child y has balance factor −1 or 0, and the subtrees below y and x are T1 (y.left), T2 (y.right), T3 (x.right). Prove that one right rotation at x leaves both x and y with balance factors in {−1, 0, 1}. Show that after an insertion (where y leans left, not 0) the repaired subtree is exactly as high as the subtree x was before the insertion, so no node above needs a repair: one rebalancing step per insertion. (d) Left-right case. Now y has balance factor +1. Show with the keys 30, 10, 20 (inserted in this order) that one right rotation at x gives a node with balance factor +2. Prove that rotating y left first and then x right works: let z = y.right have subtrees of heights hl and hr and find all the balance factors.

Solution

(a) Before the rotation the keys in order are: T1 (they are left of x), then x, then T2, then y, then T3. T2 sits in the left subtree of y, so its keys are smaller than y, and in the right subtree of x, so they are larger than x: x < T2 < y. After the rotation y(x(T1, T2), T3) reads T1, x, T2, y, T3 from left to right: the same sequence. A binary tree is a search tree exactly when its in-order sequence is sorted, so a rotation can never break the search-tree property. ∎

(b) x now has the children T1 and T2: height(x′) = 1 + max(h1, h2), balance factor h2 − h1. y has the children x′ and T3: height(y′) = 1 + max(1 + max(h1, h2), h3), balance factor h3 − (1 + max(h1, h2)).

(c) Right rotation at x with left child y (the mirror image of (a)–(b)): the subtrees are T1 = y.left, T2 = y.right, T3 = x.right. Balance(x) = −2 means height(y) − h3 = 2, so 1 + max(h1, h2) = h3 + 2, i.e. max(h1, h2) = h3 + 1. Balance(y) ≤ 0 means h1 ≥ h2, so h1 = h3 + 1 and h2 ∈ {h3, h3 + 1}. After the rotation x′ = (T2, T3) has balance factor h3 − h2 ∈ {0, −1}, and y′ = (T1, x′) has balance factor (1 + max(h2, h3)) − h1 = (h2 + 1) − (h3 + 1) = h2 − h3 ∈ {0, 1}. Both are in {−1, 0, 1}. ∎ After an insertion the case is more specific. Before the insertion x was not too tall, and y had height h3 + 1; the insertion made T1 one level higher (it went into T1), so before it T1 had height h3, and y leaned left only now, so h2 = h3. Then x′ has height h3 + 1, y′ has height 1 + max(h3 + 1, h3 + 1) = h3 + 2, and before the insertion x had height 1 + max(h3 + 1, h3) = h3 + 2: the same. The ancestors of x see no change in height, so none of them is out of balance: one rebalancing step (a single or a double rotation) repairs the whole tree after an insertion, which is what the "Predict" of video 1 says (checked for all heights below 8 in test_ex6_claims.py).

(d) Insert 30, 10, 20: the keys form the zig-zag 30 → 10 → 20 and the root 30 leans left by 2, its left child 10 leans right. One right rotation at 30 gives 10(-,30(20,-)): the new root 10 has height(right) − height(left) = 2 − 0 = +2; the zig-zag just moved to the other side. In the left-right case balance(y) = +1: h2 = h1 + 1 and height(y) = h3 + 2, so h2 = h3 + 1, h1 = h3, and one right rotation gives y′ the balance factor (h3 + 2) − h3 = +2 as computed in (b). Double rotation: let z = y.right with subtrees of heights hl and hr; its height is h2 = h3 + 1, so max(hl, hr) = h3 and, as z is a valid AVL node, hl, hr ∈ {h3 − 1, h3}. Rotating y left puts z above y, rotating x right puts z above x: the result is z(y′, x′) with y′ = (T1, zl) and x′ = (zr, T3). Their heights are 1 + max(h3, hl) = h3 + 1 and 1 + max(hr, h3) = h3 + 1; their balance factors hl − h3 ∈ {−1, 0} and h3 − hr ∈ {0, 1}; and z has two subtrees of height h3 + 1, factor 0. All nodes are in {−1, 0, 1} and the subtree has height h3 + 2 again. ∎

Exercise 2 · The thinnest AVL trees. Let N(h) be the smallest number of nodes of an AVL tree of height h (levels), N(0) = 0, N(1) = 1. (a) Prove N(h) = N(h − 1) + N(h − 2) + 1 for h ≥ 2: say why the root of a thinnest tree has one subtree of height h − 1 and the other of height h − 2, and why each of them is itself a thinnest tree. (b) Compute N(1), …, N(10) and compare with video 1. Prove by induction that N(h) = F(h + 2) − 1, where F(1) = F(2) = 1 and F(k + 2) = F(k + 1) + F(k). (c) Let φ = (1 + √5) / 2, the positive root of φ² = φ + 1. Prove F(k) ≥ φ^(k−2) for all k ≥ 1 and conclude that an AVL tree with n nodes has height h ≤ log_φ(n + 1). Show that log_φ(x) = 1.44… · log₂(x). (d) For n = 1,000,000: how many levels can an AVL tree have at most (use N(28) and N(29))? How many does a perfectly balanced tree need? Compare with the bound of (c).

Solution

(a) A tree of height h has a subtree of height exactly h − 1 (the higher one); by the AVL rule the other subtree has height h − 1 or h − 2. The number of nodes is 1 plus the sizes of the two subtrees, and a subtree of height g has at least N(g) nodes (N is increasing). So N(h) ≥ 1 + N(h − 1) + N(h − 2), and equality is reached by putting a thinnest tree of height h − 1 on one side and a thinnest tree of height h − 2 on the other (it is a valid AVL node: the heights differ by 1). ∎

(b) N(0) = 0, N(1) = 1, N(2) = 2, N(3) = 4, N(4) = 7, N(5) = 12, N(6) = 20, N(7) = 33, N(8) = 54, N(9) = 88, N(10) = 143: the counts of video 1 (each is one more than the two before it added together). Claim N(h) = F(h + 2) − 1: for h = 0 and 1, F(2) − 1 = 0 and F(3) − 1 = 1; if it holds for h − 1 and h − 2 then N(h) = (F(h + 1) − 1) + (F(h) − 1) + 1 = F(h + 2) − 1. ∎ (Checked up to h = 59, and that N(h) really is the minimum over all AVL shapes for h ≤ 7.)

(c) F(1) = 1 ≥ φ⁻¹ and F(2) = 1 ≥ φ⁰. If F(k) ≥ φ^(k−2) and F(k + 1) ≥ φ^(k−1), then F(k + 2) = F(k + 1) + F(k) ≥ φ^(k−1) + φ^(k−2) = φ^(k−2)(φ + 1) = φ^(k−2) · φ² = φ^k. ∎ Hence n ≥ N(h) = F(h + 2) − 1 ≥ φ^h − 1, so φ^h ≤ n + 1 and h ≤ log_φ(n + 1). Since log_φ x = log₂ x / log₂ φ and 1 / log₂ φ = 1 / 0.6942 = 1.4404…, an AVL tree is never more than about 44% taller than a perfect tree (video 1: "about 1.44 times log₂ n").

(d) N(28) = F(30) − 1 = 832,039 ≤ 1,000,000 < N(29) = F(31) − 1 = 1,346,268, so an AVL tree with a million keys has at most 28 levels. A perfect tree needs ⌈log₂(1,000,001)⌉ = 20. The bound of (c) gives log_φ(1,000,001) = 28.71, i.e. also 28 after rounding down: for this n it is exact. So even in the worst case an AVL tree is 40% taller than a perfect one (28 against 20), well below "twice as tall".

Exercise 3 · (2,4) trees and red-black trees. A (2,4) tree has nodes with 1, 2 or 3 keys (2, 3 or 4 children), all leaves at the same depth, and the keys in search order (video 2). Let d be the number of levels. (a) Prove that insertion with splits and deletion with transfers and fuses keep all leaves at the same depth. Say exactly when the depth of the tree changes and which operation does it. (b) Prove that a (2,4) tree with n keys has between ⌈log₄(n + 1)⌉ and ⌊log₂(n + 1)⌋ levels. Evaluate for n = 1,000 and n = 1,000,000 (video 2). (c) Draw a (2,4) tree as a binary tree: a 2-node is a black node, a 3-node a black node with one red child (left or right), a 4-node a black node with two red children. Prove that the result satisfies (i) the root is black, (ii) a red node has no red child, (iii) every path from the root to an empty child contains exactly d black nodes. These are the three red-black rules. (d) Conclude that a red-black tree with n keys has height at most 2·⌊log₂(n + 1)⌋ ≤ 2 log₂(n + 1). Why can the AVL tree promise a smaller constant (Exercise 2) but the red-black tree promise cheaper updates?

Solution

(a) Insertion. The key goes into a leaf, so no leaf moves. A node with four keys a < b < c < d splits into the nodes [a b] and [d] on the same level, and c goes into the parent, which gains a key and a child. If the parent now has four keys it splits in the same way, one level up. If the root splits, a new root is created above the two halves: every leaf gets one level deeper at the same moment. Deletion. The key is taken out of a leaf. An empty node is repaired by a transfer (a key moves from a sibling through the parent into the empty node; nodes stay on their levels) or a fuse (the empty node, a sibling and the parent's key between them become one node on the same level; the parent loses a key and a child). If the root loses its only key, the fused node is its only child and becomes the root: every leaf gets one level shallower. So all leaves are at the same depth always, and the depth changes only by a root split (+1) or by a root that disappears in a fuse (−1). ∎

(b) With d levels every level i has at least 2^(i−1) nodes (every internal node has at least 2 children) and each node has at least one key: n ≥ 1 + 2 + … + 2^(d−1) = 2^d − 1. Every level has at most 4^(i−1) nodes with at most 3 keys: n ≤ 3 · (4^d − 1)/3 = 4^d − 1. Hence 2^d ≤ n + 1 and 4^d ≥ n + 1: ⌈log₄(n + 1)⌉ ≤ d ≤ ⌊log₂(n + 1)⌋. n = 1,000: log₄(1,001) = 4.98 and log₂(1,001) = 9.97: between 5 and 9 levels. n = 1,000,000: 9.97 and 19.93: between 10 and 19 (video 2; measured: 6 levels for the keys 1 … 1,000 in order). ∎

(c) Encode a 2-node as a black node, a 3-node [k1 k2] as a black k2 with the red child k1 on its left (or black k1 with the red child k2 on its right), a 4-node [k1 k2 k3] as a black k2 with the red children k1 and k3; the subtrees below the (2,4) node hang under the right places. (i) The root of the binary tree is the top of the root node: black. (ii) A red node is a key that shares its parent's (2,4) node; its children are the tops of the (2,4) children, which are black: no red node has a red child. (iii) A path from the root to an empty child goes down one (2,4) level after another and meets exactly one black node, the top of the node, on each level; all leaves are at the same depth d, so every such path contains exactly d black nodes. These are the three rules of a red-black tree; the checks run on random (2,4) trees in test_ex6_claims.py. ∎ Both ways of writing a 3-node are valid and both occur (video 3: "on the left or on the right").

(d) A path has at most d black nodes and, as there are no two reds in a row, at most one red node in each (2,4) level: at most 2d nodes, so the height is ≤ 2d ≤ 2·⌊log₂(n + 1)⌋ ≤ 2 log₂(n + 1) (video 3: 31 levels for the keys 1 … 100,000 in order, limit 33). The AVL tree guarantees ≈ 1.44 log₂ n (Exercise 2), so it is the better balanced tree: lookups visit fewer nodes. The red-black tree is more relaxed and pays less to keep the invariant: an insertion needs at most 2 rotations and a deletion at most 3 (video 3), and most repairs are recolourings, whereas an AVL deletion may need a rotation on every level on the way up. That is why a library tree map (Java's TreeMap) is red-black.

Exercise 4 · A calendar. A room is booked for half-open time intervals [start, end). book(start, end) must accept the booking if it overlaps no existing booking and refuse it otherwise, for thousands of requests. (a) Design the structure: what are the keys and the values of the sorted map, and which of floorEntry, ceilingEntry, first, last, subMap do you call? (b) Prove that if the new interval overlaps any booking, it overlaps the booking with the greatest start ≤ start (the floor) or the booking with the smallest start ≥ start (the ceiling): only two neighbours ever need to be checked. Why does it matter that the existing bookings do not overlap each other? (c) Give the cost per request with a balanced search tree and with a sorted array, using the numbers of video 4. Trace it on the bookings (10, 20), (30, 40), (50, 60) and then on the requests (15, 25), (25, 35), (20, 30), (0, 100). (d) Extend the design: "what is the next free slot of length L starting at or after time t?" Which operation do you need and what does it cost?

Solution

(a) Keys: the start times. Values: the end times. book(s, e): floorEntry(s) (the booking that starts last at or before s) and ceilingEntry(s) (the first booking that starts at or after s); accept only if the floor ends at or before s and the ceiling starts at or after e (intervals are half-open, so touching is fine), then put(s, e). In the reference code: Ex6Designs.Calendar (a TreeMap) and the bisect version in ex6_designs.py.

(b) Suppose a booking B overlaps [s, e): B.start < e and B.end > s. Case B.start ≤ s. The floor F is the booking with the greatest start ≤ s, so F.start ≥ B.start. If F ≠ B, then B starts before F, and because bookings do not overlap B must end before F starts: B.end ≤ F.start ≤ s, which contradicts B.end > s. So B = F. Case B.start > s. The ceiling C has the smallest start ≥ s, so C.start ≤ B.start < e; if C ≠ B then C starts in [s, e), so C itself overlaps the new interval. Either way the floor or the ceiling overlaps. ∎ The assumption that the existing bookings do not overlap each other is used in the first case ("B ends before F starts"); with overlapping bookings a long early booking could hide behind a short one and we would have to look further.

(c) With a balanced tree: two searches and one insertion, O(log n) per request. With a sorted array: the two searches are binary searches, O(log n), but inserting shifts on average half of the entries: O(n). Video 4: for 9,999 distinct random keys the sorted lists moved 24,909,043 entries and the AVL tree needed 121,667 comparisons in total (both languages). Trace: (15, 25): the floor (10, 20) ends at 20 > 15 → refused. (25, 35): the ceiling (30, 40) starts at 30 < 35 → refused. (20, 30): the floor (10, 20) ends at 20 ≤ 20 and the ceiling (30, 40) starts at 30 ≥ 30 → accepted. (0, 100): there is no floor, the ceiling (10, 20) starts at 10 < 100 → refused.

(d) Start with the candidate time t. If the floor booking is still running at t, move the candidate to its end. Then look at the next bookings in order (ceilingEntry, then higherEntry): while the next booking starts before candidate + L, move the candidate to the end of that booking and take the next one. Cost: O(log n + k) where k is the number of bookings that were skipped; the next-booking steps are O(log n) each in the worst case but O(1) amortised in an iterator. With each tree node also storing the largest gap in its subtree it becomes O(log n); that is an augmented tree (reference code: next_free / nextFree, checked against a brute-force search).

Exercise 5 · Deleting from a (2,4) tree. The video says: delete from a leaf, swap an inner key with its in-order successor first, and repair an empty node by a transfer or a fuse. (a) Why does the key that replaces a deleted inner key always sit in a leaf? What is the invariant that guarantees it is the smallest key of the right subtree? (b) Write the case analysis for an empty node n with parent p, as a table: which sibling is looked at first, what moves in a transfer (keys and children), what becomes of the three pieces in a fuse, and what can happen to p afterwards. (c) Prove that every repair keeps all leaves at the same depth, and explain when (and only when) the tree gets shorter. (d) Trace the deletions of video 2. It is larger than every key in the left subtrees (it is in the right subtree of k) and smaller than the other keys of the right subtree, so putting it in k's place keeps the order. Deleting it from the leaf is then the leaf case.

Exercise 7 · AVL insertion — ex6_avl.pyEx6Avl.java. The rotations are given. Write the bookkeeping (height, update, balance), then rebalance with the four cases, then insert. Exercise 8 · A sorted map on a search tree — ex6_sortedmap.pyEx6SortedMap.java. The node and the plain insertion are given. Write first, last, floor, ceiling and sub_map / subMap. Solution

Reference: solutions/py/ex6_sortedmap.py, solutions/java/Ex6SortedMap.java. first and last walk down the left or the right edge. floor(key): start at the root; if the current key equals key return it; if it is smaller it is a candidate — remember it and go right to look for a closer one; if it is larger go left. The answer is the last candidate remembered (or none). ceiling is the mirror image. One path from the root: O(height). sub_map(lo, hi): visit n; go left only if lo < n.key (otherwise every key on the left is < lo); add n if lo <= n.key < hi; go right only if n.key < hi. The cost is at most 2·h + k nodes for k results: a visited node outside the range lies on the search path of lo (its key is below lo: we only walked right) or of hi (its key is at least hi: we only walked left), two paths of at most h nodes, and every other visited node is one of the k results (checked in the tests: 300 random ranges on a balanced tree of height 10). A plain traversal of the whole tree would cost n.

The keys are still in order, and — look at this — all stored heights are correct, so a check that reads node.height never notices. Why small examples hide it. Straight-line cases (left-left, right-right) are handled correctly, and sorted insertion produces only those: the usual test "insert 1 … 1,000 and the height is 10" passes (the stored and the real height are 10). The tree is wrong only when a zig-zag occurs, and even then not for every input: of all insertion orders of 1 key, 2 keys, 3, 4, 5, 6, 7 keys the numbers of orders that end with a node of balance ±2 are 0, 0, 2, 0, 8, 272, 1,184 (out of 1, 2, 6, 24, 120, 720, 5,040): the two bad orders for three keys are 1, 3, 2 and 3, 1, 2, and all 24 orders of four keys happen to be fine. A test that tries every order of four keys would have said "correct". The test_ex6_read.pyEx6ReadTest.java tests count them. The fix. In the left-heavy case: if balance(n.left) > 0: n.left = rotate_left(n.left) before rotate_right(n), and the mirror image on the right (the code of Exercise 7). With it all orders of up to 7 keys, and the keys 1 … 1,000, give valid trees. Habits: recompute the balance factors from the real tree (do not trust the stored heights), and test the four cases separately.

Exercise 10 — Avl10 in read/py/ex6_read.py / Ex6Read.Avl10 in read/java/Ex6Read.java. The comment claims that the rotations keep the stored heights up to date, so insert is O(log n) and the height stays logarithmic.

Solution

The bug. In rotate_right / rotate_left the two update calls are in the wrong order: update(y) (the node that moves up) is called before update(x) (the node that moves down and is now y's child). y's new height is then computed from x's old height, which is too large. Insert 10, 20, 30: after the left rotation the root 20 has the children 10 and 30, real height 2, but it stores 1 + max(1, 3) = 4 (x = 10 still carried the height 3 of the old top). The claim "the rotations keep the stored heights up to date" is false. Why small examples hide it. A wrong height does no harm until an ancestor reads it to compute its balance factor; with few keys there is no such ancestor, or the error does not tip a decision. The real shape is a valid AVL tree for all insertion orders of up to 5 keys (0 bad orders among the 1, 2, 6, 24 and 120 orders); the first failures are at 6 keys (192 of 720 orders, for instance 1, 3, 4, 2, 5, 6) and at 7 keys 1,056 of 5,040, including the simplest test of all, the keys 1, 2, …, 7 in order. The stored heights, by contrast, are wrong already at 3 keys (4 of the 6 orders: the four that need a rotation). With 1 … 1,000 in order the tree has real height 14 (a correct AVL tree: 10) and the root stores 16. Insertion still runs in O(log n) per step but the height guarantee is lost: the invariant "balance factors in −1, 0, 1" is broken and the stored heights are not the real ones. The fix. Update the node that went down first: update(x) then update(y) (the order of Exercise 7's rotations). With it every order of up to 7 keys gives a valid AVL tree with correct stored heights, and the keys 1 … 1,000 give height 10. Habits: assert, after every insertion, that every stored height equals the height recomputed from the children, and test with sorted input and random input with more keys than your shape tests have.

§4Working with AI

When an AI writes a balanced tree it usually also claims that it is balanced and how tall it gets. Treat both as hypotheses:

  1. Recompute the heights; do not read the height field. Both buggy trees of Exercises 9 and 10 have correct-looking stored heights in some tests. After every insertion, compute the real balance factors from the tree and assert they are −1, 0 or 1, and assert that every stored height equals the real height.
  2. Test the four cases separately, and test every order of a few keys. An AVL tree without double rotations is fine for sorted input and for every order of four keys, and wrong for 30, 10, 20; the AVL tree with stale heights is right for every order of up to five keys and wrong for the keys 1 … 7. "It works on my example" proves little: try all 720 orders of six keys, and sorted input and random input.
  3. Compare the in-order keys with the sorted input. A rotation bug that loses or duplicates a subtree usually breaks the order or the count; check both.
  4. Ask for the numbers, then check them. For the keys 1 … 1,000 in order a correct AVL tree has 10 levels and a red-black tree 17, a (2,4) tree 6; an AI that says "a red-black tree is better balanced than an AVL tree" is wrong (it is looser) and one that says "AVL needs O(1) rotations per deletion" is wrong too (a deletion can need a rotation per level).
  5. Count rotations. At most 2 per insertion in both trees, at most 3 per deletion in a red-black tree. A tree that does more is rebalancing too often or wrongly.
  6. Distrust claims about the standard library. "Python's dict is sorted", "Python has a built-in sorted map", "TreeMap is a hash map": all false. Python has bisect on lists (O(n) insertions) and the third-party sortedcontainers; Java's TreeMap is a red-black tree and its subMap(from, to) excludes to.
PITFALL · "The tree looks balanced" is not a proof.

A tree can have the right shape for a few inputs and the wrong stored heights, or the right heights and the wrong shape. Check the invariant itself, after every operation.
