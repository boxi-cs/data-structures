Heaps and Priority QueuesData Structures · Chapter 8

An emergency room does not treat patients in the order they walk in, and a computer does not run its tasks in the order they arrive. This chapter builds the structure behind "give me the most urgent one": the priority queue, and the heap, a tree stored in a plain array that keeps only the smallest entry on top and repairs itself in about log n steps. The same idea builds a heap from n entries in O(n) steps and sorts an array in place.

Why this matters

about 90–120 minutes (4 videos of 8–10 minutes plus the exercises).

"The most urgent first" is everywhere

Operating systems pick the next process, simulators pick the next event, Dijkstra's shortest paths (chapter 9) pick the next vertex, and a search for the k best results keeps the k best so far: all of them need a collection with a fast insert and a fast "take out the smallest".

Promise only what you need

A priority queue promises one thing, that the smallest key comes out first, not that the entries are sorted. That weaker promise is why a heap makes both insert and remove-min cost about log n, where a sorted list or an unsorted list pays about n for one of them.

A tree needs no pointers when it is complete

Storing the tree level by level in an array turns "parent" and "child" into index arithmetic; the same layout gives a heap built in O(n) and an in-place sort with a guaranteed O(n log n), and it is the reason the standard libraries' priority queues are arrays.

§1What a priority queue promises

An entry is a pair of a key, the priority, and a value, the thing we care about (a patient, a task). By convention the smaller key is the more urgent one: key 1 beats key 3. The operations are few: insert(key, value) puts a new entry in, min() looks at the entry with the smallest key without removing it, remove_min() takes it out and returns it, and there are a size and a test for empty. Notice what is missing: there is no "give me the third smallest" and no promise that the entries are kept in sorted order. The only promise is about the smallest one.

NOTE · Keys are compared, values are not.

The values can be anything (a dictionary, an object); only the keys need an order. That is also where the standard libraries differ in how they compare ties, as the end of this video shows.

§2Two simple implementations, and what they cost

  • An unsorted list. insert appends: one step, however many entries there are. remove_min has to look at every entry, because the smallest can be anywhere: about n steps.
  • A sorted list (smallest at the end). remove_min takes the last entry: one step. insert has to find the place and shift entries over: up to n steps.
structureinsertremove_minmin
unsorted listO(1)O(n)O(n)
sorted listO(n)O(1)O(1)
heap (video 2)O(log n)O(log n)O(1)

We have not removed the cost by sorting, only moved it from taking out to putting in.

PREDICT

Insert 1,000 entries with increasing keys one after another and then remove all of them. About how many steps does each list need, and about how many comparisons does a heap need?

Show the answer

The unsorted list needs 500,500 steps (1,000 inserts plus 1 + 2 + … + 999 steps of scanning: n + n(n − 1)/2). The sorted list needs 500,500 too, because increasing keys are its worst case (every insert shifts everything). The heap needs 15,965 comparisons: about thirty times fewer. The table printed by the demo (code/py/pq_costs_demo_output.txt, identical in Java):

A "step" of a list is one entry looked at or moved and a heap counts comparisons, so do not read the columns as a precise ratio: the shape is what matters, n² against n log n. For random keys the sorted list pays about half (about 252 thousand for n = 1,000 in both languages) and the heap about the same as before (about 17 thousand).

§3The standard libraries

heapq is not a class but a set of functions that work on a plain list, and it is a min-heap: heappush, heappop, heapify (turns an existing list into a heap in place, in O(n)), and items[0] is the minimum. After pushing 5, 3, 8, 1, 4, 9, 2 the list is [1, 3, 2, 5, 4, 9, 8]: a heap, not a sorted list. Priorities are usually the first item of a tuple, (priority, name). Equal priorities fall through to comparing the second items, which fails for values that cannot be compared (TypeError for two dictionaries), and ties do not come out in the order they went in (offered a b c d e, popped a c e b d); the usual fix is a counter as a tie-breaker. There is no max-heap: negate the keys (code/py/heapq_demo.py).

java.util.PriorityQueue offers offer, poll, peek and an optional Comparator, and it is a min-heap by default (Comparator.reverseOrder() makes it a max-heap). After offering 5, 3, 8, 1, 4, 9, 2 its toString() is [1, 3, 2, 5, 4, 9, 8]: the heap array, not a sorted list; a for-each over new PriorityQueue<>(List.of(9, 4, 7, 1, 8, 2, 6)) prints 1 4 2 9 8 7 6. null is not allowed (NullPointerException), and ties are unspecified (offered a b c d e, polled a e d c b) (code/java/JavaPqDemo.java).

PITFALL · A priority queue is not a sorted collection.

Printing a heapq list or a Java PriorityQueue, or iterating over it, shows the internal array order, which only guarantees that the smallest is first. The only way to get the entries in order is to remove them one by one.

Heap: up-heap and down-heap

A heap is a complete binary tree stored in an array with one local rule: no child is smaller than its parent. Insert adds the entry at the end and climbs (up-heap); remove min moves the last entry to the root and sinks it (down-heap). The tree has only about log₂ n levels, so both take about log n steps.

complete binary treeheap orderindex formulasup-heapdown-heapO(log n)invariant
Heap: up-heap and down-heapVideo in preparation.
IN THIS CHAPTER§1 Two rules: a shape and an order§2 The array layout§3 Insert and up-heap§4 Remove min and down-heap§5 Why it costs O(log n), and why it is correct

§1Two rules: a shape and an order

The shape rule: the tree is complete, every level is full except maybe the last, which is filled from the left. The order rule: every entry is smaller than or equal to its children, so the smallest entry is at the root. That is all: brothers and sisters are not ordered, and a node on one branch can be larger than a node deeper on another branch.

Insert into a heap: up-heap

Pick a key to insert into a min-heap of seven entries: it appears in the last free cell of the array and the leaf of the tree, then climbs one level at a time while it is smaller than its parent; each comparison and swap is highlighted in both views and a counter shows the comparisons and swaps so far.

§2The array layout

Because the tree is complete we need no pointers: store it level by level from left to right. The root is at index 0, its children at 1 and 2, theirs at 3, 4, 5, 6. For the entry at index j (0-based):

formula
left child2j + 1
right child2j + 2
parent(j − 1) / 2, rounded down

A heap of n entries has ⌊log₂ n⌋ + 1 levels: 10 levels for 1,000 entries and 20 levels for 1,000,000. Everything we do follows one path from the top to the bottom or from the bottom to the top, so it costs about the number of levels.

PITFALL · 0-based or 1-based?

Some textbooks number the entries from 1; then the children of j are 2j and 2j + 1 and the parent is ⌊j / 2⌋. Using those formulas on a 0-based array is a classic bug (Exercise 9). Also look at the root: (0 - 1) // 2 is −1 in Python, and items[-1] is the last entry, so no error and a silent wrong answer; in Java (0 - 1) / 2 is 0 (integer division rounds toward zero), so the root is its own parent.

§3Insert and up-heap

Put the new entry at the end of the array. That keeps the tree complete, but the order rule may be broken between the new entry and its parent. Compare it with its parent; if it is smaller, swap them and repeat one level up. In the example the entries 15, 9, 20, 4, 12, 7, 2 are inserted one after another into an empty min-heap (code/py/heap_demo_output.txt):

insertarray afterwardscomparisonsswaps
15[15]00
9[9, 15]11
20[9, 15, 20]10
4[4, 9, 20, 15]22
12[4, 9, 20, 15, 12]10
7[4, 9, 7, 15, 12, 20]21
2[2, 9, 4, 15, 12, 20, 7]22

Inserting 4 puts it at index 3 under 15: smaller, swap; now under 9: smaller, swap; it is the root. Two comparisons, two swaps. Inserting 12 puts it under 9 and it is not smaller than 9, so we stop at once: one comparison.

§4Remove min and down-heap

The smallest entry is at the root, so we take it, but that leaves a hole. Fill it with the last entry of the array: the shape is complete again, but this entry is probably too large for the root. Sink it: compare it with its two children, pick the smaller child, and if that child is smaller than our entry, swap; repeat one level down. Removing 2 from the heap above moves 7 to the root; its children are 9 and 4, the smaller is 4 and it is smaller than 7, so swap; now 7 has only the child 20, which is larger, and we stop: [4, 9, 7, 15, 12, 20] with 3 comparisons and 1 swap. Why the smaller child? Because it moves up to become the parent of the other child, and it must not be larger than its new child.

Remove the minimum: down-heap

Press Remove min: the root leaves, the last entry takes its place and sinks; at each level the two children are compared, the smaller one is highlighted, and the swap is animated in the tree and in the array. The readout keeps the number of comparisons and swaps.

PREDICT

The heap is stored as [2, 9, 4, 15, 12, 20, 7]. Is this array sorted? Is the second smallest entry always at index 1?

Show the answer

No to both. The second smallest entry is 4 and it sits at index 2, after 9. A heap is not a sorted array: it is only organised well enough to find the smallest, and that freedom is why it can be repaired so cheaply.

§5Why it costs O(log n), and why it is correct

Each step of up-heap looks at a constant number of entries (one comparison per level), a step of down-heap at up to two, and there are at most as many levels as the height of the tree: both cost about log n. The worst case for insert is a new entry that is the smallest so far, so it climbs all the way: 1,000 entries inserted in decreasing order cost 7,987 comparisons (about 8 per entry, close to the height) and 64,000 entries cost 894,481 (about 14 per entry): the cost per entry grows like log n, not like n (code/py/build_experiment_output.txt). The repair is correct because of an invariant: during up-heap everything obeys the order rule except possibly the moving entry and its parent, and each swap pushes that single possible violation one level up; during down-heap everything obeys it except possibly the moving entry and its children, and choosing the smaller child makes each swap safe. At most one place is ever broken and we always know where.

ArrayHeap in code/py/array_heap.py keeps the entries in a list data and counts comparisons and swaps; the same pushes as heapq give the same list [1, 3, 2, 5, 4, 9, 8] (the numbers 5, 3, 8, 1, 4, 9, 2). Its parent(0) is (0 - 1) // 2 = -1, the trap above.

ArrayHeap<E> in code/java/ArrayHeap.java keeps the entries in an ArrayList<E> ordered by a Comparator, and counts comparisons and swaps; the same offers as PriorityQueue give the same array [1, 3, 2, 5, 4, 9, 8].

NOTE · Three common mistakes.

Mixing 0-based and 1-based index formulas; sinking along the larger or just the left child (Exercise 10); removing the last entry only after the sinking started, so the heap size is wrong during the repair.

Bottom-up heap construction

You already have n entries in an array and want a heap. Inserting them one by one costs up to n log n, but there is a cheaper way: start at the last entry that has a child and sink every entry in turn, back to the root. Half of the entries are leaves and cost nothing, and adding up what the others can cost gives about n, never more than 2n comparisons.

Bottom-up heap constructionVideo in preparation.
IN THIS CHAPTER§1 The idea§2 A worked example§3 Why bottom-up is cheap

§1The idea

Draw the array as a tree: it is not a heap yet, but a single entry with no children, a leaf, is already a heap. So work from the bottom up: take the last entry that has a child and sink it exactly like the down-heap of video 2; then go back one index and do it again. At each step the two subtrees below the entry are already heaps, so sinking it makes the whole subtree a heap. When the root has sunk, the whole tree is a heap. The last entry that has a child is the parent of the last entry: for ten entries the last index is 9 and its parent is index 4, so we sink the entries at indices 4, 3, 2, 1, 0 in that order.

§2A worked example

The entries are 20, 16, 9, 12, 5, 8, 3, 14, 6, 11 (code/py/build_demo_output.txt):

1[20, 5, 3, 6, 11, 8, 9, 14, 12, 16]32
0[3, 5, 8, 6, 11, 20, 9, 14, 12, 16]42

Load an arbitrary array into the tree and press Step: the loop variable walks from the last internal entry back to the root, each entry sinks with its comparisons highlighted, and two counters show the comparisons and swaps so far. A second button builds the same entries by repeated insertion and compares the totals.

PREDICT

Inserting the same ten entries into an empty heap one by one: more or fewer than 12 comparisons? Is the resulting array the same?

Show the answer

More: 17 comparisons and 12 swaps. And the array is a different valid heap, [3, 6, 5, 9, 11, 16, 8, 20, 14, 12] (bottom-up gave [3, 5, 8, 6, 11, 20, 9, 14, 12, 16]): many arrays are heaps of the same entries, so "the same entries" does not mean "the same cost".

§3Why bottom-up is cheap

Sinking an entry costs at most its height, the number of levels below it, and most entries are near the bottom: about half are leaves (height 0, no cost), about a quarter are one level above (at most 1 each), about an eighth two levels above (at most 2): n/4 · 1 + n/8 · 2 + n/16 · 3 + … is smaller than n. Only the single root can cost the full height log n. More exactly (Exercise 2), the sum of the heights of all n entries is at most n − 1, so a bottom-up build makes fewer than 2n comparisons and fewer than n swaps, whatever the input. Inserting one by one spends its effort in the opposite place: a new entry at the bottom may climb all the way up. For decreasing keys (the worst case for inserting into a min-heap) the difference grows with n (code/py/build_experiment_output.txt, identical in Java):

NOTE · An honest caveat.

Decreasing keys are the worst case for inserting. With random keys a new entry usually stops after a level or two, and inserting one by one costs only about 2.3 comparisons per entry in both languages; bottom-up still wins with about 1.9, and it has a guarantee (never more than 2 per entry). The n log n of inserting is a worst case, not an average; the O(n) of bottom-up holds for every input.

heapq.heapify(numbers) turns a list into a heap in place in O(n): [9, 4, 7, 1, 8, 2, 6] becomes [1, 4, 2, 9, 8, 7, 6]. ArrayHeap(items) in code/py/array_heap.py builds the same way (its heapify method).

new PriorityQueue<>(collection) builds the heap bottom-up in O(n): for List.of(9, 4, 7, 1, 8, 2, 6) it holds 1 4 2 9 8 7 6, the array that a for-each prints. ArrayHeap(Collection, Comparator) in code/java/ArrayHeap.java builds the same way (its heapify); adding the elements one by one with add would be the slower O(n log n) worst case.

PITFALL · The build loop runs from the last internal entry back to the root.

The last internal entry is the parent of the last index, (n - 2) / 2 (integer division). Running the loop upwards (from the root down) or sinking the root first builds something that is not a heap, because the subtrees below an entry are not heaps yet when it sinks; starting at n - 1 is correct but wasteful (the leaves cost no comparisons, only the calls).

Heap sort

A heap gives its smallest entry in about log n steps; take entries out one by one and they come out in order. Heap sort does this inside the array it was given: build a max-heap, then repeatedly swap the root with the last entry of the heap, shrink the heap by one and sink the new root. The sorted part grows at the back while the heap shrinks at the front: O(n log n) in the worst case, O(1) extra memory, and not stable.

heap sortmax-heapin placeO(n log n) worst casenot stablecomparison with merge sort and quicksort
Heap sortVideo in preparation.
IN THIS CHAPTER§1 Two phases§2 A worked example§3 The cost, and how it compares

§1Two phases

Phase one: turn the array into a max-heap, every entry larger than or equal to its children, so the largest is at the root, with the bottom-up method of video 3. Phase two: swap the root with the last entry of the heap; the largest entry is now where it belongs, at the very end of the array. Shrink the heap by one so the last cell is no longer part of it; the new root may be too small, so sink it. Repeat: every round fixes one more cell at the back and the heap in front gets shorter. Why a max-heap? Because the largest must go to the end; a min-heap would put the smallest at the front, where the heap lives, and we would have to move everything. And no second array is needed: the heap in front and the sorted entries behind it share the same cells.

§2A worked example

The same ten entries, 20, 16, 9, 12, 5, 8, 3, 14, 6, 11 (code/py/heap_sort_demo_output.txt, identical in Java). Phase one gives the max-heap [20, 16, 9, 14, 11, 8, 3, 12, 6, 5] with 9 comparisons and 2 swaps. Round one swaps 20 with the last entry 5 (20 is in place) and sinks 5 past 16, 14 and 12: [16, 14, 9, 12, 11, 8, 3, 5, 6, 20], 6 comparisons and 4 swaps counting the first. Round two puts 16 at the end of the heap, round three puts 14, each round costing a few comparisons, fewer and fewer because the heap shrinks. In the end the array is sorted, [3, 5, 6, 8, 9, 11, 12, 14, 16, 20], after 35 comparisons and 23 swaps in all.

Heap sort, in place

Press Run: the array is built into a max-heap, then each round moves the root to the end (the sorted suffix changes colour and the tree loses a node) and sinks the new root. The array and tree views stay linked and two counters keep the comparisons and the swaps.

§3The cost, and how it compares

Phase one is linear: at most 2 comparisons per entry. Phase two does n − 1 rounds, each sinking an entry through at most log₂ n levels with two comparisons per level, so at most about 2n log₂ n comparisons: O(n log n) in the worst case, whatever the input, which quicksort cannot promise, and the extra memory is a handful of variables where merge sort needs a second array of n entries. In practice it pays for that. Comparisons on random input of 4,000 entries (code/py/heap_sort_demo_output.txt; Java's numbers are within a few percent):

sortcomparisons (n = 4,000)
merge sortabout 43 thousand
quicksort (last entry as pivot)about 54–56 thousand
heap sortabout 83 thousand
n log₂ nabout 48 thousand

Heap sort pays about 1.7 · n log₂ n, almost twice as many comparisons as merge sort: every entry that sinks came from the bottom of the heap, so it usually goes all the way back down, at two comparisons per level. There is a second cost these counts do not show: heap sort jumps around the array (from j to 2j + 1) where merge sort and quicksort walk through memory in order, which computers like. A lower bound for any comparison sort is ⌈log₂ n!⌉ comparisons (22 for n = 10; Exercise 3).

PREDICT

Sort [(2, a), (2, b), (1, c)] by the first item with heap sort. Do the two entries with key 2 keep their order?

Show the answer

No. Heap sort gives (1, c), (2, b), (2, a); a stable sort gives (1, c), (2, a), (2, b). Heap sort is not stable: the swap of the root with the last entry jumps over everything in between. Even two entries with equal keys are enough to see it (Exercise 3). If you need stability, sort pairs (key, original position), at the price of O(n) extra memory.

heap_sort(items, key) in code/py/heap_sort.py sorts in place and returns (comparisons, swaps) for the whole sort, build phase included. The standard library has no heap sort: list.sort and sorted use Timsort, which is stable and adapts to partly sorted input. The heapq module offers heapq.nsmallest/nlargest (the k best, Exercise 4) and heapq.merge (Exercise 5) instead.

HeapSort.heapSort(int[]) in code/java/HeapSort.java sorts in place and returns {comparisons, swaps}, and there is a generic version with a Comparator that shows the unstable order of equal keys. The standard library has no heap sort: Arrays.sort(int[]) is a dual-pivot quicksort and Arrays.sort(Object[]) / List.sort use TimSort, which is stable.

§2Check your understanding

1. What does remove_min of a priority queue return?

That is the only promise of a priority queue; it does not even promise that the entries are kept sorted.

2. In a heap stored in an array numbered from 0, where are the children of the entry at index 5?

The children of j are 2j + 1 and 2j + 2; (a) is the 1-based formula (2j and 2j + 1), (c) confuses the children with the neighbours of j, and (d) is the parent of j with its neighbour.

3. A min-heap is stored as [2, 9, 4, 15, 12, 20, 7]. Which statement is true?

A heap only keeps the smallest entry at the root; the largest entry, 20, is at index 5, and the array is not sorted.

4. Building a heap from n given entries bottom-up needs, in the worst case,

Half of the entries are leaves and the sum of the heights of all entries is below n; inserting one by one costs up to n log n in the worst case.

5. Which statement about heap sort is true?

On random input it makes about 1.7 n log₂ n comparisons, almost twice as many as merge sort, and equal keys can change places.

PROOFS

Exercise 1 · The shape of a heap. A heap with n entries is a complete binary tree stored in an array a[0 … n−1]: the levels are stored one after the other, level d (the root has depth 0) is full unless it is the last one, and the last level is filled from the left. (a) Prove that level d occupies the indices 2ᵈ − 1 … 2ᵈ⁺¹ − 2, and that the children of the entry at index j are at 2j + 1 and 2j + 2, and its parent at ⌊(j − 1) / 2⌋ (j ≥ 1). (b) Prove that the height of the heap (in edges) is ⌊log₂ n⌋. How many levels does a heap of 1,000 entries have, and one of 1,000,000? (c) Prove that the internal entries are exactly a[0 … ⌊n/2⌋ − 1], so a heap has ⌈n/2⌉ leaves, and that the last internal entry is at index (n − 2) / 2 (integer division). Find it for n = 10 and check it against video 3. (d) Many textbooks number the entries from 1. Give the formulas for children and parent in that case, and explain what goes wrong if you use them on a 0-based array (Python and Java behave differently for the parent of the root: how?).

Solution

(a) Depth 0 has 1 = 2⁰ entry and a full level d has 2ᵈ entries, so the levels before level d hold 1 + 2 + … + 2ᵈ⁻¹ = 2ᵈ − 1 entries and level d starts at index 2ᵈ − 1 and ends at 2ᵈ⁺¹ − 2 (every level but the last is full). Number the entries of level d from the left: the entry at index j has position p = j − (2ᵈ − 1). The entries of level d + 1 come in pairs below the entries of level d, in the same left-to-right order, so its children are the positions 2p and 2p + 1 of level d + 1, which are the indices (2ᵈ⁺¹ − 1) + 2p and (2ᵈ⁺¹ − 1) + 2p + 1. Substituting p = j − 2ᵈ + 1: (2ᵈ⁺¹ − 1) + 2j − 2ᵈ⁺¹ + 2 = 2j + 1, and the right child is 2j + 2. For the parent, a child c ≥ 1 is 2j + 1 or 2j + 2 for exactly one j, and ⌊(2j + 1 − 1) / 2⌋ = j = ⌊(2j + 2 − 1) / 2⌋, so the parent is ⌊(c − 1) / 2⌋. ∎

(b) By (a) the entry at index i has depth d exactly when 2ᵈ ≤ i + 1 ≤ 2ᵈ⁺¹ − 1, i.e. d = ⌊log₂(i + 1)⌋. The height is the depth of the last entry, index n − 1, so it is ⌊log₂ n⌋. For n = 1,000 it is 9, i.e. 10 levels; for n = 1,000,000 it is 19, i.e. 20 levels (the numbers of video 2).

(c) An entry j is internal when its left child exists: 2j + 1 ≤ n − 1, i.e. j ≤ (n − 2) / 2, i.e. j ≤ ⌊n/2⌋ − 1 (for n ≥ 2). So the internal entries are exactly 0 … ⌊n/2⌋ − 1, there are ⌊n/2⌋ of them and n − ⌊n/2⌋ = ⌈n/2⌉ leaves; the last internal entry is ⌊n/2⌋ − 1 = (n − 2) / 2. For n = 10 it is 4 (internal 0–4, leaves 5–9): video 3 starts at "last internal node 4". (Checked for all n < 2,100 in test_ex8_claims.py.)

(d) 1-based: the children of j are 2j and 2j + 1 and the parent is ⌊j / 2⌋. On a 0-based array these formulas treat index 0 as its own child (2·0 = 0) and the pair (2j, 2j + 1) is shifted by one: the entry at index 2 is never a child of the root. That is Exercise 9. The parent of the root with the 0-based formula (j − 1) / 2: in Python (0 - 1) // 2 is −1 (floor division), and items[-1] is the last entry: no error, a silent wrong answer; in Java (0 - 1) / 2 is 0 (integer division rounds toward zero): the root becomes its own parent. Test for j = 0 explicitly (our parent(0) throws).

Exercise 2 · Bottom-up construction is O(n). The height of an entry is the longest downward path to a leaf (leaves have height 0). Let S(n) be the sum of the heights of all entries of a heap with n entries. (a) Show that S(n) = ⌊n/2⌋ + S(⌊n/2⌋) for n ≥ 2 (and S(0) = S(1) = 0). (Hint: remove all the leaves; what is left, and what happened to the heights?) (b) Conclude that S(n) = ⌊n/2⌋ + ⌊n/4⌋ + ⌊n/8⌋ + … ≤ n − 1. Compute S(10) and check that it matches the ten entries of video 3. For a perfect heap with n = 2ᵏ⁺¹ − 1 entries show that S(n) = n − log₂(n + 1). (c) Sinking an entry of height h takes at most h swaps and at most 2h comparisons. Conclude that building a heap bottom-up from n entries takes fewer than 2n comparisons and fewer than n swaps. How does that fit the 12 comparisons of video 3 (n = 10)? (d) Inserting the n entries one by one costs one up-heap per entry; give an input (ordering) for which this is Θ(n log n) and explain why that does not contradict (c).

Solution

(a) Remove all the leaves of a heap with n ≥ 2 entries. By Exercise 1(c) the leaves are the indices ⌊n/2⌋ … n − 1, so what is left is a[0 … ⌊n/2⌋ − 1]: again a complete tree, with ⌊n/2⌋ entries. Every remaining entry has its height decreased by exactly 1 (its longest downward path ends in a leaf at the bottom; the entry just above that leaf is still there and has become a leaf of the smaller tree, and no new longer path appeared). The removed leaves had height 0, and each of the ⌊n/2⌋ remaining entries had one more than in the smaller tree. So S(n) = ⌊n/2⌋ + S(⌊n/2⌋). ∎

(b) Unrolling, S(n) = ⌊n/2⌋ + ⌊n/4⌋ + ⌊n/8⌋ + …, a sum with at most ⌊log₂ n⌋ non-zero terms, and ⌊n/2ⁱ⌋ ≤ n/2ⁱ, so S(n) ≤ n(1/2 + 1/4 + … + 1/2ᵐ) = n(1 − 2⁻ᵐ) < n, and since S(n) is an integer, S(n) ≤ n − 1. (The exact value is n minus the number of 1-bits of n: checked for all n < 3,000.) S(10) = 5 + 2 + 1 = 8: the five internal entries have heights 1, 1, 1, 2, 3. For n = 2ᵏ⁺¹ − 1: S(n) = Σₕ h · 2ᵏ⁻ʰ = 2ᵏ⁺¹ − k − 2 = n − (k + 1) = n − log₂(n + 1); n = 7: 4 = 2·1 + 2.

(c) An entry that starts a sink at height h is at height ≤ h − t after t swaps, and an iteration of the loop needs the entry to have a child, i.e. height ≥ 1; so there are at most h iterations, each with at most 2 comparisons (child against child, child against entry) and one swap. Summing over the internal entries: comparisons ≤ 2·S(n) ≤ 2(n − 1) < 2n and swaps ≤ S(n) < n. For video 3 (n = 10, S = 8): ≤ 16 comparisons, measured 12 (the fixes cost 1, 2, 2, 3, 4 comparisons at heights 1, 1, 1, 2, 3, bounded by 2, 2, 2, 4, 6). The decreasing input of video 3 gives 1,982 comparisons for n = 1,000 against the bound 1,998.

(d) Decreasing keys with a min-heap (n, n − 1, …, 1): every new entry is the smallest so far and climbs to the root, a climb of ⌊log₂ k⌋ levels for the k-th insert, in total Σₖ ⌊log₂ k⌋ = n log₂ n − O(n): Θ(n log n) (7,987 comparisons for n = 1,000, 894,481 for 64,000 in video 3). There is no contradiction: (c) bounds the bottom-up method; one-by-one insertion builds a (different) heap in more steps, and for random keys it is only about 2.3 comparisons per entry against about 1.9 (the honest finding of video 3: n log n is only its worst case).

Exercise 3 · Heap sort: stability and a lower bound. A sort is stable if entries with equal keys keep their original relative order. (a) Show that heap sort (the algorithm of video 4: build a max-heap, then repeatedly swap the root with the last entry of the heap, shrink the heap and sink the root; a child moves up only if it is strictly larger) is not stable: find an input with only two entries that shows it. Also check the three-entry example of the video. (b) Show how to make any sort stable by sorting pairs (key, original position). Prove that the output is the stable order, and say what it costs in memory. (c) A comparison sort must be able to produce each of the n! orders. Prove that every comparison sort needs at least ⌈log₂ n!⌉ comparisons in the worst case, compute it for n = 10 (video 4 sorts ten entries with 35 comparisons), and show that log₂ n! ≥ (n/2) log₂(n/2), so ⌈log₂ n!⌉ is of order n log n.

Solution

(a) Two entries (1, a), (1, b) with equal keys. Build: the only internal entry is index 0; its child (1, b) is not strictly larger, so nothing moves. Extraction: swap the root with the last entry: [(1, b), (1, a)]. The equal keys changed places: not stable (checked in test_ex8_claims.py). Video 4's example [(2, a), (2, b), (1, c)] gives (1, c), (2, b), (2, a): the 2s are reversed. Heap sort throws the original order away because the swap of the root with the last entry jumps over every entry in between.

(b) Replace every entry x with the pair (x.key, i), where i is its original position, and sort the pairs lexicographically. Distinct pairs have a strict total order, so the sorted sequence is unique; pairs with equal keys appear in increasing i, which is their original order. So the output is exactly the stable order, whatever (unstable) algorithm sorts the pairs. The cost: n extra integers, O(n) memory, and the in-place advantage is gone.

(c) A comparison sort is a binary decision tree (each inner node one comparison, each leaf one output order). To be correct it needs a leaf for each of the n! input orders, and a binary tree of height h has at most 2ʰ leaves, so 2ʰ ≥ n! and the worst case needs h ≥ ⌈log₂ n!⌉ comparisons. n = 10: 10! = 3,628,800, log₂ = 21.79, so at least 22; the heap sort of video 4 used 35 on its input (more than the bound, as it must be; we also checked all 8! inputs for n = 8 against ⌈log₂ 8!⌉ = 16). Lower bound of order n log n: the largest ⌈n/2⌉ factors n, n − 1, …, ⌊n/2⌋ + 1 of n! are each ≥ n/2, so n! ≥ (n/2)^(n/2) and log₂ n! ≥ (n/2) log₂(n/2), which is of order n log n. So heap sort, merge sort and quicksort are optimal up to a constant factor.

DESIGNS

Exercise 4 · The k largest items of a stream. Items arrive one at a time; there are too many to store, but you must be able to report the k largest at any moment (k is small, say 10 or 1,000). (a) Design the algorithm with a heap of at most k entries. Which kind of heap (min or max) do you use and why? What do you do with a new item? (b) Give the cost in comparisons per item and in total for n items (a bound in terms of n and k) and the memory. Trace it on the stream 5, 1, 9, 3, 7, 8, 2 with k = 3 and write the heap after every item. (c) Compare with (i) sorting the whole stream, (ii) a max-heap of all n items followed by k removals, (iii) keeping a sorted list of size k. When is each better?

Solution

(a) Keep a min-heap of the k largest items seen so far: its root is the smallest of the k, the one that must be beaten. A new item x: if the heap has fewer than k entries, insert x. Otherwise compare x with the root; if x is not larger, ignore it; if it is larger, remove the root and insert x (one heapreplace: put x at the root and sink it). The answer is the contents of the heap (sort them if you want them in order). A max-heap would put the largest on top, which tells you nothing about which entry to throw away.

(b) Per item: 1 comparison with the root, and when it is larger at most 2⌊log₂ k⌋ more for the down-heap, so at most 1 + 2⌊log₂ k⌋ per item and O(n log k) in total (plus O(k) or O(k log k) to fill the heap at the start); memory O(k), one pass. Trace (k = 3), heap in array order after each item: 5 → [5]; 1 → [1, 5]; 9 → [1, 5, 9]; 3 > 1, replace the root → [3, 5, 9]; 7 > 3 → [5, 7, 9]; 8 > 5 → [7, 8, 9]; 2 ≤ 7, ignored → [7, 8, 9]. The three largest are 9, 8, 7 (checked in test_ex8_claims.py, also in Java).

(c) (i) Sorting the whole stream: O(n log n) time and O(n) memory, and it needs the whole stream: no good for k ≪ n or an endless stream. (ii) A max-heap of all n items, then k removals: O(n + k log n) time but O(n) memory. (iii) A sorted list of size k: the same O(n) comparisons for the common case "x is too small" but O(k) to insert, so O(nk) in the worst case: better only for tiny k. When k is close to n, sorting is simpler and just as good.

Exercise 5 · Merging k sorted lists. You have k lists, each already sorted, N items in total (think of k sorted log files). (a) Design a merge that outputs the N items in sorted order using a heap that never holds more than k entries. What is an entry, what does the heap compare, and what do you do after each removal? (b) Give the time in terms of N and k, and the extra memory. Trace it on [1, 4, 9], [2, 3, 10, 11], [], [0, 5] and count the removals. (c) Why is "merge the first two lists, then merge the result with the third, …" worse (give its cost for k lists of equal length)? What if you merge the lists in pairs, like merge sort?

Solution

(a) An entry is (value, list number, position in the list): the value is the front item of one list. The heap compares by value (break ties by list number so the merge is deterministic and stable across lists). Put the first entry of every non-empty list into the heap (at most k entries). Repeat: remove the smallest entry, output its value, and if its list has a next item put that item's entry into the heap. At every moment the heap holds exactly one entry for each list that is not finished, so it never holds more than k.

(b) Every item is inserted once and removed once, each in O(log k) (the heap has at most k entries): O(N log k) time and O(k) extra memory (besides the output). Trace for [1, 4, 9], [2, 3, 10, 11], [], [0, 5]: the heap starts with 1, 2, 0 (the empty list contributes nothing); the removals give 0 (then 5 enters), 1 (4), 2 (3), 3 (10), 4 (9), 5 (list 4 is finished), 9 (list 1 is finished), 10 (11), 11: 9 removals = N, and the heap never exceeded 3 entries.

(c) Merging the result so far with the next list costs the length of both: with k lists of m items each, the j-th merge handles (j + 1)m items, in total about k²m/2 = O(Nk), far worse than N log k when k is large. Merging in pairs like merge sort (k/2 pairs, then k/4, …) takes log₂ k rounds of N items each: O(N log k) too, but it needs a whole new list per round (O(N) memory) and all lists available; the heap streams the output with O(k) memory (Python's heapq.merge does exactly this).

Exercise 7 · A priority queue with a custom order — ex8_pq.pyEx8Pq.java. Wrap a heap (yours, heapq or PriorityQueue) in an interface with insert(priority, value), min, remove_min, a custom order (a key function / a Comparator, so a max-queue is one line), and first-in-first-out among equal priorities, which the standard libraries do not promise (video 1 shows a c e b d and a e d c b). Values are never compared.

Solution

Reference: solutions/py/ex8_pq.py, solutions/java/Ex8Pq.java. Entries are stored as (key(priority), sequence number, priority, value) in Python and as (entry, sequence number) with a comparator that compares the order first and the sequence number second in Java. Because the sequence number is unique, two entries are never equal, so (1) the heap never falls through to comparing the values (Python: heapq.heappush(h, (1, {"job": "a"})) twice raises TypeError, as in video 1) and (2) equal priorities come out in insertion order: a strict total order has exactly one sorted order, and sorting by (key, sequence number) is the stable sort of the priorities. A max-queue is key=lambda p: -p (Python) or Comparator.reverseOrder() (Java); for priorities that cannot be negated, use a wrapper class or a comparator. Without the counter, heapq with a class that compares priorities only gave a c e b d in video 1 and java.util.PriorityQueue gave a e d c b: ties are unspecified, and the two libraries differ.

Common mistakes: sinking in a[0 … end] (the sorted entry gets pulled back into the heap), >= instead of strict > (equal entries swap for nothing and the counts change), a call of sorted()/list.sort() (no longer in place). Exercise 9 — Heap9 in read/py/ex8_read.py / Ex8Read.Heap9 in read/java/Ex8Read.java. The comment claims that insert and remove_min are correct and take O(log n).

Solution

The bug. insert uses the 0-based parent formula (j − 1) // 2, but remove_min sinks along the 1-based child formulas 2j and 2j + 1 (copied from a textbook that numbers from 1). The two halves disagree about the tree: insert believes the children of index j are 2j + 1 and 2j + 2, remove_min looks at 2j and 2j + 1. At the root the "children" are indices 0 (the root itself) and 1, so the real right child, index 2, is never compared with the root; one level below, the children of index 1 are looked up at 2 and 3 instead of 3 and 4, and so on. The sinking entry therefore stops, or turns, too early and a larger entry stays above a smaller one: the list stops being a heap.

A small input. Insert 1, 3, 2, 4 (the list is [1, 3, 2, 4]) and call remove_min four times: the calls return 1, 3, 2, 4 instead of 1, 2, 3, 4. After the first call the list is [3, 2, 4]: the root 3 is larger than its child 2. With seven entries, 1, 5, 2, 6, 7, 3, 4 and one remove_min, the list is [4, 5, 2, 6, 7, 3]: the new root 4 was compared only with index 1 (5), never with index 2 (2), and the next call returns 4 although 2 is smaller; the whole sequence comes out 1, 4, 3, 5, 2, 6, 7.

Why small examples do not show it. For every order of 1, 2 or 3 entries the code is correct (we tried all 1 + 2 + 6 orders): after the first removal there are at most two entries, and then comparing the root with index 1 is all there is to do. From four entries on it fails: for 4 entries on 8 of the 24 input orders, for 5 on 24 of 120, for 7 on 3,732 of 5,040. A test with the textbook example of three entries passes; a random test against sorted() with more than three entries finds it at once (test_ex8_read.py).

The claim. "O(log n)" is true (the loop runs at most about log₂ n times) but correctness is not: an algorithm that is fast and wrong is not a heap. The fix: children 2j + 1 and 2j + 2 and the loop condition 2j + 1 < n. The Java class Ex8Read.Heap9 has the same bug ((j - 1) / 2 is fine for j ≥ 1, the children are 2 * j and 2 * j + 1) and the same numbers.

Exercise 10 — Heap10 in read/py/ex8_read.py / Ex8Read.Heap10 in read/java/Ex8Read.java. The comment claims that remove_min sinks the new root along the smaller child so the list is a heap again.

Solution

The bug. The index formulas are right this time, but the code only looks at the left child: it swaps with it whenever it is smaller than the sinking entry and never looks at the right child. The comment says "smaller child"; the code says "left child". Two things go wrong: the right child can be smaller than the left one (the entry should go there), so the smaller of the two ends up below a larger one; and the loop can stop because the left child is not smaller although the right child is.

A small input. Insert 1, 3, 2, 4 and remove the minimum: the new root 4 is compared with its left child 3 and swapped: [3, 4, 2]; the right child 2 is smaller than the new root 3 and no one ever looked at it. The four calls return 1, 3, 2, 4 instead of 1, 2, 3, 4. With seven entries 1, 5, 3, 6, 7, 4, 8 and one remove_min the list is [5, 6, 3, 8, 7, 4]: the root 5 is larger than its right child 3, and the calls return 1, 5, 4, 6, 7, 3, 8.

Why small examples hide it. With at most three entries, after the removal there are at most two entries and the root has at most one child: no choice to make, the "left child" is the smaller child. From four entries on it fails: 8 of the 24 orders of four entries, 60 of 120 for five, and every one of the 5,040 orders of seven entries (so even sorted input shows it: 1, 2, 3, 4, 5 returns 4 before 3). The fix: pick the smaller of the two children, comparing them first when both exist (as ArrayHeap.down_heap in the chapter code does: one comparison between the children, one between the smaller child and the entry). Always test a heap against sorted() with random input of more than three entries and assert the heap property after every operation.

§4Working with AI

When an AI writes a heap or a priority queue it usually also claims that it works and how fast it is. Treat both as hypotheses:

  1. Test against sorted() with more than three entries. Both buggy heaps of Exercises 9 and 10 are correct for every input of up to three entries and fail from four entries on; a random test (insert n random numbers, remove all, compare with the sorted list) finds them at once, and so does asserting the heap property (data[(j - 1) // 2] <= data[j] for every j) after every operation.
  2. Ask which index convention it uses, and test the root. Mixed 0-based and 1-based formulas are the most common heap bug; also check parent(0) (it is -1 in Python and 0 in Java, neither is an error).
  3. Count comparisons, do not just time. An insert that is "O(log n)" can be tested with the doubling test of chapter 1: insert 1,000 decreasing keys and 2,000, and compare the comparisons per entry (about 8 and 9 for the correct heap: 7,987 and 17,964 comparisons).
  4. Distrust claims about the standard library. "Iterating a PriorityQueue gives sorted order", "heapq has a max-heap", "equal priorities come out first in, first out": all false. Print the real behaviour, and add a counter to the entries yourself when you need FIFO ties (Exercise 7).
  5. Ask about the worst case and about stability. A heap sort that is claimed to be "stable" or "faster than quicksort in practice" is wrong on both counts (video 4).
  6. Ask for the max-heap you need. Python's heapq is min-only (negate the keys, or wrap the items), Java needs a reversed Comparator; an AI that sorts descending by "popping from heapq" is probably off by a reverse.
PITFALL · "It returns the smallest, so it is a heap" is not a proof.

The first remove_min of a broken heap is usually right; only the repair after it can be wrong. Test a sequence of removals.
